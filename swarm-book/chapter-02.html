02

跑通第一个 Agent

上一章全是大白话。这一章，我们用 5 行真代码，亲手让一个 Agent 活过来，并逐字看懂每一行到底在干什么。

本章目标

  • 把 Swarm 装到你的电脑上，并配好 API Key。
  • 逐行读懂官方最小示例 bare_minimum.py——总共只有 5 行有效代码。
  • 搞清楚 Swarm()、Agent(...)、messages、client.run(...) 各自扮演什么角色。
  • 亲手运行它，看到 LLM 回你一句问候，并知道那句话是怎么"取出来"的。

一、准备工作：装好 Swarm、配好钥匙

动手之前只需两步。第一步，把 Swarm 这个库装进 Python 环境。Swarm 目前没有发布到 PyPI，所以我们直接从 GitHub 仓库安装：

终端 · 安装 Swarm 
pip install git+https://github.com/openai/swarm.git
这行命令在做什么

pip 是 Python 的"应用商店安装器"。git+https://... 告诉它："别去官方商店找了，直接从这个 GitHub 地址把代码拉下来装上。"装完，你的 Python 里就能 import swarm 了。

第二步，配置 OpenAI API Key。Swarm 默认用 OpenAI 的模型（gpt-4o）来当 Agent 的"大脑"，而访问 OpenAI 需要一把"钥匙"来证明你的身份、并从你的账户扣费。你在 OpenAI 官网申请到一串以 sk- 开头的钥匙后，把它设成一个环境变量：

终端 · 配置 API Key 
export OPENAI_API_KEY="sk-你自己的密钥"
类比：门禁卡

API Key 就像进公司大楼的门禁卡。Swarm 每次去"请教"OpenAI 的大脑时，都要刷一下这张卡。export 相当于把卡放进你终端这个"口袋"，之后同一个终端里跑的程序都能自动摸到它——你的代码里完全不用写钥匙，既省事又安全。

小心

API Key 是要花钱的（按调用量计费），而且等同于你账户的密码。千万不要把它直接写进代码、或提交到 GitHub。用环境变量正是为了避免这种泄露。

二、先看全貌：整个程序就这么点

准备就绪。下面是 Swarm 官方仓库里最小的一个例子，路径是 examples/basic/bare_minimum.py（bare minimum 就是"最低限度"的意思）。它把一个 Agent 从创建到跑起来所需的一切，压缩到了极致：

bare_minimum.py 
from swarm import Swarm, Agent

client = Swarm()

agent = Agent(
    name="Agent",
    instructions="You are a helpful agent.",
)

messages = [{"role": "user", "content": "Hi!"}]
response = client.run(agent=agent, messages=messages)

print(response.messages[-1]["content"])

去掉空行，真正干活的只有 5 处：建引擎、建 Agent、写消息、跑一次、取结果。我们一个一个来拆。

三、逐行精读

第 1 行：把工具从库里拿出来

import 
from swarm import Swarm, Agent

这行从我们刚装好的 swarm 库里，取出两样东西：Swarm 和 Agent。你可能会好奇：一个库里明明有那么多代码，凭什么这两个名字就能直接拿出来用？

答案藏在库的"入口文件" swarm/__init__.py 里，它只有短短几行：

swarm/__init__.py 
from .core import Swarm            # 从 core.py 里拿出引擎类 Swarm
from .types import Agent, Response  # 从 types.py 里拿出数据类 Agent、Response

__all__ = ["Swarm", "Agent", "Response"]  # 声明“对外只公开这三个名字”

__init__.py 就像一家公司的前台：它把散落在各个房间（core.py、types.py）里的重要人物，集中登记在门口。于是外人（我们）只要说一句 from swarm import Swarm, Agent，前台就能直接把人叫出来，我们不必知道他们具体坐在哪个房间。__all__ 这份名单则明确告诉别人：这个库对外正式提供的就是 Swarm、Agent、Response 三样。

第 2 行：创建引擎 client = Swarm()

创建引擎 
client = Swarm()

Swarm() 造出一个"引擎"对象，我们给它起名叫 client。回忆第 01 章那个"会自己转的循环"——它就住在这个引擎里。之后我们要让 Agent 干活，都得通过这个 client 下命令（第 4 行的 client.run(...)）。

类比：招来一位调度主管

client 好比公司里的调度主管：他手里握着那本"工作流程手册"（自动循环）和那把"门禁卡"（自动读取环境变量里的 API Key）。你把员工（Agent）和任务（messages）交给他，他负责一趟趟去请示大脑、执行工具、直到把活办完。

注意括号里是空的 Swarm()——我们什么参数都没传。这说明它有一套开箱即用的默认配置：默认它会自己去连 OpenAI，并自动从环境变量 OPENAI_API_KEY 里读你刚才配的钥匙。不这么写会怎样？ 如果你没配环境变量、又不传自定义客户端，等真正调用大脑时就会因为"没钥匙"而报错。

第 3 步：创建一个最简 Agent

创建 Agent 
agent = Agent(
    name="Agent",                             # 给这个员工起个名字
    instructions="You are a helpful agent.",  # 岗位说明书：你是一个乐于助人的助手
)

这就是我们的第一个 Agent。它是全书最"朴素"的一个——只有一份岗位说明书，连工具箱都是空的。回顾第 01 章的公式：Agent = 说明书 + 工具箱 + 循环。这里的循环由 client 提供，工具箱这次留空，所以真正需要我们填的只有说明书。

  • name="Agent"：员工的名字。这里就直白地叫它 "Agent"。名字在多 Agent 协作、看日志时很有用，但对这个单人示例影响不大。
  • instructions="You are a helpful agent."：这就是第 01 章说的 system prompt（岗位说明书）。它会作为 system 角色的消息，排在对话最前面，告诉大脑"你该以什么身份、什么口吻回答"。
instructions 就是岗位说明书

你没看错——所谓 instructions，在底层就是拼进消息列表最前面的那条 system 消息。把它写成"你是一个耐心的客服"，Agent 就会像客服；写成"你只用文言文回答"，它就满口之乎者也。这一个字段，就决定了 Agent 的人设与行为基调。

你也许注意到我们没写 model、也没写 functions。这是因为 Agent 的这些字段都有默认值（模型默认 gpt-4o，工具箱默认空列表）。至于这些字段的完整定义，正是下一章 types.py 的主角，这里先按下不表。

第 4 步：写好要说的话

准备对话 
messages = [{"role": "user", "content": "Hi!"}]

还记得第 01 章说的吗——我们和大脑打交道，靠的是一份消息列表。这里就是它：一个 Python 列表，里面装着一条消息。每条消息是一个字典，有两个关键字段：

  • "role": "user"：这条话是"用户"（也就是你）说的。
  • "content": "Hi!"：话的内容——一句简单的"你好！"。

为什么要用列表装、而不是直接传一句字符串？因为对话天生是多轮、有先后顺序的：user 说一句、assistant 回一句、user 再追问……全都要按顺序记在这个列表里，大脑才能读懂上下文。现在只有一句，是因为对话刚刚开始。

第 5 步：启动主循环 client.run(...)

跑起来 
response = client.run(agent=agent, messages=messages)

高潮来了。这一行把前面备好的三样东西凑到一起，正式开跑：

  • agent=agent：让哪个员工上工。
  • messages=messages：把当前的对话历史交给他。

调用 run 之后，第 01 章那个"自动循环"就在引擎内部转起来了：它把 instructions 拼成 system 消息、连同 messages 一起发给大脑，拿回回复；如果 Agent 想调用工具就自动执行再问一轮……直到大脑给出最终答复。整个过程结束后，它把结果打包成一个 response 交还给我们。

这个 response 是什么？

run() 返回的不是一句普通字符串，而是一个 Response 对象——一张"办公交接单"，里面装着更新后的完整对话历史（messages）、当前接手的 Agent、以及上下文变量。它的确切结构，我们下一章讲 types.py 时会逐字拆开。

第 6 步：取出最后一句回复

打印结果 
print(response.messages[-1]["content"])

这一行看着有点绕，我们从里往外拆：

  • response.messages：从交接单里取出完整的对话历史列表。此时它比我们最初的 messages 更长了——因为大脑的回复也被追加了进去。
  • [-1]：Python 里 -1 表示"倒数第一个"，也就是列表里最后一条消息。对话历史的最后一条，正是大脑刚生成的那句回复。
  • ["content"]：从那条消息字典里，取出 content 字段，也就是回复的纯文字内容。

合起来就是："把这次对话的最后一句话的文字内容打印出来。" 为什么不直接打印整个 response？因为那样会连角色、工具调用记录等一堆结构一起吐出来，看着乱。我们只关心大脑最终对我们说的那句人话，所以精准地取 messages[-1]["content"]。

四、亲手运行，见证 Agent 说话

把上面的完整代码保存成一个文件，比如 hello.py，确认已经装好 Swarm、配好 OPENAI_API_KEY，然后在终端里运行：

终端 · 运行 
python hello.py

稍等一两秒（这段时间就是引擎在跟 OpenAI 的大脑通信），你会在终端看到类似这样的一句友好问候：

终端输出
Hi there! How can I assist you today?
你的输出可能略有不同

LLM 的回答带有随机性，每次跑出来的措辞未必一模一样——可能是 "Hello! How can I help you?"，也可能换个说法。这很正常，只要是一句得体、乐于助人的问候，就说明你的第一个 Agent 已经成功跑通了！🎉

就这样，你已经完整走了一遍 Agent 的生命周期：建引擎 → 建 Agent → 递话 → 跑循环 → 取回复。虽然这个 Agent 还只会"说话"、不会"做事"（因为工具箱是空的），但骨架已经立起来了。从第 04 章起，我们就给它往工具箱里塞真本领。

常见疑问

为什么 messages 要用一个"列表"来装，不能直接传字符串？

因为对话本质上是一串按顺序排列的消息：谁先说、谁后说、各自扮演什么角色（user/assistant/system），都必须保留下来，大脑才能理解上下文。用列表正好能有序地存放多条消息。这次只有一句，是因为对话刚开头；等到多轮问答时，这个列表会越来越长，每一轮的问和答都追加进去。

run() 返回的 response 里到底有什么？

它是一个 Response 对象，主要装着三样东西：messages（本轮结束后完整的对话历史，包含大脑的新回复）、agent（当前接手的 Agent，多 Agent 交接时会变）、context_variables（上下文变量）。本章我们只用到了 messages。它的完整字段定义，正是下一章 types.py 要讲的内容。

我没写 model，那这个 Agent 用的是哪个模型？

用的是默认模型 gpt-4o。Agent 这个数据类给 model 字段预设了默认值，所以你不写它也能跑。如果想换模型（比如换成更便宜的），只要在创建 Agent 时多写一句 model="gpt-4o-mini" 即可。这些字段的默认值下一章会一一说明。

报错说找不到 API Key 怎么办？

八成是环境变量没配好，或者你换了一个新终端窗口（export 只对当前终端有效）。重新在运行程序的那个终端里执行一遍 export OPENAI_API_KEY="sk-..."，再跑程序即可。想一劳永逸的话，可以把这行写进 ~/.zshrc 或 ~/.bashrc。

本章小结

  • 安装：pip install git+https://github.com/openai/swarm.git；配钥匙：export OPENAI_API_KEY="sk-..."。
  • client = Swarm() 造出引擎，第 01 章的自动循环就住在里面。
  • Agent(name=..., instructions=...) 造出一个最简 Agent，instructions 就是它的 system prompt（岗位说明书）。
  • messages 是有序的消息列表，装着这轮对话的历史。
  • client.run(agent, messages) 启动主循环，返回一个 Response 对象；response.messages[-1]["content"] 取出最后一句回复的文字。
