引擎核心：run 主循环

前六章我们一直在说"Agent 有一个自动循环"。这个循环到底长什么样？就在 core.py 的 run() 里，短短四十行。这是整台发动机的心脏——读懂它，你就真正读懂了 Swarm。

本章目标

  • 把第 01 章那句"Agent = 说明书 + 工具箱 + 自动循环"里的"自动循环"彻底拆开。
  • 看清 run() 的五步主循环：问 LLM → 记录回复 → 判断是否点单 → 执行工具 → 回到开头。
  • 用逐行精读的方式读懂 run() 每一行，尤其是那些"为什么这么写"的关键细节（深拷贝、切片、类型转换）。
  • 顺带读懂两个帮手：handle_tool_calls（执行工具）和 handle_function_result（归一化返回值）。

一、回顾：我们要拆的到底是哪个"循环"

第 01 章我们给 Agent 下过一个极简定义：

第 01 章的定义

Agent = 一份岗位说明书（system prompt） + 一个工具箱（functions） + 一个自动循环（不停地"问 LLM → 执行工具 → 再问"）。

前面几章我们分别讲清了说明书（instructions）、工具箱（functions）、上下文变量、交接。唯独那个"自动循环"，一直是个黑盒——我们只知道"它会自动多轮调用工具直到完成"，但从没看它内部怎么转。

本章就把这个黑盒撬开。它的真身，是 swarm/core.py 里一个叫 run() 的方法。你每次写 client.run(agent=..., messages=...)，进的就是这里。

二、核心图：run() 的五步主循环

类比：厨房里的循环

还记得第 01 章"点菜"的比喻吗？run() 就是餐厅里那个不知疲倦的服务员：把顾客（LLM）的话传到厨房、催菜、上菜，然后回来问顾客"还要点什么吗？"。只要顾客还在点菜（还有 tool_calls），服务员就一直来回跑；顾客说"够了，这就是我的答案"（没有 tool_calls），服务员才停下。max_turns 则是餐厅打烊时间——再想点也不伺候了。

三、逐行精读 run() 主体（非流式分支）

下面是 core.py 中 run() 的核心部分（第 252–292 行，即 stream=False 的普通分支）。我们先看全貌，再用"左代码 / 右讲解"的方式逐段拆。

swarm/core.py · run()（第 252-292 行） 
active_agent = agent
context_variables = copy.deepcopy(context_variables)
history = copy.deepcopy(messages)
init_len = len(messages)

while len(history) - init_len < max_turns and active_agent:

    # get completion with current history, agent
    completion = self.get_chat_completion(
        agent=active_agent,
        history=history,
        context_variables=context_variables,
        model_override=model_override,
        stream=stream,
        debug=debug,
    )
    message = completion.choices[0].message
    debug_print(debug, "Received completion:", message)
    message.sender = active_agent.name
    history.append(
        json.loads(message.model_dump_json())
    )  # to avoid OpenAI types (?)

    if not message.tool_calls or not execute_tools:
        debug_print(debug, "Ending turn.")
        break

    # handle function calls, updating context_variables, and switching agents
    partial_response = self.handle_tool_calls(
        message.tool_calls, active_agent.functions, context_variables, debug
    )
    history.extend(partial_response.messages)
    context_variables.update(partial_response.context_variables)
    if partial_response.agent:
        active_agent = partial_response.agent

return Response(
    messages=history[init_len:],
    agent=active_agent,
    context_variables=context_variables,
)

第一段：循环开始前的四行"准备工作"

循环还没开始，先把四样东西准备好。这四行看似平平无奇，其实每一行都藏着"为什么必须这么写"的讲究。

active_agent = agent
记住"当前是谁在说话"。 active_agent 是整个循环里最重要的变量——它指向"此刻负责回答的 Agent"。一开始就是你传进来的那个 agent。发生交接（第 06 章）时，改的就是它。
context_variables = copy.deepcopy(context_variables)
深拷贝上下文变量，绝不污染调用者的原始数据。 循环里会不断往 context_variables 里写东西（工具可以更新它）。如果不拷贝直接改，就会连带改掉调用者传进来的那个字典——调用者会莫名其妙发现自己的变量被 run() 偷偷改了。深拷贝 = 复印一份自己用，原件不动。
history = copy.deepcopy(messages)
同理，把消息列表也复印一份。 循环里会疯狂往 history 追加消息（LLM 的回复、工具的结果……）。深拷贝保证调用者传进来的 messages 列表始终保持原样，不被 run() 撑大。
init_len = len(messages)
记住"起跑线"在哪。 记下开局时消息有几条。循环结束后，我们只想把本次新产生的消息还给调用者，而不是把人家原来那几条也重复还回去。init_len 就是那把"从这里往后才是新增"的尺子（最后 history[init_len:] 会用到它）。
为什么两处都要 deepcopy？

核心原则：函数不该偷偷改掉调用者传进来的东西（这在编程里叫"避免副作用"）。messages 和 context_variables 都是可变对象（list / dict），Python 里直接赋值只是"起个别名"，改别名就是改原件。copy.deepcopy 才是真正复印一份。少了这两行，多次调用 run() 就会互相干扰，非常难排查。

第二段：while 循环的"护栏"

while len(history) - init_len < max_turns and active_agent:
循环的两个继续条件，缺一不可。
① len(history) - init_len < max_turns：本轮已经新增了多少条消息？只要还没超过 max_turns（默认无穷大 float("inf")），就继续。这是防止 LLM 和工具"来回拉扯停不下来"的安全护栏。
② and active_agent：还得有一个"当前 Agent"在岗。如果某次交接把 active_agent 设成了 None，循环就自然停止。

第三段：① 问 LLM，② 记录回复

completion = self.get_chat_completion( agent=active_agent, history=history, ... )
①问 LLM。 把"当前 Agent"和"全部历史"交给 get_chat_completion，它内部会拼上 system 说明书、把工具箱转成 LLM 能懂的格式，然后真正发请求给 OpenAI。（这个帮手第四节细讲。）
message = completion.choices[0].message
取出 LLM 这一轮回的那条消息。 OpenAI 的返回结构里，choices[0].message 就是模型说的话——可能是纯文本回答，也可能是"我要调用某某工具"。
message.sender = active_agent.name
盖个"这话是谁说的"的章。 给消息加一个 sender 字段，标明是哪个 Agent 说的。多 Agent 交接时，这让你能在历史里分清哪句是英语 Agent、哪句是西语 Agent 说的。
history.append( json.loads(message.model_dump_json()) ) # to avoid OpenAI types (?)
②把回复追加进历史——但要先"洗成普通 dict"。 LLM 返回的 message 是一个 OpenAI 的特殊对象（带类型）。这里先 model_dump_json() 转成 JSON 字符串，再 json.loads() 变回朴素的 Python 字典。
为什么绕这一圈？避免让 OpenAI 的专有类型"污染"我们的历史列表。 历史里全是干净的 dict，后续处理、序列化、打印都方便，也不会绑死在某个库的类型上。

第四段：③ 判断——LLM 还点单吗？

if not message.tool_calls or not execute_tools: debug_print(debug, "Ending turn.") break
③循环的"刹车"在这里。 两种情况会 break 跳出循环：
① not message.tool_calls：LLM 这轮没有要调用任何工具——说明它已经给出了最终答案，活儿干完了，停。
② not execute_tools：调用方明确设了 execute_tools=False，表示"我不想让你真的执行工具"，那也停。
这一句就是整个 Agent"知道什么时候该收工"的关键。

第五段：④ 执行工具，处理交接与上下文更新

partial_response = self.handle_tool_calls( message.tool_calls, active_agent.functions, context_variables, debug )
④真正执行 LLM 点的那些工具。 把 LLM 要调的工具清单、当前 Agent 的工具箱、上下文变量都交给 handle_tool_calls。它会逐个执行工具，把结果打包成一个 partial_response（里面有：工具产生的消息、更新的上下文变量、以及可能的"要切换到哪个 Agent"）。
history.extend(partial_response.messages)
⑤把工具结果并入历史。 工具跑出来的结果（role="tool" 的消息）追加到 history。下一圈再问 LLM 时，它就能看到"工具查到了什么"，从而组织下一步回答。
context_variables.update( partial_response.context_variables)
合并上下文变量。 如果工具更新了上下文变量（第 05 章），在这里合并进主 context_variables，供后续轮次使用。
if partial_response.agent: active_agent = partial_response.agent
交接切换（第 06 章的第三步！）。 如果某个工具返回了一个 Agent，这里就把 active_agent 换成它。下一圈循环就由新 Agent 接手。这一句和第 06 章讲的"三步换人"是同一件事——现在你看到它在主循环里的确切位置了。

执行完这一段，循环回到 while 顶部，带着更新后的 history、context_variables、active_agent 再问 LLM 一轮——如此往复。

第六段：循环结束，只把"新增的"还回去

return Response( messages=history[init_len:], agent=active_agent, context_variables=context_variables, )
打包结果返回。 关键是 history[init_len:]——用开头记下的那把尺子 init_len，只切出本次新产生的消息还给调用者（调用者原来的消息就不重复给了）。同时把最终的 active_agent（可能已经交接过）和 context_variables 一并打包成 Response 返回。
这也解释了第 06 章为什么 response.messages[-1] 拿到的是新回复——因为 messages 只含新增部分。
一句话总括 run()

准备好 active_agent / history / context_variables → 循环【问 LLM → 记录回复 → 没点单就 break → 否则执行工具、合并结果、可能换人】→ 把新增消息打包返回。四十行，一台完整的 Agent 引擎。

四、两个关键帮手

run() 把"执行工具"和"归一化返回值"这两件脏活，分别交给了两个帮手函数。读懂它们，第 06 章的交接、第 05 章的上下文注入才算彻底闭环。

帮手 A：handle_tool_calls（第 89-137 行）——真正跑工具的地方

core.py · handle_tool_calls 
def handle_tool_calls(self, tool_calls, functions, context_variables, debug) -> Response:
    function_map = {f.__name__: f for f in functions}   # 按函数名建一张"名字→函数"的字典
    partial_response = Response(messages=[], agent=None, context_variables={})

    for tool_call in tool_calls:                # LLM 可能一次点了好几个工具，逐个处理
        name = tool_call.function.name
        # handle missing tool case, skip to next tool
        if name not in function_map:            # LLM 点了个不存在的工具？
            debug_print(debug, f"Tool {name} not found in function map.")
            partial_response.messages.append({  # 不崩溃！回一条"错误"消息，继续下一个
                "role": "tool",
                "tool_call_id": tool_call.id,
                "tool_name": name,
                "content": f"Error: Tool {name} not found.",
            })
            continue
        args = json.loads(tool_call.function.arguments)   # LLM 给的参数是 JSON 字符串，解析成 dict
        debug_print(debug, f"Processing tool call: {name} with arguments {args}")

        func = function_map[name]
        # pass context_variables to agent functions
        if __CTX_VARS_NAME__ in func.__code__.co_varnames:  # 这个函数需要 context_variables 吗？
            args[__CTX_VARS_NAME__] = context_variables     # 需要就悄悄注入进去（第 05 章）
        raw_result = function_map[name](**args)             # ★ 真正执行工具函数！

        result: Result = self.handle_function_result(raw_result, debug)  # 把返回值归一化成 Result
        partial_response.messages.append({      # 把工具结果作为一条 role="tool" 消息记下来
            "role": "tool",
            "tool_call_id": tool_call.id,
            "tool_name": name,
            "content": result.value,
        })
        partial_response.context_variables.update(result.context_variables)
        if result.agent:                        # 工具返回了 Agent？记下"要交接"（第 06 章第二步）
            partial_response.agent = result.agent

    return partial_response

逐点说清这段的四个精彩设计：

  • 先建一张"名字 → 函数"的地图（function_map）。LLM 点单时只会给函数名字（字符串），我们得靠这张地图找到对应的真函数。
  • 容错，不崩溃。如果 LLM 点了个根本不存在的工具（它偶尔会犯迷糊），代码不会报错崩掉，而是回一条 "Error: Tool xxx not found." 消息，然后 continue 处理下一个。这条错误消息会喂回给 LLM，它读到后通常会自我纠正。
  • 参数来自 LLM，需要解析。tool_call.function.arguments 是 LLM 生成的一段 JSON 字符串，json.loads 把它变成真正的参数字典 args，再用 **args 传给函数。
  • 悄悄注入 context_variables。如果工具函数的参数列表里有 context_variables，框架会自动把上下文塞进去——而这个参数对 LLM 是隐藏的（还记得 get_chat_completion 里把它从工具描述里 pop 掉了吗）。这就是第 05 章"上下文变量"能被工具用到的原理。
工具是并行还是串行执行的？

这里是一个 for tool_call in tool_calls: 的串行 for 循环——按顺序一个接一个执行。那 Agent 上的 parallel_tool_calls=True 是什么意思？它只是允许 LLM 在一轮里一次性"点多个单"（返回多个 tool_calls），至于这些单子，框架仍然是老老实实按顺序挨个做的。所以"parallel"指的是"LLM 可以一次多点几样"，不是"我们同时开好几个线程跑工具"。

帮手 B：handle_function_result（第 71-87 行）——把返回值"归一化"

工具函数五花八门：有的返回字符串、有的返回数字、有的返回一个 Agent（交接）、有的直接返回一个 Result 对象。handle_function_result 的职责就是把这些统统"归一化"成同一种东西——Result，好让上层代码不用操心具体是哪种。

core.py · handle_function_result 
def handle_function_result(self, result, debug) -> Result:
    match result:
        case Result() as result:          # 情况一：本来就是 Result → 原样返回
            return result

        case Agent() as agent:            # 情况二：返回值是 Agent → 交接信号
            return Result(
                value=json.dumps({"assistant": agent.name}),  # value 里塞一句说明性文字
                agent=agent,              # 把 Agent 记进 Result.agent
            )
        case _:                           # 情况三：其它（字符串/数字/...）
            try:
                return Result(value=str(result))   # 一律转成字符串塞进 value
            except Exception as e:
                error_message = f"Failed to cast response to string: {result}. ..."
                debug_print(debug, error_message)
                raise TypeError(error_message)

三种情况看 Result 的三个字段（回顾第 03 章 types.py）就全懂了：value（字符串结果）、agent（要不要交接）、context_variables（要不要更新上下文）。

  • 返回 Result：说明工具作者想精细控制（同时给结果、切 Agent、更新上下文），直接原样用。
  • 返回 Agent：识别为交接，把 Agent 装进 Result.agent——这正是第 06 章交接的"第一步"。
  • 返回其它：一律 str(...) 转成字符串当作普通数据。如果连字符串都转不成，就明确报错提示"请让工具返回字符串或 Result"。

小实验：给循环设个"一圈就停"

把调用改成 client.run(agent=english_agent, messages=messages, max_turns=1)。max_turns=1 意味着"最多新增 1 条消息就停"。这时循环第一圈问完 LLM、追加了那条"要调用工具"的消息后，len(history)-init_len 就已经不小于 1 了，循环条件不满足，工具还没来得及执行、更没交接，就停了。你会看到最终回复不再是西班牙语——这个反例能让你对 max_turns 这道护栏印象深刻。

常见疑问

run() 到底什么时候才停？

有两种停法：

  • 正常停（最常见）：某一圈 LLM 返回的消息里没有 tool_calls——它不想再调工具了，认为已经能给出最终答案。此时 if not message.tool_calls: break 生效，循环干净利落地结束。
  • 护栏停：新增消息数达到了 max_turns（默认无穷大，所以通常不触发），或者 active_agent 被交接成了 None。这是防止"LLM 和工具无限拉扯停不下来"的兜底。

另外把 execute_tools=False 也会在第一次遇到 tool_calls 时立即 break（相当于"只问不做"）。

为什么进 run() 一开始就要对 messages 和 context_variables 做 deepcopy？

因为循环内部会反复修改这两个东西（往 history 追加消息、往 context_variables 写值）。Python 里 list / dict 是"传引用"的：如果不复印，run() 的修改会直接改到调用者传进来的原始对象上。

后果很隐蔽：比如你写了个循环多次调用 run()，每次都传同一个 messages 列表——如果不 deepcopy，第一次 run 就把它撑大了，第二次的对话历史就全乱了。deepcopy 保证"我在自己的副本上折腾，绝不动你的原件"，这是良好函数设计的基本礼貌（无副作用）。

LLM 一次点了 3 个工具，是同时并行跑，还是一个个来？

一个个串行来。 handle_tool_calls 里是 for tool_call in tool_calls: 的普通 for 循环，按 LLM 给的顺序挨个执行，前一个跑完才跑下一个。

容易混淆的是 Agent.parallel_tool_calls=True 这个设置。它管的是"允不允许 LLM 在一轮里一次性点多个单"（即返回多个 tool_calls），跟"我们这边怎么执行"无关。所以：LLM 可以一次多点，但 Swarm 仍是顺序执行。如果某个工具很慢，会阻塞后面的工具。

为什么把 LLM 回复 json.loads(message.model_dump_json()) 转来转去？直接 append 不行吗？

直接 append 也能跑，但会让 history 里混进 OpenAI 库的特殊对象类型。作者的意图（看注释 to avoid OpenAI types）是：让历史列表里清一色都是朴素的 Python 字典。

好处有三：① 序列化/存盘/打印都简单；② 不把整个框架绑死在 OpenAI 的类型上，将来换别的模型客户端更容易；③ 和工具产生的那些手写 dict 消息（role="tool"）保持格式统一。这一"转圈"是用一点点性能换取历史结构的干净与可移植。

本章小结

  • run() 就是第 01 章那句"自动循环"的真身，是整台 Swarm 发动机的心脏。
  • 循环前的四行准备：active_agent（记住当前是谁）、deepcopy 两份（不污染调用者数据）、init_len（记住起跑线）。
  • 五步主循环：①问 LLM → ②回复追加进 history（先洗成普通 dict）→ ③没 tool_calls 就 break → ④ handle_tool_calls 执行工具（可能更新 context、可能交接）→ ⑤结果并入 history，回到①。max_turns 是防死循环的护栏。
  • handle_tool_calls 串行执行工具：建名字→函数地图、容错跳过不存在的工具、解析 LLM 给的 JSON 参数、按需注入 context_variables、把结果记成 tool 消息、识别交接。
  • handle_function_result 把工具五花八门的返回值归一化成 Result：是 Result 原样用、是 Agent 当交接、其它一律转字符串。
  • 最后 return Response(messages=history[init_len:], ...)——只把本次新增的消息还给你。
