05

上下文变量

"用户叫什么、user_id 多少"这类信息，既不该让 LLM 瞎填，又要在整场对话里被记住、被工具用到。Swarm 用一个"随身档案袋"优雅地解决了它。

本章目标

  • 理解 context_variables（上下文变量）是什么：Agent 的"随身档案袋"。
  • 学会用函数式 instructions：让 system prompt 根据档案袋动态生成（比如用名字问候）。
  • 看懂框架的两个"魔法"：怎样把档案袋喂给动态 instructions，又怎样自动塞进工具函数。
  • 体会 Swarm 的设计巧思：约定优于配置，以及"这些数据为什么不让 LLM 看见"。

一、什么是上下文变量：Agent 的随身档案袋

想象你是一名客服。每次接待客户，手里都夹着一个档案袋，上面写着"这位客户叫 James，会员号 123"。无论对话进行到第几轮、你要查账户还是要打招呼，随手翻档案袋就知道客户是谁——你不需要每句话都重新问一遍"请问您贵姓"。

类比：随身档案袋

context_variables 就是 Agent 的随身档案袋：一个普通的 Python 字典，装着"用户是谁、user_id 多少、当前订单号"等跨轮次都要记住的信息。它会一直跟着这场对话，动态生成的问候语能用它，工具函数也能翻它。

为什么不把这些信息直接写进对话消息里让 LLM 记？因为像 user_id=123 这种是程序内部数据，不该由 LLM 来"猜"或"填"（它可能填错，甚至编一个）。档案袋让这类数据在程序侧可靠地流转，稍后你会看到框架甚至会特意把它对 LLM 藏起来。

二、逐行精读：context_variables.py

先看官方示例的全貌，再逐块拆解。它做了两件有代表性的事：用名字问候用户，以及让一个工具函数读取档案袋。

examples/basic/context_variables.py 
from swarm import Swarm, Agent

client = Swarm()


# ① 函数式 instructions：system prompt 根据档案袋"动态生成"
def instructions(context_variables):
    name = context_variables.get("name", "User")
    return f"You are a helpful agent. Greet the user by name ({name})."


# ② 一个能读档案袋的工具函数
def print_account_details(context_variables: dict):
    user_id = context_variables.get("user_id", None)
    name = context_variables.get("name", None)
    print(f"Account Details: {name} {user_id}")
    return "Success"


agent = Agent(
    name="Agent",
    instructions=instructions,          # 注意：这里传的是"函数"本身，不是字符串
    functions=[print_account_details],
)

# ③ 准备档案袋
context_variables = {"name": "James", "user_id": 123}

① 函数式 instructions：会"看人下菜碟"的说明书

第 03 章讲过，Agent 的 instructions（系统提示词）既可以是一个固定字符串，也可以是一个 Callable（可调用的函数）。这里就是后者：

动态 instructions 
def instructions(context_variables):
    name = context_variables.get("name", "User")   # 从档案袋取名字，取不到就用 "User"
    return f"You are a helpful agent. Greet the user by name ({name})."

它接收档案袋，返回一段随档案袋内容变化的说明书。档案袋里 name="James"，生成的 system prompt 就变成"…用名字（James）问候用户"。为什么用 .get("name", "User") 而不是 ["name"]？——用 .get 带默认值，即使档案袋里没有 name 也不会报错（KeyError），而是安全地退回到 "User"。这是写"档案袋读取"时的好习惯。

② 能读档案袋的工具函数

print_account_details 是一个普通工具函数（回忆第 04 章：放进 functions 就能被 Agent 使用）。它的特别之处只有一点——它的参数里有一个正好叫 context_variables 的参数：

能读档案袋的工具 
def print_account_details(context_variables: dict):
    user_id = context_variables.get("user_id", None)
    name = context_variables.get("name", None)
    print(f"Account Details: {name} {user_id}")
    return "Success"

就靠这个特定名字的参数，框架会自动把档案袋递到它手里（下一节揭秘原理）。函数返回 "Success"，这个返回值会作为工具执行结果喂回给 LLM。

③ 把档案袋交给 run()

最后，我们把档案袋通过 run() 的 context_variables 参数传进去，它就会在这场对话里全程可用。

三、框架内部的三个"魔法"

示例代码看起来很省心：我们既没手动把 name 拼进 prompt，也没手动把档案袋传给工具。这些"自动"的部分，都藏在 core.py 里。这里有三处巧思。

魔法一：instructions 是函数就调用它

在组装发给 LLM 的消息前，框架先决定 system prompt 到底是什么（core.py 的 get_chat_completion）：

swarm/core.py · get_chat_completion 
instructions = (
    agent.instructions(context_variables)   # 若 instructions 是函数 → 传入档案袋、调用它
    if callable(agent.instructions)         # callable() 判断它是不是"可调用"的
    else agent.instructions                 # 否则它就是普通字符串，直接用
)
messages = [{"role": "system", "content": instructions}] + history

一句话：用 callable() 判断 instructions 是不是函数。是函数，就把档案袋传给它、拿到动态生成的字符串；不是函数（是普通字符串），就原样使用。这就是我们的 instructions(context_variables) 能被自动调用、并拿到档案袋的原因。

魔法二：按参数名自动把档案袋塞进工具

当 LLM 要求调用某个工具时，框架在真正执行前会做一次检查（core.py 的 handle_tool_calls）：

swarm/core.py · handle_tool_calls 
# __CTX_VARS_NAME__ = "context_variables"  （文件顶部定义的常量）

func = function_map[name]
# 如果这个工具函数的参数名里，有一个正好叫 "context_variables"…
if __CTX_VARS_NAME__ in func.__code__.co_varnames:
    args[__CTX_VARS_NAME__] = context_variables   # …就自动把档案袋塞进去
raw_result = function_map[name](**args)

拆开看：

  • __CTX_VARS_NAME__ 是文件顶部定义的常量，值就是字符串 "context_variables"。
  • func.__code__.co_varnames 能列出这个函数所有局部变量名（含参数名）。
  • 整句是说：如果工具函数的参数里有一个正好叫 context_variables，框架就悄悄把档案袋作为这个参数传进去。
设计巧思：约定优于配置

框架没有让你写任何"请把档案袋给我"的配置或装饰器，而是约定：只要你的工具函数参数名叫 context_variables，就自动能拿到它。这叫"约定优于配置（convention over configuration）"——用一个大家都遵守的命名约定，省掉一堆繁琐设置。所以参数名必须一字不差叫 context_variables，拼错就拿不到。

魔法三：把档案袋从 LLM 眼前藏起来

这里是最点睛的一笔。第 04 章说过，框架会用 function_to_json 把工具函数翻译成说明书给 LLM。但 print_account_details 有个 context_variables 参数——如果照实翻译，LLM 就会以为"我调用这个工具时得填一个 context_variables 参数"，然后瞎编一个。这显然不对。于是框架在生成说明书后，专门把它抹掉（同样在 get_chat_completion 里）：

swarm/core.py · 对 LLM 隐藏档案袋 
tools = [function_to_json(f) for f in agent.functions]
# hide context_variables from model —— 别让 LLM 看到这个参数
for tool in tools:
    params = tool["function"]["parameters"]
    params["properties"].pop(__CTX_VARS_NAME__, None)   # 从参数清单里删掉
    if __CTX_VARS_NAME__ in params["required"]:
        params["required"].remove(__CTX_VARS_NAME__)     # 也从"必填"里删掉

.pop(..., None) 表示"如果有 context_variables 这个参数就删掉，没有也不报错"。这样一来：LLM 完全看不见这个参数，自然不会去填它；而档案袋则由"魔法二"在程序侧悄悄注入。分工清清楚楚——LLM 只填它该填的业务参数，内部数据由框架负责。

四、图解：一个档案袋，两条去路

档案袋进入 run() 后，会同时流向两个地方：动态生成的 instructions，以及带 context_variables 参数的工具函数。而对 LLM，它是隐藏的。

五、跑一个完整例子

完整的 context_variables.py 会跑两次 run()：第一次让 Agent 打招呼（触发动态 instructions），第二次让它打印账户详情（触发能读档案袋的工具函数）。

examples/basic/context_variables.py（完整） 
from swarm import Swarm, Agent

client = Swarm()


def instructions(context_variables):
    name = context_variables.get("name", "User")
    return f"You are a helpful agent. Greet the user by name ({name})."


def print_account_details(context_variables: dict):
    user_id = context_variables.get("user_id", None)
    name = context_variables.get("name", None)
    print(f"Account Details: {name} {user_id}")
    return "Success"


agent = Agent(
    name="Agent",
    instructions=instructions,
    functions=[print_account_details],
)

context_variables = {"name": "James", "user_id": 123}

# 第一次：打招呼 —— 触发动态 instructions，用名字问候
response = client.run(
    messages=[{"role": "user", "content": "Hi!"}],
    agent=agent,
    context_variables=context_variables,
)
print(response.messages[-1]["content"])

# 第二次：打印账户详情 —— 触发工具函数，读取档案袋
response = client.run(
    messages=[{"role": "user", "content": "Print my account details!"}],
    agent=agent,
    context_variables=context_variables,
)
print(response.messages[-1]["content"])

运行方式（需配置 OPENAI_API_KEY，会真正调用大模型）：

终端 
export OPENAI_API_KEY="sk-..."
python context_variables.py

预期输出（措辞每次略有不同，重点看行为）：

终端输出
Hi James! How can I help you today?
（第一次：因为动态 instructions 读到了 name=James，Agent 主动用名字问候）

Account Details: James 123
Your account details have been printed successfully.
（第二次：工具函数 print_account_details 拿到档案袋，
 打印出 "Account Details: James 123"，随后 Agent 回复已成功打印）
对照三个魔法看输出

第一次能叫出"James"，是魔法一把档案袋喂给了动态 instructions；第二次打印出 James 123，是魔法二把档案袋自动塞进了 print_account_details；而整个过程中 LLM 从没被要求填 context_variables，是魔法三把它藏了起来。

常见疑问

context_variables 会被发给 LLM 吗？会泄露 user_id 吗？

作为工具参数是不会的——框架专门用 params["properties"].pop("context_variables", None) 把它从工具说明书里删掉了（魔法三），LLM 根本看不到这个参数、也不会去填它。不过要注意：如果你在动态 instructions 里主动把某个值拼进了 prompt（比如把名字写进问候语），那部分就会作为 system prompt 发给 LLM。所以"藏起来"针对的是工具参数；你自己主动放进 prompt 的内容当然会发出去。

工具函数怎样才能拿到档案袋？

只有一个条件：把参数名取成正好叫 context_variables。框架靠 if "context_variables" in func.__code__.co_varnames 来检测（魔法二）。名字必须一字不差——写成 ctx、context_vars 都拿不到。这就是"约定优于配置"：约定好这个名字，就不用任何额外声明。

instructions 传函数和传字符串有什么区别？

传字符串：system prompt 固定不变。传函数（Callable）：框架用 callable() 检测到它是函数后，会把当前档案袋传进去调用它（魔法一），于是 prompt 可以随档案袋动态变化——比如根据不同用户名生成不同问候语。呼应第 03 章：instructions 的类型既可以是 str 也可以是 Callable。

档案袋里没有某个键（比如没写 user_id）会怎样？

取决于你怎么读。例子里都用了 .get("user_id", None) 这种带默认值的安全写法，取不到就返回默认值（None 或 "User"），不会崩。如果用 context_variables["user_id"] 这种方括号取法，缺键就会抛 KeyError。所以读档案袋推荐用 .get() 并给个合理默认值。

本章小结

  • context_variables 是 Agent 的"随身档案袋"——一个普通字典，装着跨轮次要记住的内部信息。
  • 魔法一：callable() 判断 instructions 是函数就调用它，实现动态 system prompt。
  • 魔法二：工具函数只要有个叫 context_variables 的参数，框架就自动把档案袋塞进去——约定优于配置。
  • 魔法三：生成工具说明书时把 context_variables pop 掉，对 LLM 隐藏，避免它瞎填内部数据。
