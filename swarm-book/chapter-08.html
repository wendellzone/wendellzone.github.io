流式输出

为什么 ChatGPT 的字是一个个"蹦"出来的？本章拆开 run_and_stream，看 Swarm 如何把 LLM 吐出的一堆小碎片，实时拼成一句完整的话。

本章目标

  • 理解流式（streaming）和普通输出的区别，以及它为什么体验更好。
  • 明白 LLM 是把回复切成很多小碎片（chunk / delta）一点点吐出来的。
  • 逐行读懂 core.py 的生成器函数 run_and_stream。
  • 读懂 util.py 的 merge_chunk / merge_fields——如何把碎片拼成完整消息。

一、先讲个类比：上菜的两种方式

回忆一下前面几章：我们调用 client.run(...)，程序会一直转，直到 LLM 说完最终答案，才一次性把结果返回给我们。这就像去餐厅点了一桌菜，厨师非要等所有菜都做好，才用一个大托盘一起端上来——你只能干等，前面十分钟屏幕上一个字都没有。

类比：做好一道先上一道

流式（stream）则相反：厨师做好一道就先端一道。对应到聊天界面，就是你看到文字一个字一个字往外蹦。虽然总时间差不多，但用户"立刻看到反应"，体验好太多——这正是 ChatGPT 打字机效果的由来。

二、LLM 是"碎片式"吐字的

要实现打字机效果，光靠我们自己"假装"一个字一个字显示是不行的——因为普通 run 拿到结果时，整句话早就生成完了。真正的流式，需要 LLM 本身支持一边生成一边往外送。

事实上，LLM 内部就是一个词一个词（准确说是一个 token 一个 token）生成的。开启流式后，它不再"憋着"等全部生成完，而是每生成一小段就立刻发出来。这一小段，官方叫 chunk（数据块），每个 chunk 里携带的那一点点新增内容，叫 delta（增量）。

delta 长什么样

一个 delta 可能只带几个字，比如 {"content": "你"}、下一个 {"content": "好"}；如果 LLM 正在"点单"调用工具，delta 里带的就是工具调用参数的一小段字符串，比如 {"tool_calls": [{"function": {"arguments": "{\"loc"}}]}。碎片本身不完整，必须靠我们把它们接起来。

所以流式处理的核心任务只有一件事：把源源不断到来的碎片，累加拼接成一条完整的消息。下面这张图就是本章的灵魂：

三、run_and_stream：一个"边算边吐"的生成器

处理流式的主角，是 core.py 里的 run_and_stream 方法（第 139–229 行）。在读代码前，先扫清一个概念障碍：生成器（generator）。

什么是生成器？

普通函数用 return 一次性交出结果就结束了。生成器用的是 yield：它能算出一个结果就先"吐"一个出去（同时函数暂停在原地），等外面来取下一个时再接着往下算。
好比一条"传送带"：不是等所有货物打包好一起交付，而是做好一件就往带子上放一件，外面的人边收边用。这正好契合流式——碎片来一个、往外送一个。

先看它的开头：这是个生成器（函数体里有 yield），负责准备好"账本"，然后进入主循环。

swarm/core.py · run_and_stream（准备阶段） 
def run_and_stream(
    self,
    agent: Agent,
    messages: List,
    context_variables: dict = {},
    model_override: str = None,
    debug: bool = False,
    max_turns: int = float("inf"),
    execute_tools: bool = True,
):
    active_agent = agent                          # 当前"上班"的 Agent（可能会被交接替换）
    context_variables = copy.deepcopy(context_variables)  # 深拷贝，避免污染调用者的字典
    history = copy.deepcopy(messages)             # 深拷贝对话历史，本函数内部随意增删
    init_len = len(messages)                      # 记住"原始历史"有多长，最后好切出"新增部分"

    while len(history) - init_len < max_turns:    # 只要没超过最大轮数就一直转
active_agent = agent
当前干活的 Agent。之所以用一个新变量而不是直接用 agent，是因为工具可能触发交接（第06章），这里要能随时被换成别的 Agent。
context_variables = copy.deepcopy(...) history = copy.deepcopy(messages)
深拷贝：复制一份全新的、和外面互不相干的数据。为什么这么写：函数内部要往 history 里疯狂追加消息，如果不拷贝，就会把调用者传进来的原始列表也改乱——这是很隐蔽的 bug。
init_len = len(messages)
先记下"原始历史"有多长。函数结尾会用 history[init_len:] 精准切出"这次新产生的消息"，不把用户原来传进来的旧消息重复返回。
while len(history) - init_len < max_turns:
主循环。条件是"新增消息数还没到上限"。max_turns 是保险丝——万一 Agent 陷入"不停调工具"的死循环，也能强制停下。

进入循环后，第一步是搭一个空消息模板，等着往里塞碎片。请特别注意 tool_calls 用了 defaultdict：

swarm/core.py · 空消息模板 
    message = {
        "content": "",                    # 文本内容，初始空字符串，碎片会往后拼
        "sender": agent.name,             # 这条消息由谁说的
        "role": "assistant",              # 角色固定是"助手"
        "function_call": None,
        "tool_calls": defaultdict(        # 关键：工具调用用 defaultdict 存
            lambda: {
                "function": {"arguments": "", "name": ""},
                "id": "",
                "type": "",
            }
        ),
    }
defaultdict 的巧思：碎片乱序也不怕

普通字典你访问一个不存在的键会报错。defaultdict 则会在你首次访问某个键时，自动用你给的模板造一个空值填进去。
为什么这里非它不可？因为 LLM 可能同时调用多个工具，碎片带着 index（第几个工具）陆续到达，而且顺序不保证。有了 defaultdict，代码写 message["tool_calls"][2] 时，哪怕 2 号工具的碎片先到、里面还什么都没有，也能自动开好一个空槽位往里塞——不用提前知道总共有几个工具、也不怕碎片乱序。

模板备好，就去问 LLM。注意这次传的是 stream=True——这是和普通 run 唯一的实质差别，它让 get_chat_completion 返回一个可迭代的碎片流而不是一整条消息。

swarm/core.py · 发起流式请求并消费碎片 
        # 用当前历史和 Agent 发起请求，stream=True 表示"要流式"
        completion = self.get_chat_completion(
            agent=active_agent,
            history=history,
            context_variables=context_variables,
            model_override=model_override,
            stream=True,
            debug=debug,
        )

        yield {"delim": "start"}              # 向外发一个"回复开始"的信号
        for chunk in completion:              # 遍历源源不断到来的碎片
            delta = json.loads(chunk.choices[0].delta.json())  # 取出这一片的增量数据
            if delta["role"] == "assistant":
                delta["sender"] = active_agent.name  # 补上"谁说的"，方便外面打印
            yield delta                       # 把这一片原样吐给外面（让 UI 立刻显示）
            delta.pop("role", None)           # 拼接前把 role/sender 摘掉
            delta.pop("sender", None)         # （它们不是要累加的内容，只是标记）
            merge_chunk(message, delta)       # 把这一片累加进完整 message
        yield {"delim": "end"}                # 向外发一个"这段回复结束"的信号
yield {"delim": "start"} ... yield {"delim": "end"}
delim 是 delimiter（分隔符）的缩写。这两句不带任何内容，纯粹是给外面的界面打标记："一段回复要开始了 / 刚结束了"。UI 收到 start 就可以另起一行、收到 end 就知道该换行——第09章的打印函数正是靠它。
for chunk in completion:
遍历碎片流。因为 completion 是流式的，这个 for 循环会随着碎片陆续到达而一次次转动，而不是一瞬间跑完。
delta = json.loads(chunk.choices[0].delta.json())
从 OpenAI 返回的对象里，把这一片的增量掏出来、转成普通 Python 字典。为什么转 dict：后面 merge_chunk 是按字典操作的，也方便直接 yield 给外面用。
yield delta
先吐再拼。注意顺序：碎片先原样 yield 给外面（UI 立刻把这个字显示出来，打字机效果就来自这里），然后才 merge 进内部 message。这样用户感知到的是实时的。
delta.pop("role", None) delta.pop("sender", None)
拼接前把 role、sender 两个"标记字段"摘掉。为什么：它们只是元信息，不是要累加的正文；如果留着，merge 时会把 "assistant" 一遍遍拼成 "assistantassistant..."。
merge_chunk(message, delta)
核心动作：把这一片累加进完整 message。具体怎么加，下一节拆 merge_chunk。

碎片全部收完、拼接成完整 message 后，剩下的逻辑就和普通 run（第07章）几乎一模一样了：整理工具调用、判断要不要结束、执行工具、可能切换 Agent。

swarm/core.py · 收尾与工具处理 
        # 把 tool_calls 从 defaultdict 转成普通列表（按序号取出所有值）
        message["tool_calls"] = list(
            message.get("tool_calls", {}).values())
        if not message["tool_calls"]:
            message["tool_calls"] = None      # 一个工具都没调，就置空
        debug_print(debug, "Received completion:", message)
        history.append(message)               # 完整消息进历史

        if not message["tool_calls"] or not execute_tools:
            debug_print(debug, "Ending turn.")
            break                             # 没有要调的工具 → 回合结束，跳出循环

        # 把拼好的 tool_calls 字典还原成 SDK 对象，好交给执行器
        tool_calls = []
        for tool_call in message["tool_calls"]:
            function = Function(
                arguments=tool_call["function"]["arguments"],
                name=tool_call["function"]["name"],
            )
            tool_call_object = ChatCompletionMessageToolCall(
                id=tool_call["id"], function=function, type=tool_call["type"]
            )
            tool_calls.append(tool_call_object)

        # 执行工具，可能更新 context_variables、可能触发交接
        partial_response = self.handle_tool_calls(
            tool_calls, active_agent.functions, context_variables, debug
        )
        history.extend(partial_response.messages)
        context_variables.update(partial_response.context_variables)
        if partial_response.agent:
            active_agent = partial_response.agent   # 交接：换人干活

    yield {
        "response": Response(                 # 循环结束后，最后 yield 出完整结果
            messages=history[init_len:],      # 只返回本次新增的消息
            agent=active_agent,
            context_variables=context_variables,
        )
    }
message["tool_calls"] = list( message.get("tool_calls", {}).values())
把前面用 defaultdict 装着的工具调用，按 .values() 全取出来变成普通列表。到这一步碎片已经拼完整了，defaultdict 的历史使命结束，转回普通结构供后续使用。
if not message["tool_calls"]: break
这就是循环的出口：LLM 这一轮没有点任何工具，说明它给出的是最终答案，回合结束。（和第07章 run 的终止条件是同一个道理。）
tool_calls = [] ... Function(...) ...
流式拼出来的工具调用是纯字典，而执行器 handle_tool_calls 想要的是 SDK 的对象类型。这一段就是把字典"包装"回对象——这是普通 run 不需要做的额外一步（run 拿到的本来就是对象）。
yield { "response": Response(...) }
压轴的一 yield。整个循环结束后，把最终完整的 Response（含全部新消息、当前 Agent、上下文）打包成 {"response": ...} 吐出去。外面正是靠"看到带 response 键的那一片"来判断流结束、拿到最终结果。

四、merge_chunk / merge_fields：碎片是怎么"接"起来的

真正干"拼接"活的，是 util.py 里这两个小函数。先看 merge_fields——一个会自己钻进去的递归合并器。

swarm/util.py · merge_fields 
def merge_fields(target, source):
    for key, value in source.items():          # 遍历新碎片里的每个字段
        if isinstance(value, str):             # 如果值是字符串
            target[key] += value               # → 直接"拼接"到已有内容后面
        elif value is not None and isinstance(value, dict):  # 如果值是字典
            merge_fields(target[key], value)   # → 递归钻进去继续合并
if isinstance(value, str): target[key] += value
字符串就拼接。这是打字机效果的本质：content 字段每来一片就 += 一次，"" → "你" → "你好" → "你好呀"……越接越长。工具调用的 arguments 参数也是字符串，同理一段段拼成完整 JSON。
elif ... isinstance(value, dict): merge_fields(target[key], value)
字典就递归。比如 tool_calls 里嵌着一层 function: {arguments, name}，遇到这种嵌套字典就再调一次自己，钻进去把里层的字符串也拼好。为什么用递归：结构可能有多层，递归能自动适配任意深度，代码却极短。

再看 merge_chunk——它在 merge_fields 的基础上，专门处理 tool_calls 这个"需要按序号归位"的特殊字段。

swarm/util.py · merge_chunk 
def merge_chunk(final_response: dict, delta: dict) -> None:
    delta.pop("role", None)                    # 再保险地摘掉 role，不参与拼接
    merge_fields(final_response, delta)        # 先把普通字段（如 content）合并进去

    tool_calls = delta.get("tool_calls")       # 看这一片里有没有工具调用
    if tool_calls and len(tool_calls) > 0:
        index = tool_calls[0].pop("index")     # 取出"这是第几个工具"的序号
        merge_fields(
            final_response["tool_calls"][index],  # 定位到对应槽位
            tool_calls[0]                         # 把这片的工具参数拼进去
        )
merge_fields(final_response, delta)
先用上面那个通用合并器，把 content 之类的普通字段拼好。工具调用比较特殊，所以下面单独处理。
index = tool_calls[0].pop("index")
这是"按序号归位"的关键。每个工具调用碎片都自带一个 index，说明它属于第几个工具。pop 把 index 取出来（同时从字典里删掉，因为它不该被拼进最终数据）。
merge_fields(final_response["tool_calls"][index], tool_calls[0])
拿着 index 定位到对应槽位，再把这片碎片拼进去。回扣前面的 defaultdict：正因为 tool_calls 是 defaultdict，即使某个 index 首次出现、还没有槽位，这里也能自动新建——碎片无论怎么乱序到达，都能精准归位到属于自己的那个工具上。

五、亲手消费这个碎片流

下面这段小程序不依赖任何辅助函数，手动遍历 run(stream=True) 返回的生成器，让你直观看到"碎片一片片来、最后才拿到完整 Response"。

stream_demo.py 
from swarm import Swarm, Agent

client = Swarm()
agent = Agent(name="Agent", instructions="You are a helpful agent.")

messages = [{"role": "user", "content": "用一句话介绍你自己"}]

# stream=True 时，run 返回的是一个"生成器"，要用 for 去遍历它
stream = client.run(agent=agent, messages=messages, stream=True)

for chunk in stream:
    # 1) 带 content 的碎片：把新增文字实时打印出来（不换行，营造打字机效果）
    if "content" in chunk and chunk["content"] is not None:
        print(chunk["content"], end="", flush=True)

    # 2) 最后一片带 "response" 键：这才是完整结果
    if "response" in chunk:
        print()  # 收尾换行
        final = chunk["response"]
        print("=== 完整消息条数：", len(final.messages))

运行方式：把上面代码存成 stream_demo.py，确保已按第02章配置好 OPENAI_API_KEY，然后在终端执行 python stream_demo.py。

预期输出（文字会逐字浮现，非一次性打印）
我是一个乐于助人的智能助手，随时准备回答你的问题～
=== 完整消息条数： 1
看点在哪

肉眼上，第一行的文字是一个字一个字冒出来的（因为我们收到一片就打印一片）；而 === 完整消息条数 那行，要等到最后那片带 response 的碎片到达后才出现。这就完整对应了 run_and_stream 的行为：中途 yield 碎片，最后 yield 一个完整 Response。第09章会用官方封装好的 process_and_print_streaming_response 把这套逻辑做得更漂亮。

常见疑问

stream=True 和 stream=False 返回的东西一样吗？

不一样。stream=False（默认）时，run 直接返回一个 Response 对象，你拿到就能用。stream=True 时，run 转而调用 run_and_stream，返回的是一个生成器——你必须用 for 去遍历它，中途每一片是"碎片"（delta 或 delim 标记），只有最后一片带 "response" 键里才是真正的完整 Response。所以流式模式下想拿最终结果，得等遍历到那一片才行。

为什么 tool_calls 要用 index 来拼？直接顺着接不行吗？

因为一次回复里 LLM 可能同时调用多个工具，而每个工具的参数又被切成多个碎片陆续到来，且不保证顺序——可能先来 1 号工具的一片，再来 0 号工具的一片，又回到 1 号。如果只是"顺着接"，几个工具的参数就会串在一起、变成乱码。每个碎片自带的 index 就是它的"座位号"，配合 defaultdict 提供的自动开槽，无论碎片怎么乱序到达，都能被拼回属于自己的那个工具上。

merge_fields 用 += 拼接，那第一次拼的时候 target 里是什么？

是空字符串 ""。回看 run_and_stream 的消息模板：content 初始就是 ""，tool_calls 的 arguments、name 也都初始为 ""。所以第一片碎片 "" += "你" 得到 "你"，之后不断往后接。正因为模板事先把这些字段都填了空串，+= 才不会因为"键不存在"而报错。

本章小结

  • 流式让文字一个字往外蹦，体验更好；它要求 LLM 把回复切成一堆小碎片（chunk / delta）实时吐出。
  • run_and_stream 是个生成器：用 yield 中途吐碎片、用 delim 标记回复起止，最后 yield 一个完整 Response。
  • 消息模板里 tool_calls 用 defaultdict，让乱序到达的工具碎片能按 index 自动归位。
  • merge_fields 负责合并：字符串就拼接、字典就递归；merge_chunk 在其上专门处理 tool_calls 的按序号归位。

碎片能拼成完整回复了。下一章，我们把它接进一个"能一直聊下去"的交互式循环。
