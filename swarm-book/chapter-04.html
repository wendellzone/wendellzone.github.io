04

让 Agent 会用工具

只要写一个普通的 Python 函数，把它塞进 Agent，它就"会查天气"了。这一章我们拆开这个魔法，看看框架是怎么把你的函数"翻译"给 LLM 听懂的。

本章目标

  • 学会给 Agent 装工具：只要把普通函数放进 functions=[...] 就行。
  • 搞懂一个关键问题：LLM 怎么"知道"你这个函数叫什么、要什么参数、是干嘛的？
  • 逐行读懂 function_to_json——它把 Python 函数自动翻译成一份"工具说明书"（JSON Schema）。
  • 明白为什么写好类型注解和 docstring会直接决定 Agent 用得好不好。

一、给 Agent 加一把新工具

回忆第 01 章的类比：Agent 就是一个"带工具箱的员工"。所谓"加工具"，在 Swarm 里简单到让人不敢相信——写一个普通 Python 函数，塞进去就完事了。

看这个官方例子 function_calling.py，我们定义了一个查天气的函数 get_weather，然后把它放进 Agent 的 functions 列表里：

examples/basic/function_calling.py 
from swarm import Swarm, Agent

client = Swarm()


def get_weather(location) -> str:
    return "{'temp':67, 'unit':'F'}"


agent = Agent(
    name="Agent",
    instructions="You are a helpful agent.",
    functions=[get_weather],   # 把函数塞进工具箱
)
类比：给员工的工具箱加一把螺丝刀

员工（Agent）本来只会动嘴（LLM 只会生成文字）。你往他的工具箱（functions）里放一把"查天气的螺丝刀"（get_weather 函数），从此他遇到"天气"相关的活，就懂得拿这把工具去用。你不需要教他怎么用，框架会帮忙。

注意 get_weather 就是一个再普通不过的函数——它自己完全不知道"LLM""Agent"这些概念的存在。这正是 Swarm 的设计之美：你写的还是普通 Python，框架负责把它"接"到大模型上。

二、灵魂拷问：LLM 到底怎么"认识"你的函数？

这里藏着本章最关键的问题。第 01 章讲过，LLM 只会读文字、生成文字，它并不能直接"看到"你 Python 里的一个函数对象。那它凭什么知道有个叫 get_weather、需要一个 location 参数的工具可用呢？

答案是：在把请求发给 LLM 之前，框架会先把你的每个函数翻译成一段 LLM 能读懂的文字描述——一份标准格式的 JSON Schema（工具说明书）。干这件"翻译"活儿的，就是 util.py 里的 function_to_json 函数。

一句话理解

function_to_json 就是一台翻译机：左边喂进去一个 Python 函数，右边吐出来一份 JSON 格式的"工具说明书"，告诉 LLM "有这么个工具，它叫啥、要哪些参数、参数是什么类型、是干嘛用的"。

三、逐行精读：function_to_json

下面是完整源码。别怕，我们一段一段拆，每一行都讲清楚"为什么这么写"。

swarm/util.py · function_to_json 
def function_to_json(func) -> dict:
    """
    把一个 Python 函数转换成可 JSON 序列化的字典，
    描述这个函数的签名：名字、说明、参数。
    """
    # ① 类型映射表：把 Python 类型 翻译成 JSON Schema 里的类型名
    type_map = {
        str: "string",
        int: "integer",
        float: "number",
        bool: "boolean",
        list: "array",
        dict: "object",
        type(None): "null",
    }

    # ② 读取函数签名（有哪些参数、参数的类型注解、默认值）
    try:
        signature = inspect.signature(func)
    except ValueError as e:
        raise ValueError(
            f"Failed to get signature for function {func.__name__}: {str(e)}"
        )

    # ③ 遍历每个参数，生成 properties（每个参数长什么样）
    parameters = {}
    for param in signature.parameters.values():
        try:
            param_type = type_map.get(param.annotation, "string")
        except KeyError as e:
            raise KeyError(
                f"Unknown type annotation {param.annotation} for parameter {param.name}: {str(e)}"
            )
        parameters[param.name] = {"type": param_type}

    # ④ 找出"必填"参数：没有默认值的就是必填
    required = [
        param.name
        for param in signature.parameters.values()
        if param.default == inspect._empty
    ]

    # ⑤ 拼装成最终的 JSON Schema（工具说明书）
    return {
        "type": "function",
        "function": {
            "name": func.__name__,            # 函数名 → 工具名
            "description": func.__doc__ or "",  # docstring → 工具说明
            "parameters": {
                "type": "object",
                "properties": parameters,      # 参数清单
                "required": required,          # 哪些参数必填
            },
        },
    }

① 类型映射表 type_map

Python 有自己的类型（str、int……），而 LLM 认的 JSON Schema 用的是另一套名字（"string"、"integer"……）。这张表就是两种语言的对照词典：

  • str → "string"（字符串）
  • int → "integer"（整数）
  • float → "number"（小数）
  • bool → "boolean"（真/假）
  • list → "array"（列表）、dict → "object"（字典）

② 读函数签名 inspect.signature

inspect 是 Python 自带的"内省"工具箱，可以在运行时反过来观察一个函数长什么样。inspect.signature(func) 会把函数的"签名"（有几个参数、每个参数叫什么、有没有类型注解、有没有默认值）全部读出来。不这么写会怎样？——那我们就只能靠猜，根本没法自动生成说明书。

③ 遍历参数生成 properties

对每个参数，用 param.annotation（也就是你写的类型注解，比如 location: str 里的 str）去查上面的词典，得到 JSON 类型。这里有个关键细节：

没写类型注解会怎样？

看这行：type_map.get(param.annotation, "string")。.get 的第二个参数 "string" 是默认值——如果你的参数没写类型注解（词典里查不到），框架就兜底当成字符串。所以 function_calling.py 里的 get_weather(location)（没写 : str）也能正常工作，location 会被当作 string。

④ 判断哪些参数"必填" required

这一段用一句话概括：没有默认值的参数 = 必填。判断依据是 param.default == inspect._empty。

inspect._empty 是 Python 用来表示"这个参数压根没写默认值"的特殊标记。所以 def f(a, b=10) 里，a 是必填（没默认值），b 不是必填（默认值是 10）。为什么要区分？这样 LLM 才知道调用时哪些参数非给不可，不会漏填。

⑤ 拼装说明书，重点看 description

最后组装成 LLM 认识的标准结构。请特别留意这一行：

关键一行 
"description": func.__doc__ or "",  # 函数的 docstring 变成工具说明

func.__doc__ 就是你写在函数里的那段三引号 docstring。它被直接拿来当作工具的 description——也就是告诉 LLM "这个工具是干嘛用的、什么时候该用它"的唯一说明。

为什么 docstring 如此重要（务必记住）

LLM 决定"要不要调用某个工具"，几乎全靠读这段 description。如果你的函数没写 docstring，说明书里的说明就是空的，LLM 只能靠函数名瞎猜，很容易该调用时不调用、或者调错工具。所以：写工具函数，一定要写清楚 docstring！把它当成"贴在工具上的使用标签"来写。

四、图解：从 Python 函数到工具说明书

把上面这套翻译过程画成一张图，一眼就懂：

四条对应关系（背下来）

函数名 → name（工具叫什么）
docstring → description（工具是干嘛的）
参数 + 类型注解 → properties（要哪些参数、什么类型）
没有默认值的参数 → required（哪些必须填）

五、跑一个完整例子

下面是完整可运行的 function_calling.py。它会问 LLM "纽约天气怎么样"，LLM 发现自己有 get_weather 这个工具，就会"点单"要求调用它；框架执行函数、把结果喂回去，LLM 最终用人话作答。

examples/basic/function_calling.py（完整） 
from swarm import Swarm, Agent

client = Swarm()


def get_weather(location) -> str:
    return "{'temp':67, 'unit':'F'}"


agent = Agent(
    name="Agent",
    instructions="You are a helpful agent.",
    functions=[get_weather],
)

messages = [{"role": "user", "content": "What's the weather in NYC?"}]

response = client.run(agent=agent, messages=messages)
print(response.messages[-1]["content"])

运行方式（需要配置好 OPENAI_API_KEY，这一步会真正调用大模型）：

终端 
export OPENAI_API_KEY="sk-..."
python function_calling.py

预期输出（大意如下，措辞每次可能略有不同）：

终端输出
The current weather in NYC is 67°F.
（纽约现在气温 67 华氏度。）
幕后发生了什么

① 框架用 function_to_json 把 get_weather 转成说明书，连同你的问题一起发给 LLM。② LLM 读到"有个查天气工具"，回复"请调用 get_weather(location='NYC')"。③ 框架真正执行这个函数，拿到 {'temp':67, 'unit':'F'}，喂回给 LLM。④ LLM 用这份真实数据组织出最终中文/英文回答。这正是第 01 章讲的"点单 → 做菜 → 上菜"三步走。

常见疑问

如果我不写类型注解会怎样？

不会报错，框架会兜底把它当成字符串（string）。因为源码里是 type_map.get(param.annotation, "string")，查不到类型时用默认值 "string"。所以 get_weather(location) 这种没注解的写法也能跑。不过为了让 LLM 更准确地填参数（比如某个参数其实是整数），建议还是老老实实写上类型注解。

docstring 真的会影响效果吗？还是只是给人看的注释？

会，而且影响很大。docstring 被直接当作工具的 description 发给 LLM，它就是 LLM 判断"要不要用、什么时候用这个工具"的主要依据。没有 docstring，LLM 只能靠函数名猜，容易用错或漏用。把 docstring 想成"贴在工具上的使用说明标签"，写清楚它的用途和适用场景。

带默认值的参数（比如 units="F"）LLM 需要填吗？

不强制。有默认值的参数不会出现在 required 里（判断依据是 param.default == inspect._empty），所以 LLM 可以选择不填，框架就用默认值。只有没有默认值的参数才是必填。

LLM 会自己跑我的 get_weather 吗？

不会——这点第 01 章强调过。LLM 只负责"点单"（说要调用哪个函数、参数是什么），真正执行函数的永远是框架（就在 core.py 的 handle_tool_calls 里，第 07 章会细讲）。所以就算工具函数里有危险操作，也是你的程序在可控地执行，不是 LLM 偷偷替你跑。

本章小结

  • 给 Agent 加工具超简单：写个普通函数，放进 functions=[...] 即可。
  • LLM 看不懂 Python 函数对象，靠 function_to_json 把它翻译成 JSON 工具说明书。
  • 四条对应关系：函数名→name、docstring→description、参数类型→properties、无默认值的参数→required。
  • 没写类型注解会兜底当字符串；docstring 是 LLM 判断该不该用工具的关键，务必写好。

现在 Agent 会用工具了。但有些信息（比如"用户是谁"）不该让 LLM 填，又要在工具间共享——下一章的上下文变量就是解法。
