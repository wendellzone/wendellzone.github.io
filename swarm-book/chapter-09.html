交互式循环

前面每章都是"问一次答一次"。真实聊天需要连续多轮。本章用几十行代码，搭一个能在终端一直聊下去的 Agent，并读透官方开箱即用的 run_demo_loop。

本章目标

  • 理解为什么"连续对话"必须手动维护 messages 和 agent。
  • 逐行读懂最朴素的交互循环 simple_loop_no_helpers.py。
  • 读透官方封装 run_demo_loop，以及它的两个打印助手。
  • 看懂终端里那些 \033[94m 到底是什么（ANSI 颜色码）。

一、为什么需要一个"循环"

前面所有例子，本质都是"调一次 client.run(...)，拿到答案，程序结束"。可真实的聊天不是这样——你会一句接一句地问，助手要记得你们前面聊过什么。这就需要一个不停转的循环：读一句用户输入 → 问 Agent → 打印回答 → 回到开头再读下一句。

类比：值班的接线员

普通 run 像打一通"打完即挂"的电话。交互循环则像一个一直在线的接线员：接一个问题、答一个、继续等下一个，全程记着这通电话之前说了啥。而"记着说过什么"这件事，Swarm 不替你保存——得靠你自己把每轮的对话历史攒起来。这就是本章反复强调的"手动维护"。

二、最朴素的循环：simple_loop_no_helpers.py

官方 examples/basic/ 里有个极简例子，故意不用任何辅助函数（no helpers），好让你看清循环的骨架。全文只有二十几行：

examples/basic/simple_loop_no_helpers.py 
from swarm import Swarm, Agent

client = Swarm()

my_agent = Agent(
    name="Agent",
    instructions="You are a helpful agent.",
)


def pretty_print_messages(messages):
    for message in messages:
        if message["content"] is None:      # 没内容的消息（比如纯工具调用）跳过
            continue
        print(f"{message['sender']}: {message['content']}")


messages = []                               # ① 对话历史，从空开始
agent = my_agent                            # ② 当前 Agent，从起始 Agent 开始
while True:                                 # ③ 无限循环，一直聊
    user_input = input("> ")                # ④ 读一行用户输入
    messages.append({"role": "user", "content": user_input})  # ⑤ 追加到历史

    response = client.run(agent=agent, messages=messages)     # ⑥ 交给引擎跑一轮
    messages = response.messages            # ⑦ 用返回的完整历史更新 messages
    agent = response.agent                  # ⑧ 若发生交接，下轮用新 Agent
    pretty_print_messages(messages)         # ⑨ 打印
messages = [] agent = my_agent
两个"要一直带在身上"的状态：对话历史和当前 Agent。它们定义在循环外面，所以每一轮循环都能读到上一轮攒下的值——这正是"记忆"的载体。
while True:
一个永远为真的循环，程序会一直转下去（想退出就 Ctrl+C）。这就是"能一直聊"的骨架。
user_input = input("> ") messages.append({"role": "user", ...})
input 会停下来等你在终端敲字并回车。拿到这句话后，包成一条 role="user" 的消息，追加到历史末尾——注意是 append，旧消息全都保留。
response = client.run(agent=agent, messages=messages)
把"当前 Agent + 完整历史"交给引擎跑一轮（内部就是第07章那个主循环）。因为传的是完整历史，LLM 才看得到前面聊过的所有内容。
messages = response.messages
本章最关键的一行。用引擎返回的完整历史覆盖掉 messages。这一轮里 Agent 说的话、调用工具产生的消息，全都在 response.messages 里。不这么赋值回去，下一轮 LLM 就看不到自己刚说过什么——等于失忆。
agent = response.agent
同样重要：如果这一轮发生了交接（第06章），response.agent 就是接手的新 Agent。把它赋回去，下一轮就自动由新 Agent 应答——交接才能在多轮之间"延续"。
Swarm 是无状态的，记忆靠你维护

注意：client 自己不存任何对话历史。每次 run 都是一次独立、干净的调用。是你的循环把 messages 和 agent 攒在手里、一轮轮传进去，才拼出了"连续对话"的错觉。这个"无状态"设计是 Swarm 极简的关键，第10章会专门复盘。

三、官方开箱即用版：run_demo_loop

上面那个循环能用，但打印很朴素、也不支持流式。官方在 swarm/repl/repl.py 里封装了一个更好用的版本 run_demo_loop：多了流式支持和彩色美化打印。骨架和 simple_loop 几乎一样，你会发现"手动维护 messages 和 agent"的模式原封不动。

swarm/repl/repl.py · run_demo_loop 
def run_demo_loop(
    starting_agent, context_variables=None, stream=False, debug=False
) -> None:
    client = Swarm()
    print("Starting Swarm CLI 🐝")

    messages = []                           # 同样：历史从空开始
    agent = starting_agent

    while True:
        user_input = input("\033[90mUser\033[0m: ")   # 灰色提示 "User:"
        messages.append({"role": "user", "content": user_input})

        response = client.run(
            agent=agent,
            messages=messages,
            context_variables=context_variables or {},
            stream=stream,                  # 是否走第08章的流式
            debug=debug,
        )

        if stream:
            # 流式：把生成器交给流式打印器边收边显示，并拿回完整 Response
            response = process_and_print_streaming_response(response)
        else:
            # 非流式：直接把消息列表漂亮打印
            pretty_print_messages(response.messages)

        messages.extend(response.messages)  # 把本轮新增消息接到历史后面
        agent = response.agent              # 交接则更新 Agent
if stream: response = process_and_print_streaming_response(response)
流式模式下，client.run 返回的是生成器（第08章）。这里把它交给专门的流式打印器：一边遍历碎片一边实时打印，最后把完整的 Response 返回回来赋给 response，让下面的 extend/agent 逻辑照常工作。
messages.extend(response.messages)
和 simple_loop 的 messages = response.messages 效果一致——把本轮新消息并入历史。（这里用 extend 追加，因为流式返回的 messages 只含"本次新增"部分。）道理相同：不并回去就会失忆。

3.1 流式打印器 process_and_print_streaming_response

这个函数就是第08章那段"手动消费生成器"的豪华版：它按碎片的不同类型分别处理，打印得井井有条。

swarm/repl/repl.py · process_and_print_streaming_response 
def process_and_print_streaming_response(response):
    content = ""
    last_sender = ""

    for chunk in response:                  # 遍历碎片流
        if "sender" in chunk:               # 碎片带 sender → 记住是谁在说
            last_sender = chunk["sender"]

        if "content" in chunk and chunk["content"] is not None:
            if not content and last_sender: # 一段话的第一个字：先蓝色打印发言人名
                print(f"\033[94m{last_sender}:\033[0m", end=" ", flush=True)
                last_sender = ""
            print(chunk["content"], end="", flush=True)  # 逐字打印（不换行）
            content += chunk["content"]

        if "tool_calls" in chunk and chunk["tool_calls"] is not None:
            for tool_call in chunk["tool_calls"]:
                f = tool_call["function"]
                name = f["name"]
                if not name:                # 名字还没拼全的碎片先跳过
                    continue
                print(f"\033[94m{last_sender}: \033[95m{name}\033[0m()")  # 紫色显示工具名

        if "delim" in chunk and chunk["delim"] == "end" and content:
            print()                         # 收到"结束"标记 → 换行
            content = ""

        if "response" in chunk:             # 最后一片：拿到完整 Response 并返回
            return chunk["response"]
if "sender" in chunk: last_sender = chunk["sender"]
碎片里带 sender（第08章 run_and_stream 补上的）就记下"当前是谁在发言"，好在正文前面打印它的名字。
if not content and last_sender: print(f"\033[94m{last_sender}:\033[0m", ...)
当"本段还没打印过任何字"（content 为空）且知道发言人时，先把发言人名字用蓝色打出来，然后清空 last_sender 避免重复打印。之后的字就紧跟其后逐个输出。
print(chunk["content"], end="", flush=True)
逐字打印的核心：end="" 不换行、flush=True 立刻刷到屏幕（不缓冲）。这两个参数缺一不可，否则就没有"打字机"效果。
print(f"...\033[95m{name}\033[0m()")
遇到工具调用碎片，用紫色打印工具名，如 transfer_to_sales()，让你一眼看出"Agent 正在点单调工具"。name 没拼全就先 continue，等拼全再打。
if chunk["delim"] == "end" and content: print()
收到第08章那个 delim: end 结束标记，就 print() 换行、并清空 content，准备迎接下一段发言。delim 标记在这里派上了用场。
if "response" in chunk: return chunk["response"]
看到带 response 键的最后一片，就把完整 Response 返回出去——run_demo_loop 正是靠这个返回值继续维护 messages 和 agent。

3.2 非流式打印器 pretty_print_messages

如果没开流式，用的是这个。它遍历一整个消息列表，把 Agent 的发言和工具调用漂亮地打出来。

swarm/repl/repl.py · pretty_print_messages 
def pretty_print_messages(messages) -> None:
    for message in messages:
        if message["role"] != "assistant":   # 只打印助手的消息
            continue

        # 蓝色打印 Agent 名字
        print(f"\033[94m{message['sender']}\033[0m:", end=" ")

        if message["content"]:               # 有文本就打印文本
            print(message["content"])

        # 紫色打印工具调用（如果有）
        tool_calls = message.get("tool_calls") or []
        if len(tool_calls) > 1:
            print()
        for tool_call in tool_calls:
            f = tool_call["function"]
            name, args = f["name"], f["arguments"]
            arg_str = json.dumps(json.loads(args)).replace(":", "=")
            print(f"\033[95m{name}\033[0m({arg_str[1:-1]})")
if message["role"] != "assistant": continue
只打印助手说的话。用户自己的输入、工具返回结果不在这里重复展示，界面更干净。
arg_str = json.dumps(json.loads(args)).replace(":", "=")
工具参数原本是 JSON 字符串（形如 {"city": "NYC"}）。这里把冒号换成等号、再用 [1:-1] 去掉首尾大括号，打印成更像函数调用的 transfer(city="NYC") 样式，读起来更自然。
那些 \033[94m 是什么？——ANSI 颜色码

你在两个打印函数里反复看到的 \033[94m、\033[95m、\033[0m，是 ANSI 转义码。\033 是转义起始符，94m=亮蓝、95m=亮紫、0m=恢复默认。终端看到它们不会显示成文字，而是切换后续文字的颜色。所以蓝色的是 Agent 名、紫色的是工具调用——这就是终端里"彩色输出"的原理，没有任何魔法。

四、亲手跑起来

方式一：直接运行前面那段 simple_loop_no_helpers.py（python simple_loop_no_helpers.py）。方式二：用官方封装，一行就能启动带美化打印的交互：

run_repl.py 
from swarm import Agent
from swarm.repl import run_demo_loop

agent = Agent(name="Agent", instructions="You are a helpful agent.")

# 一行启动交互循环；想要打字机效果就传 stream=True
run_demo_loop(agent, stream=True)

运行方式：存成 run_repl.py，配置好 OPENAI_API_KEY（见第02章），执行 python run_repl.py。程序会停在 User: 提示符等你输入，输入一句回车，Agent 就会回答，然后又回到 User: 等下一句——如此往复。

预期输出（人机连续对话，Agent 名为蓝色、此处以文字示意）
Starting Swarm CLI 🐝
User: 你好，我叫小明
Agent: 你好小明！很高兴认识你，有什么我可以帮忙的吗？
User: 我刚才说我叫什么来着？
Agent: 你刚才说你叫小明～
User:
看点在哪

第二轮它能答出"你叫小明"，正是因为循环把上一轮的对话历史攒着又传了进去。如果你把 messages.extend(...) 那句删掉，它立刻就"失忆"、答不上来了——这就是"手动维护 messages"存在的意义。

常见疑问

为什么每轮都要把 response.messages 赋回 messages？

因为 Swarm 不替你记忆。每次 run 都只看你传进去的 messages；这一轮 Agent 新说的话、调工具产生的消息，都装在返回的 response.messages 里。如果不赋回去（或 extend 回去），下一轮传进去的历史就停留在上一轮之前，LLM 看不到自己刚说过什么，也看不到最新的工具结果——表现出来就是"失忆"、答非所问。所以这行赋值是"连续对话"的命根子。

run_demo_loop 和自己写循环有什么区别？

骨架完全一样——都是"读输入 → append → run → 更新 messages 和 agent"。区别在于 run_demo_loop 帮你封装好了两件麻烦事：①流式支持（传 stream=True 就有打字机效果，内部自动消费生成器）；②彩色美化打印（蓝色 Agent 名、紫色工具调用）。想快速体验就用它；想完全掌控每个细节、或嵌进自己的应用里，就照着 simple_loop 自己写。

交互循环里发生交接（handoff），下一轮真的会换 Agent 吗？

会。关键就在 agent = response.agent 这一行。当某一轮里工具返回了一个新 Agent（第06章的交接），引擎会把 response.agent 设为接手的那个 Agent。循环把它赋回 agent 变量后，下一轮的 client.run(agent=agent, ...) 用的就是新 Agent 了。所以交接的"延续"，同样是靠循环手动维护 agent 实现的。

本章小结

  • 连续对话 = 一个 while True 循环：读输入 → 追加历史 → run → 更新 messages 和 agent → 打印。
  • Swarm 无状态，记忆靠你手动把 messages 攒着回传；不回传就会失忆。
  • agent = response.agent 让交接能在多轮之间延续。
  • 官方 run_demo_loop 是开箱即用版，多了流式支持和彩色打印；终端里的 \033[94m 只是 ANSI 颜色码。
