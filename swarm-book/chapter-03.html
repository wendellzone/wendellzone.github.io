数据模型骨架

上一章我们用到了 Agent 和 Response，却没看清它们内部长什么样。这一章翻开 types.py——整个框架就靠这三个"数据类"撑起骨架。

本章目标

  • 读懂 types.py 里的三个核心数据类：Agent、Response、Result。
  • 搞清 Agent 的每个字段是干嘛的，尤其是 instructions 为什么能"既是字符串又是函数"。
  • 理解 Response（一次办公的交接单）和 Result（工具结果的三合一信封）分别在什么时候出现。
  • 知道 AgentFunction 这个"类型别名"是什么意思。

一、先认识一下 pydantic：会自检的档案表

types.py 里的三个类，都继承自一个叫 BaseModel 的东西，它来自第三方库 pydantic。你暂时只需要理解它的作用：

类比：会自检的入职表格

普通的 Python 类像一张空白纸，你随便往上写什么它都不管。而 pydantic 的 BaseModel 像一张印好格子、会自动校验的表格：每个格子规定了"必须填什么类型"（比如名字必须是文字、工具必须是一串函数），还能预设默认值。填错类型它会当场报错。这让数据结构既清晰又可靠。

所以，接下来看到的每个 class ... (BaseModel)，你都可以想成是在定义一张表格的格式：有哪些格子、每格填什么、默认填什么。

二、开篇一行：AgentFunction 类型别名

文件顶部（去掉 import）第一句实质代码是这个：

types.py · 类型别名 
AgentFunction = Callable[[], Union[str, "Agent", dict]]

这行不创建任何对象，它只是给一个"类型"起个好记的外号（术语叫类型别名）。我们从右往左拆：

  • Callable[[], ...]：Callable 意思是"可调用的东西"，通俗说就是一个函数。方括号里的 [] 表示它的参数，这里先简化成"无参数"。
  • Union[str, "Agent", dict]：Union 表示"以下几种任选其一"。也就是说，这个函数的返回值可以是三种之一：一段文字（str）、一个 Agent、或一个字典（dict）。

合起来，AgentFunction 就是给"一个 Agent 能调用的工具函数"起的外号，它的规格是：可以被调用，返回文字、或一个新 Agent、或一个字典。为什么允许返回这三种？这正好对应后面三种玩法——返回文字是普通工具（第 04 章）、返回 Agent 会触发交接（第 06 章）、返回字典可用于更新上下文（第 05 章）。这里先埋个伏笔，混个眼熟即可。

"别名"有什么用？

就是少打字、更易读。有了 AgentFunction 这个外号，后面定义 Agent 的工具箱时，就能直接写 functions: List[AgentFunction]，而不用把那一长串 Callable[[], Union[...]] 重复抄一遍。

三、Agent：一张"员工档案卡"

这是全书最重要的数据类。它把第 01 章那个"带工具箱的员工"正式落成了代码：

types.py · class Agent 
class Agent(BaseModel):
    name: str = "Agent"                                # 员工名字，默认叫 "Agent"
    model: str = "gpt-4o"                              # 用哪个大脑（模型），默认 gpt-4o
    instructions: Union[str, Callable[[], str]] = "You are a helpful agent."  # 岗位说明书
    functions: List[AgentFunction] = []               # 工具箱：一串可调用的工具函数，默认空
    tool_choice: str = None                           # 是否/如何强制调用工具，默认不强制
    parallel_tool_calls: bool = True                  # 允许一次并行调用多个工具，默认允许
类比：一张员工档案卡

整个 Agent 就像人事部为一名员工填的档案卡：姓名、能力评级（用哪个大脑）、岗位说明书、会用的工具清单……每一栏都有默认值，所以你只填想改的那几栏就行——这正是第 02 章我们只写了 name 和 instructions 却依然能跑的原因。

逐栏来看：

  • name（默认 "Agent"）：员工的名字。在多 Agent 协作、看日志时用来区分是谁。
  • model（默认 "gpt-4o"）：给这个 Agent 当"大脑"的模型。想省钱可改成 "gpt-4o-mini" 之类。
  • instructions：岗位说明书，也就是 system prompt。类型很特别，下面单独讲。
  • functions（默认空列表 []）：工具箱，装着这个 Agent 能调用的工具函数（每个都符合上面 AgentFunction 的规格）。第 02 章这里是空的，所以那个 Agent 只会说话。第 04 章我们就往里塞工具。
  • tool_choice（默认 None）：控制"要不要/强制调用某个工具"。默认 None 表示交给大脑自己决定何时用工具。
  • parallel_tool_calls（默认 True）：允不允许大脑一次点好几个工具并行执行（比如同时查天气和查汇率）。默认允许，能提速。

重点：instructions 为什么能"既是字符串，又是函数"？

注意 instructions 那一栏的类型：Union[str, Callable[[], str]]。翻译过来就是——它可以是一段固定文字（str），也可以是一个"能返回文字的函数"（Callable[[], str]）。为什么要给个说明书留这么大的灵活度？

固定说明书 vs. 活的说明书

如果说明书永远不变（"你是一个乐于助人的助手"），写成字符串就够了。但很多时候，说明书需要随情况变化：比如"你正在服务 VIP 客户张三，他的会员等级是黄金"——名字和等级是运行时才知道的。这时就把 instructions 写成一个函数：调用时临时读取当前信息，动态"打印"出一份定制说明书。

类比：印死的告示牌 vs. 电子屏

字符串版的说明书像一块刻死的告示牌，内容永远一样；函数版的说明书像一块电子屏，每次显示前都能根据实时数据（客户是谁、现在几点）刷新内容。这种"活的说明书"依赖的实时数据，就是第 05 章的主角——上下文变量（context variables）。这里先记住：instructions 可以是函数，就是为上下文变量埋的伏笔。

四、Response：一次办公的"完整交接单"

还记得第 02 章 client.run(...) 返回的那个 response 吗？它就是这个类的实例：

types.py · class Response 
class Response(BaseModel):
    messages: List = []                    # 本轮结束后，完整的对话历史
    agent: Optional[Agent] = None          # 当前接手的 Agent（可能已被交接换人）
    context_variables: dict = {}           # 最新的上下文变量
类比：一次办公的交接单

把一次 run() 想成"让员工办一趟事"。事办完，他递给你一张交接单，上面写清三件事：①这趟对话都聊了些什么（messages）、②现在归谁负责（agent，如果中途转接过就是新员工）、③过程中记下的上下文（context_variables）。你拿着这张交接单，就能无缝发起下一轮。

  • messages：本轮跑完后完整的对话历史——不只是你最初递进去的，还追加了大脑的新回复、以及中间的工具调用记录。第 02 章我们取 response.messages[-1]，取的就是这里最后一条。
  • agent（类型 Optional[Agent]，即"可能是 Agent，也可能是 None"）：本轮结束时当前接手的 Agent。单 Agent 时它就是你传进去的那个；发生交接（第 06 章）后，它会变成被转接到的新 Agent。
  • context_variables：跑完后最新的上下文变量（第 05 章详讲）。

五、Result：工具执行结果的"三合一信封"

最后一个类，是给工具函数的返回值用的。当一个 Agent 的工具跑完，它可以把结果包装成一个 Result 交回引擎：

types.py · class Result 
class Result(BaseModel):
    """
    Encapsulates the possible return values for an agent function.

    Attributes:
        value (str): The result value as a string.
        agent (Agent): The agent instance, if applicable.
        context_variables (dict): A dictionary of context variables.
    """

    value: str = ""                    # 工具产出的文本结果
    agent: Optional[Agent] = None      # 可选：夹带一个新 Agent，用来触发交接
    context_variables: dict = {}       # 可选：要写回/更新的上下文变量

类里那段带三引号的文字是文档字符串（docstring），是作者留给读代码的人的说明，程序不会执行它。它已经把三个字段讲清楚了。

类比：一个三合一信封

Result 就像工具办完事后寄回的一个信封，里面最多能塞三样东西，而且每样都可选：

  • 一张便签（value）：文字结果，比如"查到纽约 67°F"。—— 这是最常见的用法（第 04 章）。
  • 一张调令（agent）：夹带一个新 Agent，等于对引擎说"这事该转给他了"，触发交接。（第 06 章）
  • 一张备忘（context_variables）：要更新的上下文信息，比如"记下客户已升级为黄金会员"。（第 05 章）
一个信封，三种玩法

正因为 Result 能同时携带这三样，Swarm 才能用同一套机制优雅地支持三件看似不同的事：普通返回结果、切换负责人、更新共享状态。你现在只需记住这个"三合一信封"的存在，具体怎么用，第 04、05、06 章会各自登场。

常见疑问

Response 和 Result 长得很像，都有 agent 和 context_variables，怎么区分？

看谁产出、给谁用：Response 是 run() 对外的最终产物——整趟事办完交给你的交接单；Result 是单个工具函数对内的返回——工具跑完交给引擎的信封，引擎消化后可能据此更新对话、换 Agent 或改上下文。一个是"对外的总结果"，一个是"对内的零件"。

为什么 instructions 要费劲允许"字符串或函数"两种类型？

为了同时照顾"固定"和"动态"两种需求。绝大多数场景说明书是固定的，写字符串最省事；但当说明书需要随运行时数据变化（如带上当前用户名、时间、会员等级）时，就必须写成函数，在每次调用时临时生成。这个函数版说明书正是第 05 章"上下文变量"要驱动的东西——本章先埋伏笔。

这些字段的默认值（如 model="gpt-4o"、functions=[]）是谁定的？

就是 types.py 里 = ... 那部分定的。得益于 pydantic 的 BaseModel，你在创建 Agent(name="X") 时只填想改的字段，其余的自动套用这些默认值。这就是第 02 章我们只写两个字段却能正常运行的底层原因。

AgentFunction 只是个"别名"，不写它行不行？

技术上，你可以把它那一长串 Callable[[], Union[str, "Agent", dict]] 直接抄到 functions 字段的类型里，效果一样。但那样又长又难读、还得抄好几处。起个 AgentFunction 的别名，纯粹是为了可读性和少重复——一看名字就知道"这是一个 Agent 工具函数的规格"。

本章小结

  • types.py 用 pydantic 的 BaseModel 定义了三张"会自检的表格"，撑起整个框架的数据骨架。
  • Agent（员工档案卡）：name / model / instructions / functions / tool_choice / parallel_tool_calls，每个字段都有默认值。
  • instructions 能是字符串或函数——函数形态为第 05 章"上下文变量"埋下伏笔。
  • Response（交接单）：run() 的对外产物，含 messages / agent / context_variables。
  • Result（三合一信封）：工具函数对内的返回，value / agent / context_variables 分别对应第 04（返回文本）、06（触发交接）、05（更新上下文）章。

骨架已经看清。下一章，我们给空空的工具箱塞进第一件真本领——让 Agent 会用工具。
