04

handoff 的极简哲学

多 Agent 系统里最核心的动作是"交接"——把对话从一个 Agent 转给另一个。你以为这需要一套专门的路由 API？Swarm 的答案让人拍案：让一个普通工具函数 return 一个 Agent 就行了。没有新概念，没有新 API。这一章我们看它是怎么用三小段代码做到的。

本章目标

  • 看懂交接机制的三步链路：工具返回 Agent → 打包进 Result → 换掉 active_agent。
  • 理解"返回 Agent 即交接"这一极简设计的洞察与代价。
  • 看清交接后历史是连续的，以及那条 role=tool 消息里到底写了什么。
  • 能对照"显式路由表"方案，判断两种思路各自适合什么场景。

前置回顾

入门版里你已经跑过"英语 Agent 遇到西语用户就转给西语 Agent"的例子，也见过 response.agent 会变成新的 Agent。当时这看起来像框架内置的某种"转移功能"。这一章要揭穿的真相是：Swarm 里根本没有一个叫 handoff 的东西。交接不是一个特性，而是"工具返回值恰好是个 Agent"时的自然结果。上一章结尾埋的那个钩子——工具返回的不是字符串会怎样——现在揭晓。

一、第一步：工具返回 Agent，被包成 Result

回忆第 03 章：工具的返回值会交给 handle_function_result 处理。看它怎么对待"返回值是个 Agent"的情况（core.py 第 71–87 行）：

swarm/core.py · handle_function_result 
    def handle_function_result(self, result, debug) -> Result:
        match result:
            case Result() as result:
                return result

            case Agent() as agent:                      # 第76行：返回值是个 Agent！
                return Result(
                    value=json.dumps({"assistant": agent.name}),  # 第78行
                    agent=agent,                        # 第79行：把这个 Agent 记进 Result
                )
            case _:
                try:
                    return Result(value=str(result))    # 普通返回值：转成字符串
                except Exception as e:
                    ...

这个 match 分三种情况：返回值本身是 Result 就直接用；是普通值（字符串、数字等）就 str() 一下装进 Result.value；而第 76 行——如果返回值是一个 Agent 实例，就构造一个特殊的 Result：把这个 Agent 放进 Result.agent（第 79 行），同时给 value 填一句 {"assistant": "<新agent名>"}（第 78 行）当作这次工具调用的"结果文本"。

关键洞察就在这里：Swarm 把"我要交接"这件事，编码成了"工具返回一个 Agent"。Result 这个结构（types.py 第 29–41 行）里恰好有个 agent 字段，就是为承接它准备的。

二、第二步：把 Result 里的 Agent 冒泡上来

handle_tool_calls 拿到每个工具的 Result 后（core.py 第 124–135 行）：

swarm/core.py · handle_tool_calls（节选） 
            result: Result = self.handle_function_result(raw_result, debug)
            partial_response.messages.append(
                {
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "tool_name": name,
                    "content": result.value,          # 就是那句 {"assistant": "..."}
                }
            )
            partial_response.context_variables.update(result.context_variables)
            if result.agent:                          # 第134行：这个 Result 带 Agent 吗？
                partial_response.agent = result.agent # 第135行：带！记到 partial_response

第 134–135 行：如果这个 Result 里有 agent（说明刚才那个工具返回了 Agent），就把它记到本批工具调用的汇总结果 partial_response.agent 上。同时注意，那条 role=tool 的消息照常被追加进历史——它的 content 正是第 78 行那句 {"assistant": "<新agent名>"}。

三、第三步：主循环换掉当前 Agent

回到 run() 主循环末尾（core.py 第 283–286 行）：

swarm/core.py · run 主循环换 Agent 
            history.extend(partial_response.messages)
            context_variables.update(partial_response.context_variables)
            if partial_response.agent:                # 第285行
                active_agent = partial_response.agent # 第286行：下一轮就用新 Agent 了

第 285–286 行：如果本批工具调用产生了新 Agent，就把 active_agent 换成它。于是下一轮循环调用 get_chat_completion 时，用的就是新 Agent 的 instructions 和工具集了。交接完成——全程只改了一个变量。

类比：接力赛递交接力棒

交接不需要裁判喊停、重开一局。前一棒选手（英语 Agent）跑到交接区，把接力棒（active_agent 这个变量）往后一递——递棒的动作本身，就是"return 一个 Agent"。赛道（history）是同一条、连续的，观众看到的还是同一场比赛，只是从下一段起换了个人在跑。没有人清空跑道、没有人重置比分。

四、极简 vs 显式：交接设计的取舍

返回 Agent 即交接 vs 显式路由表
Swarm：返回 Agent 即交接
  • 零新概念：不用学任何 handoff API，会写工具函数就会写交接。
  • 任意工具都能触发：一个查订单的工具，也可以在查完后顺手 return 另一个 Agent。
  • 关系是运行时动态的：转给谁可以由代码逻辑、甚至数据现算，极其灵活。
显式路由表 / 状态机
  • 有集中的全景视图：所有 A→B→C 的转移一张表看尽，便于可视化。
  • 可静态校验：能提前检查"有没有转移到不存在的节点""会不会成环"。
  • 但更重、更死板：加一条新路径要改路由表，动态路由难表达。

Swarm 用"返回 Agent"把交接降维成了"函数返回值"这个每个程序员都懂的概念，代价是你无法一眼看全"谁能转给谁"——转移逻辑散落在各个工具函数里。对教学和小规模编排，这份灵活与极简很值；到了需要审计、可视化全部流转路径的大型生产系统，显式路由的"笨重"反而成了优点。

陷阱：以为交接会"清空历史、重开对话"

交接后，那个触发交接的工具会在历史里留下一条 role=tool 消息，它的 content 是 {"assistant": "<新agent名>"}（来自第 78 行），而不是什么用户可读的回复。更重要的是：历史是连续的、不会被清空——新 Agent 接手时，看到的是包含之前所有对话的完整 history，只是从这一刻起换成它来说话。别误以为交接像"转接电话时对方听不到之前的通话"，恰恰相反，新 Agent 全程"在场"，能看到之前的上下文。

可运行片段：英语转西语

这就是 examples/basic/agent_handoff.py 的全部——注意交接就藏在那个再普通不过的 transfer_to_spanish_agent 里（真跑需要 API Key）：

examples/basic/agent_handoff.py 
from swarm import Swarm, Agent

client = Swarm()

english_agent = Agent(name="English Agent", instructions="You only speak English.")
spanish_agent = Agent(name="Spanish Agent", instructions="You only speak Spanish.")

def transfer_to_spanish_agent():
    """Transfer spanish speaking users immediately."""
    return spanish_agent          # ← 交接的全部秘密：return 一个 Agent

english_agent.functions.append(transfer_to_spanish_agent)

messages = [{"role": "user", "content": "Hola. ¿Como estás?"}]
response = client.run(agent=english_agent, messages=messages)

print(response.messages[-1]["content"])   # 最后一句由 spanish_agent 说出
预期输出（西语，措辞每次略有不同）
¡Hola! Estoy bien, gracias. ¿Y tú cómo estás?

发生了什么：english_agent 看到西语输入，决定调用 transfer_to_spanish_agent；这个工具 return spanish_agent，被打包成 Result(agent=spanish_agent)，主循环把 active_agent 换成西语 Agent；下一轮循环里，西语 Agent 面对同一段历史，用西语回复。整个过程用户只提了一句话，交接在幕后一气呵成。

铺垫：双向交接与分诊

把交接反过来用，就能做出"分诊台"：一个 triage Agent 根据用户意图把对话分派给销售/退款/技术等专职 Agent，各专职 Agent 又能通过一个 transfer_back_to_triage() 把控制权交还分诊台。这正是 examples/triage_agent 的思路，也是第 07 章"分诊编排实战"要大展身手的地方。你会发现，再复杂的编排，底层也还是这一个"返回 Agent"的动作在反复发生。

延伸：其他框架的 handoff 长什么样？

OpenAI Agents SDK（Swarm 的生产级后继）在理念上和 Swarm 一脉相承——它同样把 handoff 建模成"一种特殊的 tool"：你在 Agent 上声明 handoffs=[agent_b, agent_c]，SDK 会自动为每个目标生成一个对应的转移工具暴露给 LLM。区别是 SDK 把这层做得更正式（有专门的 handoff 类型、可加输入过滤、可带结构化数据），但"交接=调用一个工具"的内核没变。理解了 Swarm 的极简版，你就抓住了 SDK handoff 的精髓。

LangGraph 走的是另一条路：它把多 Agent 编排显式建模成一张图，节点是 Agent、边是转移规则，你先把图画出来（声明 edges），运行时按图游走。这就是图 4-1 右边那种"显式路由表/状态机"的典型代表——全景清晰、可校验，但要先付出建图的成本。两条路没有对错，只是把"灵活"和"可控"这对矛盾放在了天平的不同位置。

常见疑问

一批工具调用里如果有两个都返回了 Agent，听谁的？

看第 134–135 行：partial_response.agent 会被逐个覆盖，所以最后一个返回 Agent 的工具"胜出"。实践中很少让多个工具同时触发交接，但知道这个规则能帮你理解边界行为。工具是串行 for 循环执行的（这一点第 05 章细讲），所以"最后一个"是确定的、可预测的。

交接后，新 Agent 的工具集和 instructions 什么时候生效？

下一轮循环。active_agent 在本轮末尾（第 286 行）被换掉后，要等 while 进入下一圈、再次调用 get_chat_completion（第 260 行）时，才会用新 Agent 的 instructions 和 functions 去请求 LLM。所以交接不是"立刻由新 Agent 补一句"，而是"从下一次模型调用起换人"。

本章小结

  • Swarm 没有专门的交接 API——交接就是"让一个普通工具函数 return 一个 Agent"。
  • 三步链路：handle_function_result 把返回的 Agent 包成 Result(agent=...)（第 76–80 行）→ handle_tool_calls 冒泡到 partial_response.agent（第 134–135 行）→ 主循环换掉 active_agent（第 285–286 行）。
  • 交接后历史连续、不清空；触发交接的 role=tool 消息 content 是 {"assistant": "<新agent名>"}。
  • 极简换来零概念、任意工具可触发、运行时动态；代价是没有集中的路由全景，不便静态分析。

我们已经把 run() 主循环里"换 Agent"这条支线看透了。但主循环还有一堆防御性的边界细节没讲：它凭什么不会死循环？工具名写错了会崩吗？"并行工具调用"到底并不并行？下一章逐一拆解主循环的健壮性护栏。
