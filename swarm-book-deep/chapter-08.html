08

给 Agent 接真实数据库

上一章 airline 里的工具都是桩函数——initiate_refund 只 return "Refund initiated"，什么也没真的做。可现实中的客服机器人要能查订单、下单、真退款。这一章我们看 personal_shopper：它的工具函数会实打实地读写一个 SQLite 数据库。你会看到，当 LLM 生成的参数直接进 SQL 时，安全是绕不开的头等大事。

本章目标

  • 看懂 personal_shopper 的三个工具函数（refund_item / order_item / notify_customer）如何真正读写 SQLite。
  • 掌握参数化查询——为什么 LLM 的输出是"不可信输入"，绝不能拿去拼 SQL 字符串。
  • 理解 database.py 里的三个工程手法：连接单例、幂等建表 / 幂等写入、显式事务提交。
  • 想清楚一个架构问题：状态该放在 数据库里，还是像第 03 章那样放在 context_variables 里？

前置回顾

入门版里你已经知道：Swarm 的"工具"就是普通 Python 函数，Agent 的 functions 列表列出它能调用的工具；LLM 决定调哪个、传什么参数，引擎负责真正执行并把返回值喂回去。之前所有示例的工具都很"干净"——要么返回字符串，要么返回另一个 Agent（handoff）。这一章的关键变化只有一个：工具函数里出现了副作用，而且是最典型的一种——数据库读写。一旦工具能改动外部世界的真实状态，我们对它的要求就完全不同了：正确、安全、可重试。

类比：给员工一把能开数据库的钥匙

之前的 Agent 像一个只会"演习"的新员工——你让他"办理退款"，他答一句"退款已办好"，但保险柜根本没打开。现在你要给他一把真能打开数据库保险柜的钥匙。这当然更有用，但也更危险：他填错单号会动到别人的账户，甚至他照着话术念的一句话都可能被当成开锁指令（这就是 SQL 注入）。所以给钥匙的同时，必须配一套严格的领用规范——这正是本章的重点。

一、三个会"真的动手"的工具

personal_shopper 有两个业务 Agent：销售（sales_agent）和退款（refunds_agent），外加一个分诊台（triage_agent）路由到它们。真正干活的是三个工具函数，它们都在 main.py 里，每一个都会打开数据库连接、执行 SQL。先看退款（main.py 第 10–29 行）：

examples/personal_shopper/main.py · 第 10–29 行 
def refund_item(user_id, item_id):
    """Initiate a refund based on the user ID and item ID.
    Takes as input arguments in the format '{"user_id":"1","item_id":"3"}'
    """
    conn = database.get_connection()
    cursor = conn.cursor()
    cursor.execute(
        """
        SELECT amount FROM PurchaseHistory
        WHERE user_id = ? AND item_id = ?
    """,
        (user_id, item_id),
    )
    result = cursor.fetchone()
    if result:
        amount = result[0]
        print(f"Refunding ${amount} to user ID {user_id} for item ID {item_id}.")
    else:
        print(f"No purchase found for user ID {user_id} and item ID {item_id}.")
    print("Refund initiated")

逐行拆开看，这就是一段教科书式的"安全数据库读取"：

  • 第 14–15 行：database.get_connection() 拿到连接，conn.cursor() 开游标。注意工具函数自己不负责建连接，只向 database 模块要——连接的生命周期被收拢到一处管理（第二节详解）。
  • 第 16–22 行：一条 SELECT amount FROM PurchaseHistory WHERE user_id = ? AND item_id = ?。划重点：SQL 语句里用的是 ? 占位符，真实值 (user_id, item_id) 作为第二个参数（元组）单独传给 execute。这就是"参数化查询"，本章的安全核心，第四节专门讲。
  • 第 23 行：fetchone() 取一行结果（只需要一条），比 fetchall() 更贴合"精确查一笔购买记录"的语义。
  • 第 24–28 行：if result: 分支——查到了就报出金额，没查到就提示"没有这笔购买"。先验证购买记录存在，再谈退款，这是一个朴素但重要的业务校验：不能凭空给一个不存在的订单退款。

再看下单（main.py 第 58–82 行），它比退款多一步——不仅要读，还要写：

examples/personal_shopper/main.py · 第 58–82 行 
def order_item(user_id, product_id):
    """Place an order for a product based on the user ID and product ID.
    Takes as input arguments in the format '{"user_id":"1","product_id":"2"}'"""
    date_of_purchase = datetime.datetime.now()
    item_id = random.randint(1, 300)

    conn = database.get_connection()
    cursor = conn.cursor()
    cursor.execute(
        """
        SELECT product_id, product_name, price FROM Products
        WHERE product_id = ?
    """,
        (product_id,),
    )
    result = cursor.fetchone()
    if result:
        product_id, product_name, price = result
        print(
            f"Ordering product {product_name} for user ID {user_id}. The price is {price}."
        )
        # Add the purchase to the database
        database.add_purchase(user_id, date_of_purchase, item_id, price)
    else:
        print(f"Product {product_id} not found.")
  • 第 61–62 行：下单前先在代码里生成两样东西——下单时间 date_of_purchase 和商品实例编号 item_id = random.randint(1, 300)。这两个值不由 LLM 决定，而是程序自己生成的。这是一个好习惯：像时间戳、流水号这类"事实数据"，交给代码而不是让模型编。
  • 第 66–72 行：同样是参数化的 SELECT ... FROM Products WHERE product_id = ?——先查商品是否存在、拿到真实价格。价格来自数据库，而不是听信用户或 LLM 报的数。
  • 第 74–80 行：查到商品后，用数据库里的真实 price，调 database.add_purchase(...) 把这笔购买写入 PurchaseHistory 表。注意写库逻辑被封装在 database 模块里，工具函数只管"编排业务"，不直接写 INSERT（这个分工第二节会展开）。
  • 第 81–82 行：商品不存在就报错，不会写入任何东西。

第三个工具 notify_customer（第 32–55 行）是一次纯读取带分支：SELECT email, phone FROM Users WHERE user_id = ? 取出联系方式，再按 method（"email" 或 "phone"）选一种通知方式，缺对应字段就提示不可用。三个工具放在一起，正好覆盖了数据库的三种典型操作：只读查询（refund 的验证、notify）、读后写（order）、带条件的读取分支（notify）。

二、database.py：连接、建表、写入的工程手法

三个工具都靠 database.py 提供的底层能力。这个模块虽小，却藏着三个很实用的工程习惯。

2.1 连接单例：一个进程只开一条连接

examples/personal_shopper/database.py · 第 3–11 行 
# global connection
conn = None


def get_connection():
    global conn
    if conn is None:
        conn = sqlite3.connect("application.db")
    return conn

conn 是一个模块级全局变量，初始为 None。第一次调用 get_connection() 时才真正 sqlite3.connect(...)（延迟初始化），之后每次调用都复用同一条连接。这就是经典的单例模式：整个进程共用一条数据库连接。

为什么这样够用？因为 run_demo_loop 是单线程、同步的——一次只处理一个用户的一轮对话，工具函数串行执行，不存在并发争用。省掉了连接池的复杂度，也避免了每次工具调用都重新建连接的开销。

2.2 幂等建表：CREATE TABLE IF NOT EXISTS

examples/personal_shopper/database.py · 第 14–58 行（摘录） 
def create_database():
    conn = get_connection()
    cursor = conn.cursor()

    cursor.execute(
        """
        CREATE TABLE IF NOT EXISTS Users (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            user_id INTEGER,
            first_name TEXT,
            last_name TEXT,
            email TEXT UNIQUE,
            phone TEXT
        )
    """
    )

    cursor.execute(
        """
        CREATE TABLE IF NOT EXISTS PurchaseHistory (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            user_id INTEGER,
            date_of_purchase TEXT,
            item_id INTEGER,
            amount REAL,
            FOREIGN KEY (user_id) REFERENCES Users(user_id)
        )
    """
    )
    # ... Products 表同理 ...
    conn.commit()

关键是 IF NOT EXISTS：无论运行多少次，表存在就跳过、不存在才建，绝不报"表已存在"的错。这让 initialize_database() 可以每次启动都无脑调一遍而不出问题——这叫幂等（同一操作执行一次和执行多次结果相同）。另外注意 PurchaseHistory 上有 FOREIGN KEY (user_id) REFERENCES Users(user_id)，在数据库层面声明了"购买必须属于某个用户"的关系。

2.3 幂等写入 + 显式事务

order_item 调用的 add_purchase（第 84–111 行）把"幂等"贯彻到了写入上：

examples/personal_shopper/database.py · 第 84–111 行 
def add_purchase(user_id, date_of_purchase, item_id, amount):
    conn = get_connection()
    cursor = conn.cursor()

    # Check if the purchase already exists
    cursor.execute(
        """
        SELECT * FROM PurchaseHistory
        WHERE user_id = ? AND item_id = ? AND date_of_purchase = ?
    """,
        (user_id, item_id, date_of_purchase),
    )
    if cursor.fetchone():
        return

    try:
        cursor.execute(
            """
            INSERT INTO PurchaseHistory (user_id, date_of_purchase, item_id, amount)
            VALUES (?, ?, ?, ?)
        """,
            (user_id, date_of_purchase, item_id, amount),
        )

        conn.commit()
    except sqlite3.Error as e:
        print(f"Database Error: {e}")
  • 第 89–98 行（先查后写）：写入前先 SELECT 检查"这笔购买是否已存在"（同一 user + item + 时间），存在就直接 return，不重复插入。这就是幂等写。
  • 第 100–107 行：真正的 INSERT，依旧是 ? 占位 + 参数元组。
  • 第 109 行（显式 commit）：conn.commit()。SQLite（以及大多数数据库驱动）默认开启事务，不 commit 的写入不会真正落盘。这行是"确认下单"那一下——漏了它，程序看起来跑通了，重启后数据却没了。
  • 第 110–111 行（错误兜底）：try/except sqlite3.Error 捕获数据库异常，打印而不是让整个 Agent 循环崩掉。工具函数出错时应该优雅降级，把问题变成一条可控的消息，而不是抛出未捕获异常炸穿主循环（呼应第 05 章讲的健壮性边界）。
为什么"幂等"对 Agent 尤其重要

LLM 驱动的系统天生带重试色彩：模型可能因为没看清返回值而再调一次同一个工具，网络抖动也可能触发重发。如果 add_purchase 不做去重，用户一句"下单"就可能被记两笔账。幂等写让"多调几次"变得安全——这是把工具接上真实副作用后，必须补上的一课。

三、Agent 编排：分诊 + 双向回流

三个工具挂在两个业务 Agent 上，再由分诊台路由（main.py 第 95–126 行）：

examples/personal_shopper/main.py · 第 95–126 行（摘录） 
refunds_agent = Agent(
    name="Refunds Agent",
    description="""...必须一次问齐 user_id 和 item_id 才能发起退款...""",
    functions=[refund_item, notify_customer],
)

sales_agent = Agent(
    name="Sales Agent",
    description="""...下单必须同时有 user ID 和 product ID，缺一不可...""",
    functions=[order_item, notify_customer],
)

triage_agent = create_triage_agent(
    name="Triage Agent",
    instructions="""...判断用户是要下单还是退款，转给对应 Agent...""",
    agents=[sales_agent, refunds_agent],
    add_backlinks=True,          # ← 自动给每个下游 Agent 装一个转回分诊的工具
)

这里出现了一个上一章没见过的便捷写法：create_triage_agent(...) 是 Swarm 内置的辅助工厂（swarm.agents），它帮你把 agents=[...] 里的每个 Agent 自动生成对应的转移函数挂到分诊台上。关键是 add_backlinks=True——它会给每个下游 Agent 反向装一个"转回分诊"的工具，效果和上一章手写的 transfer_to_triage 一样，是双向 handoff 的"自动挡"版本。main.py 第 128–129 行的 for f in triage_agent.functions: print(f.__name__) 就是把自动生成的这些转移函数名打印出来，方便你确认路由确实接好了。

横向对比：状态放数据库 vs 放 context_variables

第 03 章讲过 Swarm 的"档案袋" context_variables：一个随对话流转的字典，用来携带跨轮次的上下文（比如客户资料）。上一章 airline 就把客户和航班信息放在里面。可 personal_shopper 完全没用 context_variables——它把状态全放进了数据库。为什么？

  • 放 context_variables（进程内、随会话）：适合本次对话的临时上下文——当前客户是谁、正在处理哪张航班。轻量、无需外部依赖，但会话一结束就没了，也不能被别的进程/别的会话看到。
  • 放数据库（进程外、持久化）：适合需要长期留存、跨会话共享的业务事实——用户账户、历史订单、商品价格。personal_shopper 的"购买历史"显然属于这类：这次买的东西，下次退款时还得查得到。

所以两者不是二选一，而是按数据的寿命和作用域分工：会话级、临时的放档案袋；业务级、要持久的放数据库。真实系统里常常两者并用——用 context_variables 存"当前登录用户 ID"，再拿它去数据库查这个用户的订单。

四、安全红线：参数化查询防 SQL 注入

现在讲本章最重要的一件事。回看每一条 SQL，值都是通过 ? 占位符 + 参数元组传进去的，从没有把变量拼进 SQL 字符串。这不是风格问题，是安全红线。

陷阱：绝不要用 f-string 拼 SQL —— LLM 的输出是不可信输入

假设你图省事，把 refund_item 写成这样：

# ❌ 千万不要这样写
cursor.execute(
    f"SELECT amount FROM PurchaseHistory WHERE user_id = {user_id} AND item_id = {item_id}"
)

这里的 user_id / item_id 是 LLM 根据用户对话生成的参数。而用户能操纵 LLM 说什么。如果用户诱导模型把 item_id 填成 3 OR 1=1，甚至 3; DROP TABLE PurchaseHistory; --，拼出来的 SQL 就变成了一条攻击语句——轻则返回全表数据（WHERE ... OR 1=1 恒真），重则删表。这就是SQL 注入。

正确做法就是本章一直在用的参数化查询：SQL 里写 ?，值单独作为元组传给 execute。数据库驱动会把这些值当作纯数据处理，无论内容是什么都不会被解释成 SQL 语法——3 OR 1=1 会被老老实实当成一个字符串去匹配 item_id，匹配不到，安全返回空。

为什么在 Agent 场景下格外要命：传统 Web 应用里，注入源是"用户表单"，你还能在前端做点校验；而在 Agent 里，SQL 的参数直接来自大模型的自由生成，中间隔着一个你无法完全约束的黑盒。把 LLM 的一切输出都当成最高级别的不可信输入，是接数据库时的第一心法。

五、把它跑起来

运行前提

只需要 OpenAI API Key（export OPENAI_API_KEY=...）。SQLite 是 Python 标准库内置的（import sqlite3），无需安装或启动任何外部数据库服务——数据就落在当前目录的一个文件 application.db 里。这也是本章选它做示例的原因：真实的读写副作用，零外部依赖。cd examples/personal_shopper && python3 main.py 即可。不想真跑也行，顺着下面的逻辑读就能理解。

启动时，main.py 第 86 行先调 database.initialize_database()：它幂等建表，并预置了 3 个用户、3 条购买历史、3 件商品（database.py 第 154–188 行）。比如用户 1（Alice）有一笔 item_id=101、金额 99.99 的购买；商品表里有 product_id=7（Hat, 19.99）等。有了这些种子数据，就能立刻演示退款和下单。第 89–91 行还会 preview_table 打印每张表的前几行，方便你确认数据就位。最后第 133 行把分诊台丢进 run_demo_loop：

examples/personal_shopper/main.py · 第 85–133 行（骨架） 
# Initialize the database
database.initialize_database()          # 幂等建表 + 预置种子数据

# Preview tables
database.preview_table("Users")
database.preview_table("PurchaseHistory")
database.preview_table("Products")

# ... 定义 refunds_agent / sales_agent / triage_agent ...

if __name__ == "__main__":
    run_demo_loop(triage_agent, debug=False)

下面是一段推演的交互（示意，LLM 实际措辞会不同；这里重点看"分诊 → 工具执行 → 数据库副作用"的路径）：

预期交互（推演 · 一次退款）
用户: 我要退货退款。
[Triage Agent] → 转移到 Refunds Agent            # 分诊判断这是退款类
[Refunds Agent] 请提供您的 user ID 和要退款的 item ID。   # description 要求一次问齐
用户: user_id 是 1，item_id 是 101。
[Refunds Agent] → 调用 refund_item(user_id=1, item_id=101)
Refunding $99.99 to user ID 1 for item ID 101.   # SELECT 查到了那笔购买（种子数据）
Refund initiated
[Refunds Agent] 已为您发起 101 号商品 99.99 的退款。
预期交互（推演 · 一次下单，含写库）
用户: 我想买东西。

注意"下单"这条：价格 19.99 是从 Products 表查出来的真实值，不是用户或 LLM 说了算；写入还经过了幂等去重和显式 commit。这就是"工具接上真实数据库"后，一次调用背后真正发生的事。

六、工具直连数据库，值不值

工具直连 DB（personal_shopper 的做法）vs 经 service / ORM 层
工具函数里直接写 SQL
  • 简单直接：一个函数从头到尾看得清，适合示例、原型、小工具。
  • 没有额外的抽象层，心智负担低，改起来快。
  • 只要坚持参数化查询，安全底线也守得住。
经 service / ORM 数据访问层
  • 权限与校验集中：可在一处统一做"这个用户能不能退这笔款"的鉴权，工具不必各写各的。
  • 更易测试：业务逻辑与 SQL 解耦，可替换成内存实现做单测。
  • 可复用、可演进：换数据库、加缓存、加审计日志都只动这一层。
  • 代价是更重、更多样板代码，小项目里可能过度设计。

结论：personal_shopper 作为示例，直连是合理的——它想让你一眼看清"工具怎么读写库"。但一旦进真实生产，随着权限、校验、审计、可测性的要求上来，把数据访问收拢到一个独立的 service/ORM 层几乎是必然的。无论走哪条路，参数化查询这条安全红线永远不能退让。

常见疑问

为什么全局用一条连接就够了？真实并发场景也这样吗？

够用是因为 run_demo_loop 是单线程同步的——同一时刻只有一次工具调用在跑，不会有两条线程同时抢连接。真实的 Web 服务通常是多请求并发的，那时单条连接会成为瓶颈甚至出错，需要换成连接池（每个请求借一条、用完还回）。SQLite 本身也不擅长高并发写；生产环境多会换 PostgreSQL / MySQL。这里的单例是"单进程演示"下的合理简化。

如果 LLM 把 user_id 填成了一段恶意 SQL，会怎样？

因为用了参数化查询，什么也不会发生——那段"恶意 SQL"会被数据库当成一个普通字符串值去和 user_id 列做匹配，匹配不到就返回空。这正是参数化的价值：它在数据和代码之间划了一道硬边界，值永远只是值，绝不会被解释成 SQL 语法。反之若用 f-string 拼接，那段字符串就会被当成 SQL 执行——这就是注入。

漏写 conn.commit() 会有什么现象？

程序当场看起来一切正常，INSERT 也没报错，但数据只停留在未提交的事务里。一旦进程退出或连接关闭而没 commit，这些写入会被回滚丢弃——重启后你会发现"明明下过单，历史里却查不到"。这类 bug 极隐蔽，因为它不报错。凡是有写操作（INSERT/UPDATE/DELETE），记得配一次显式 commit。

为什么 item_id 和下单时间由代码生成，而不让 LLM 填？

因为它们是系统事实，不是用户意图。下单时间应当是"服务器此刻的真实时间"，流水号应当由系统保证唯一——这些都不该交给可能产生幻觉的模型。让 LLM 只负责它擅长的部分（理解用户想买什么），把确定性的事实数据留给代码，是接工具时划分职责的一条通用原则。

本章小结

  • personal_shopper 的三个工具（refund_item / order_item / notify_customer）会真正读写 SQLite，覆盖只读查询、读后写、条件分支三种典型操作。
  • 参数化查询是安全红线：SQL 里用 ? 占位、值单独作元组传入。把 LLM 的输出当最高级别的不可信输入，绝不用 f-string 拼 SQL，否则 SQL 注入门户大开。
  • database.py 的三个工程手法：连接单例（单进程复用一条连接）、幂等建表 / 幂等写入（适配 Agent 的重试特性）、显式 commit（写入必须提交才落盘）。
  • 本例不用 context_variables，状态全放数据库——会话级临时上下文放档案袋，业务级持久事实放数据库，按数据寿命分工。
  • 工具直连 DB 简单直接，适合示例；生产中因权限、校验、可测性需求，通常会引入 service/ORM 层——但参数化查询永远不退让。
