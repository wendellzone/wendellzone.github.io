10

怎么给 Agent 做评测

改完一版 prompt，Agent 到底变好了还是变坏了？靠"手动聊两句感觉一下"是不行的。这一章看 triage_agent 和 weather_agent 的 evals：如何用一个隐藏参数 execute_tools=False，把 Agent 的"决策"变成可以写断言、可以自动跑的考卷。

本章目标

  • 理解为什么 Agent 需要自动化评测，而不是靠手感。
  • 掌握核心机制 execute_tools=False：只取 LLM 的意图，不真正执行工具。
  • 学会两类断言：结构化断言（查调了哪个函数）与 LLM 裁判（判对话是否成功）。
  • 看清两类断言各自的适用场景与代价。

前置回顾

入门版讲过 run() 的 tool_calls：LLM 想调用工具时，会先返回一条带 tool_calls 的消息（"我想调 transfer_to_refunds"），框架再去真正执行。第 05 章我们特意留过一个伏笔——run() 有个参数 execute_tools（core.py 第 275 行 if not message.tool_calls or not execute_tools: break）。这一章，这个伏笔终于要收了：评测的全部魔法，就藏在把它设成 False 上。

一、为什么 Agent 难评测

类比：给 Agent 出模拟考卷

传统函数好测：输入 2，输出必须是 4，一测一个准。可 Agent 背后是 LLM，同一句话每次回答的措辞都不同——你没法断言"输出必须一字不差等于某句话"。
于是我们换个思路：不考"它答得一字不差吗"，而考"面对'我要退款'，它有没有做出正确的决策——去调那个转接到退款专员的工具？"。这就像考试不看你作文用词，只看你有没有选对答案（ABCD）。决策是可枚举、可断言的。

二、核心机制：execute_tools=False 只取意图

要考"决策对不对"，我们只需要拿到 LLM 想调哪个工具，而不需要真的去执行它（真执行会退真钱、发真邮件，产生副作用）。triage_agent/evals.py 把这一步封装成一个小助手：

examples/triage_agent/evals.py · run_and_get_tool_calls 
def run_and_get_tool_calls(agent, query):
    message = {"role": "user", "content": query}
    response = client.run(
        agent=agent,
        messages=[message],
        execute_tools=False,   # ← 关键：只让 LLM 决定调哪个工具，但不真执行
    )
    return response.messages[-1].get("tool_calls")

逐行看它妙在哪：

  • messages=[message]：只喂一句待测的用户输入，不带任何历史，保证测的是"这句话触发的即时决策"。
  • execute_tools=False：回到 core.py 第 275 行，run() 一旦拿到 LLM 的回复就 break，不进入执行工具那一步。所以没有任何真实副作用，快且安全。
  • response.messages[-1].get("tool_calls")：取最后一条（即 LLM 那条）消息里的 tool_calls。这就是 LLM 的"答题卡"——它想调哪些工具、参数是什么。
这正是"无状态 + 可重放"的红利

还记得第 01 章说的吗？Swarm 无状态、给定输入就能复现行为。execute_tools=False 能成立，正是因为 run() 不留副作用、可被反复安全调用——评测体系是建立在那条设计哲学之上的。

三、结构化断言：查"调对了哪个函数"

拿到答题卡后，断言就非常直接了。triage_agent/evals.py 用 pytest 的参数化把多个"题目→标准答案"一次性跑完：

examples/triage_agent/evals.py · 结构化断言 
import pytest

@pytest.mark.parametrize(
    "query,function_name",
    [
        ("I want to make a refund!", "transfer_to_refunds"),
        ("I want to talk to sales.", "transfer_to_sales"),
    ],
)
def test_triage_agent_calls_correct_function(query, function_name):
    tool_calls = run_and_get_tool_calls(triage_agent, query)

    assert len(tool_calls) == 1                                  # 恰好点了 1 个工具
    assert tool_calls[0]["function"]["name"] == function_name   # 而且点对了那一个

@pytest.mark.parametrize 会把列表里每一组 (query, function_name) 各跑一次，等价于写了好几个测试。两条断言分别卡住：

  • len(tool_calls) == 1——分诊 Agent 应该干脆地转接，不能一次点两个、也不能不点。
  • tool_calls[0]["function"]["name"] == function_name——"我要退款"必须触发 transfer_to_refunds，转错专员就是 bug。

正反两面都要考：weather_agent 的双向测试

weather_agent/evals.py 更进一步，不仅测"该调工具时调了没"，还测"不该调工具时有没有克制住"：

examples/weather_agent/evals.py · 正向 + 反向 
# 正向：这些问法都应该触发 get_weather
@pytest.mark.parametrize(
    "query",
    [
        "What's the weather in NYC?",
        "Tell me the weather in London.",
        "Do I need an umbrella today? I'm in chicago.",
    ],
)
def test_calls_weather_when_asked(query):
    tool_calls = run_and_get_tool_calls(weather_agent, query)
    assert len(tool_calls) == 1
    assert tool_calls[0]["function"]["name"] == "get_weather"


# 反向：这些问题不该调用任何工具，LLM 直接答即可
@pytest.mark.parametrize(
    "query",
    [
        "Who's the president of the United States?",
        "What is the time right now?",
        "Hi!",
    ],
)
def test_does_not_call_weather_when_not_asked(query):
    tool_calls = run_and_get_tool_calls(weather_agent, query)
    assert not tool_calls   # 期望 None 或空列表

反向测试常被忽略，却很关键：一个"见问题就乱调工具"的 Agent，和一个"该调不调"的 Agent，一样是坏的。assert not tool_calls 就是在守住"该沉住气时沉住气"。

陷阱：LLM 有随机性，单次通过 ≠ 稳定

这类测试跑一次绿了，不代表它永远绿——同一句话，LLM 偶尔也会抽风调错。所以评测要多用例覆盖（参数化正是为此），关键场景甚至要多次采样看通过率，而不是把它当成传统单元测试那样"绿一次就一劳永逸"。

四、LLM 当裁判：判"整段对话成没成功"

结构化断言只能查"可编程判定"的东西（调了哪个函数）。但有些问题没法用代码断言，比如"这整段对话，Agent 到底有没有把用户的事办成？"——这需要"读懂对话"的能力。于是 Swarm 的示例请出另一个 LLM 来当裁判。

看 evals_util.py，它用 instructor 库让 GPT-4o 输出结构化的判定结果（而不是一段自由文本）：

examples/triage_agent/evals_util.py · LLM 裁判 
import instructor
from openai import OpenAI
from pydantic import BaseModel

__client = instructor.from_openai(OpenAI())   # 用 instructor 包一层 OpenAI

class BoolEvalResult(BaseModel):   # 约定裁判必须返回这个结构
    value: bool                    # 判定：成功 or 失败
    reason: Optional[str]          # 附带理由（便于排查）

def evaluate_with_llm_bool(instruction, data) -> BoolEvalResult:
    eval_result, _ = __client.chat.completions.create_with_completion(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": instruction},   # 评分标准
            {"role": "user", "content": data},             # 待评的数据（对话）
        ],
        response_model=BoolEvalResult,   # ← 强制 LLM 的输出符合这个 Pydantic 模型
    )
    return eval_result

关键是 response_model=BoolEvalResult：instructor 会保证 GPT-4o 返回的东西刚好能装进 BoolEvalResult——一个布尔值 + 理由。这样裁判的意见就变成了程序能直接 if 判断的 result.value，而不是一段还要人去解读的话。

有了这个裁判，就能评"对话是否达成目标"了：

examples/triage_agent/evals.py · 对话级评测 
CONVERSATIONAL_EVAL_SYSTEM_PROMPT = """
You will be provided with a conversation between a user and an agent, as well
as a main goal for the conversation. Your goal is to evaluate, based on the
conversation, if the agent achieves the main goal or not...
"""

def conversation_was_successful(messages) -> bool:
    conversation = f"CONVERSATION: {json.dumps(messages)}"   # 把整段对话序列化
    result: BoolEvalResult = evaluate_with_llm_bool(
        CONVERSATIONAL_EVAL_SYSTEM_PROMPT, conversation
    )
    return result.value   # 裁判说成功了吗？


@pytest.mark.parametrize(
    "messages",
    [
        [
            {"role": "user", "content": "Hello!"},
            {"role": "assistant", "content": "Hi there! How can I assist you today?"},
            {"role": "user", "content": "I want to make a refund."},
            {"role": "tool", "tool_name": "transfer_to_refunds"},
            {"role": "user", "content": "Thank you!"},
            {"role": "assistant", "content": "You're welcome! Have a great day!"},
        ],
    ],
)
def test_conversation_is_successful(messages):
    assert conversation_was_successful(messages) == True

把整段对话（JSON）连同评分标准一起交给 GPT-4o，它读完给出 True/False。这就完成了"结构化断言够不着"的语义级评测。

五、两类断言：分工与取舍

结构化断言 vs LLM 裁判
结构化断言（查函数名/数量）
  • 快、确定、免费：纯代码判定，不调模型。
  • 结果稳定可复现，适合放进 CI 天天跑。
  • 局限：只能判"可编程"的事——调了哪个工具、几个、参数对不对；判不了"回答得好不好"。
LLM 裁判（判语义/对话质量）
  • 能判"整段对话是否达成目标"这类语义问题。
  • 代价：慢、花钱（每次评测都要调一次 GPT-4o）。
  • 裁判本身也是 LLM，可能不稳——评分标准要写清楚，必要时多跑几次取共识。

实战里两者配合用：能用结构化断言卡死的（"必须转接到退款"），就用便宜确定的结构化断言；只有语义质量这类卡不死的，才动用 LLM 裁判。

常见疑问

execute_tools=False 会不会漏测"工具执行后"的问题？

会。它只测"LLM 这一步的决策意图"，不测"工具真跑起来、结果喂回后 LLM 会怎么继续"。所以它适合评"路由/决策是否正确"这类单步问题；要评多轮执行后的最终效果，得让 execute_tools 保持默认的 True、跑完整对话，再用 LLM 裁判去判整段结果（正是本章第四节做的事）。两者互补。

为什么要用 instructor，直接读 GPT-4o 的文字回答不行吗？

能读，但麻烦且脆弱。让 LLM 自由回一段话，你还得写正则/解析去判断它到底说"通过"还是"不通过"，措辞一变就可能解析错。instructor 用 Pydantic 模型（BoolEvalResult）强制它输出一个规整的 {value, reason}，你的代码直接 result.value 就行，稳得多。这其实和第 04 章 function_to_json 让 LLM 输出结构化工具调用是同一种思路——给 LLM 的输出套上 schema。

这套评测能直接用在生产吗？

它是很好的起点，但生产还需要更多：更大的用例集、对随机性做多次采样统计通过率、对成本/延迟设预算、把评测接进 CI 自动跑，等等。第 12 章会把"系统化评测"列进通往生产的路线图。

本章小结

  • Agent 输出不确定，评测的思路是考决策（调对工具了吗）而非考措辞。
  • 核心机制 execute_tools=False：只取 LLM 的 tool_calls 意图，不产生真实副作用——这依赖 Swarm 无状态、可重放的设计。
  • 结构化断言（len==1、name==期望，含正/反向）快而确定；LLM 裁判（instructor + GPT-4o + BoolEvalResult）能判语义但慢且花钱，二者配合用。
  • 有了评测，改 prompt/换模型就有了客观护栏，而不是靠手感。

实战篇到此结束——你已见过分诊编排、真实数据库、RAG、评测四种真实能力。第三部分，我们动手改造 Swarm，甚至从零把它写一遍。
