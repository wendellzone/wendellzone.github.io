深拷贝与副作用边界

上一章我们说清了"状态归调用者持有"。可引擎在算一轮的过程中，要不停地往历史里塞消息、往档案袋里写数据。它凭什么保证不弄脏你传进去的原始数据？答案藏在 run() 开头那三行毫不起眼的代码里。

本章目标

  • 看懂 run() 开头的 copy.deepcopy 与 init_len 到底在防什么。
  • 理解"副作用泄漏"是怎么发生的，以及深拷贝如何在入口处筑起一道隔离墙。
  • 搞清 init_len 的记账作用：为什么返回的是 history[init_len:] 而不是整个 history。
  • 掂量深拷贝的代价，并知道浅拷贝为什么在这里不够用。

前置回顾

入门版里你已经习惯了那个"手动赋回"的循环：messages = response.messages。上一章我们确认了引擎无状态——它不替你记历史。这就引出一个很自然的担忧：既然 messages 是你的原始 list，而引擎在一轮里要反复 append/extend，那它会不会直接在你的 list 上乱涂乱画？如果会，你就再也没法拿同一份干净的 messages 去做别的事了。Swarm 的答案是：不会——因为它进门第一件事就是"复印"。

一、进门先复印：run() 的头三行

先看 run() 非流式分支的开头（core.py 第 252–255 行）：

swarm/core.py · run 的开场三行 
        active_agent = agent
        context_variables = copy.deepcopy(context_variables)   # 第253行
        history = copy.deepcopy(messages)                       # 第254行
        init_len = len(messages)                                # 第255行

逐行拆开看：

  • 第 253 行：把调用者传进来的 context_variables 深拷贝一份，之后引擎读写的都是这份副本。你原来的 dict 一根汗毛都不会动。
  • 第 254 行：把 messages 深拷贝成 history。注意名字变了——从这行起，引擎内部只认 history，再也不碰你的 messages。后面所有的 history.append(...)、history.extend(...) 落的都是副本。
  • 第 255 行：init_len 记下"起跑线"——你原来的历史有多长。这个数字后面要用来切出"本轮新增"的部分。

流式分支 run_and_stream 里是一模一样的三行（core.py 第 150–152 行），可见这不是随手一写，而是刻意在两个入口都守住的边界。

类比：在复印件上批注，不弄脏原件

你把一份合同（messages）交给助理去处理。聪明的助理不会拿起红笔直接在你的原件上圈圈画画——他会先去复印一份，所有批注、补页都写在复印件上，最后只把"新增的那几页"还给你。你的原件始终干干净净，想再复印几份给别人处理都行。

copy.deepcopy 就是那台复印机，history 就是复印件，而 init_len 记住了"原件到第几页为止"，好让助理最后只抽出新增页交回。

二、不复印会怎样：副作用泄漏

假设我们把第 254 行删掉，直接让引擎在你的 messages 上操作。看看会发生什么：

假想：如果不深拷贝（错误示范） 
my_messages = [{"role": "user", "content": "你好"}]

# 如果 run() 内部是 history = messages（同一个对象，不复印）
# 那么引擎每次 history.append(...) 都等于在 my_messages 上 append

client.run(agent=agent, messages=my_messages)

# 我原本只想留一句干净的用户输入，结果……
print(len(my_messages))   # 不再是 1，而是被塞进了 assistant 回复、tool 消息等一堆东西

这就是副作用泄漏：函数偷偷改了调用者的输入对象。危害不止"变长"这么简单——如果你本来想拿这份 my_messages 作为一个"干净的起点"，分别跑三个不同的 Agent 做对比，一旦第一次 run 就把它污染了，后两次的起点就全变了。深拷贝把这种隐患从根上掐断：引擎的一切改动都发生在隔离墙内，墙外的原始数据永远是你交出去时的样子。

陷阱：以为 run() 会"就地帮你累积历史"

正因为有深拷贝，run() 绝不会把新消息写回你传进去的那个 list。有人写完 client.run(agent=agent, messages=messages) 后，直接接着用 messages，以为里面已经有了 Agent 的回复——结果 messages 还是老样子，Agent 说了什么一句都没进去。要拿到本轮结果，唯一的办法是用返回值：messages = response.messages（或 messages.extend(response.messages)）。这正好呼应第 01 章"状态归调用者维护"——深拷贝是这条原则在实现层的兑现。

三、init_len：只把"新增的"还给你

引擎在副本 history 上忙活完，结尾要打包 Response（core.py 第 288–292 行）：

swarm/core.py · 只返回本轮新增 
        return Response(
            messages=history[init_len:],          # 从起跑线之后切出来 —— 只有本轮新产生的
            agent=active_agent,
            context_variables=context_variables,
        )

关键就是 history[init_len:] 这个切片。history 里此刻装着"你原来的历史 + 本轮新增的消息"，而 init_len 正好是原来历史的长度。切片 [init_len:] 跳过了前面那段旧的，只把本轮真正新产生的消息交回给你。

为什么这么设计？因为如果返回整个 history，那你原来传进去的历史会被原样再返回一遍。你若写 messages = response.messages 或许没事，但你若写 messages.extend(response.messages)（很常见的累积写法），旧历史就会被重复追加一次——越滚越长、内容重复。返回"仅增量"让两种写法都安全，也让调用方对"这一轮到底新增了什么"一目了然。

四、这道边界值不值：深拷贝的取舍

入口深拷贝 vs 直接原地修改
Swarm：进门深拷贝
  • 零副作用：无论引擎内部怎么折腾，调用者的原始 messages/context_variables 永不被改。
  • 可复用同一份输入：拿同一份干净的 messages 连跑多个 Agent、多次 run 做对比，互不干扰——评测（第10章）就靠这个。
  • 行为可预测：调用方不必背"这个函数会不会偷改我的参数"这种心智负担。
  • 与第01章的无状态一脉相承：状态进出干净利落。
直接在传入对象上原地改
  • 省内存、省一次拷贝，历史很长时更快。
  • 但会污染调用者数据：你的原始 list 被塞满，再想复用就得自己先备份。
  • 难以"拿同一起点跑多次"——第一次跑完起点就变了。
  • 隐式副作用是 bug 温床，调用方稍不留神就中招。

代价确实存在：历史特别长时，每轮 run 都全量深拷贝一次会有内存和时间开销。但对 Swarm 的教学与轻量定位而言，"绝不坑调用者"的确定性远比这点开销重要。真要优化，也可以在调用层控制单次传入的历史长度，而不是让引擎去冒污染数据的风险。

可读片段：亲眼看它没改你的原件

下面这段不需要联网也能理解其逻辑（真跑需要 API Key）。重点看两次 len(messages) 的对比：

deepcopy_demo.py 
from swarm import Swarm, Agent

client = Swarm()
agent = Agent(name="Agent", instructions="You are a helpful agent.")

messages = [{"role": "user", "content": "讲个冷笑话"}]
print("run 之前，messages 长度：", len(messages))

response = client.run(agent=agent, messages=messages)

print("run 之后，原始 messages 长度：", len(messages))      # 仍然是 1，没被改
print("response.messages 长度：", len(response.messages))    # 本轮新增（至少 1 条 assistant 回复）
print("原始 messages 内容原封不动：", messages[0]["content"])
预期输出（回复文字每次不同）
run 之前，messages 长度： 1
run 之后，原始 messages 长度： 1
response.messages 长度： 1
原始 messages 内容原封不动： 讲个冷笑话

"run 之后原始 messages 长度还是 1"——这就是深拷贝在起作用：引擎往副本里塞了回复，却没动你的原件。要累积历史，你得自己 messages = response.messages 或 messages += response.messages。

延伸：为什么是深拷贝，浅拷贝为什么不够？

浅拷贝（list(messages) 或 copy.copy）只复制最外层的容器：新 list 是新的，但里面的每个元素（每条消息 dict）还是原来那些对象的引用。这意味着：history.append(新消息) 确实不会影响原 list 的长度（外层是独立的），但如果引擎去修改某条已有消息内部的字段（比如往一条消息 dict 里写个键），那改动会顺着共享引用泄漏回你的原始 messages 里的那条 dict。context_variables 更明显——它常是嵌套 dict，浅拷贝下内层 dict 仍被共享，引擎一 update 嵌套结构就漏出去了。

deepcopy 则递归复制到底，连最里层的 dict/list 都是全新对象，彻底断开一切共享引用。这也是"隔离墙"能真正隔离的前提。

顺带一提：这种"进门先拿一份不可变/独立的快照，改动只作用于快照，最后交回新状态"的思路，和很多生产框架里的不可变状态（immutable state）/ State 快照设计是同一种精神——把"谁能改什么、改动波及范围"约束得清清楚楚。Swarm 用一行 deepcopy 就把这个理念落了地。

常见疑问

每轮都深拷贝整个历史，长对话不会很慢吗？

会有开销，但通常不是瓶颈——真正的耗时大头在网络往返和 LLM 推理，深拷贝一个消息 list 的成本相比之下微乎其微。而且深拷贝只在每次 run() 入口发生一次，不是每条消息都拷。如果你的历史确实巨大（几千条），更好的做法是在调用层做"历史裁剪/摘要"再传入，而不是让引擎放弃隔离保护。

context_variables 也被深拷贝了，那我的更新怎么拿回来？

靠返回值。引擎在副本上 update，最后通过 Response.context_variables 把更新后的副本交还给你。你的原始 dict 没变，但 response.context_variables 里是最新的。想留住就 context_variables = response.context_variables。这和 messages 的处理是同一套逻辑——进来复印、出去交回。第 03 章会讲这个"档案袋"是怎么被注入到工具和 instructions 里的。

本章小结

  • run() 一进门就 copy.deepcopy 了 context_variables 和 messages（第 253–254 行），流式分支同样如此（第 150–151 行）——引擎只在副本上工作。
  • 这道深拷贝隔离墙杜绝了副作用泄漏：你的原始数据永远保持干净、可复用。
  • init_len（第 255 行）记住起跑线，结尾 history[init_len:] 只返回本轮新增，避免旧历史被重复交回。
  • 代价是长历史时的拷贝开销，但换来"绝不坑调用者"的确定性，对教学与轻量框架很划算。
