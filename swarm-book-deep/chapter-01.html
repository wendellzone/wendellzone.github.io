第一章 · Chapter 01
01

无状态设计

Swarm 的引擎自己什么都不记得。这个看似偷懒的决定，其实是它最重要的设计哲学。这一章我们搞清楚：状态到底放在哪、谁来维护、为什么这样最好。

本章目标

  • 理解"有状态 vs 无状态"到底在说什么。
  • 看清 Swarm 把状态全部外置到 messages 和 context_variables 的设计。
  • 从源码确认 Swarm 引擎实例上不存任何对话状态。
  • 明白这带来的好处（可并发、可重放、易测试）与代价（调用者要自己维护状态）。

前置回顾

入门版里你写过这样的交互循环（simple_loop_no_helpers.py 的核心）：每轮把用户输入塞进 messages，调用 client.run()，再手动把返回的 response.messages 赋回给 messages、把 response.agent 赋回给 agent。当时你可能觉得"这一步有点啰嗦"。这一章会告诉你：这份"啰嗦"正是 Swarm 无状态设计的体现，而且它是故意的。

一、什么是"有状态"与"无状态"

用一个生活类比就懂：

类比：会记账的老店 vs 凭小票的快餐店

有状态像一家会记账的老店：你是熟客，老板脑子里记着"你上次点了什么、还欠多少钱"。方便，但老板一换人、店一打烊，记忆就可能丢失或对不上。
无状态像快餐店：店员什么都不记，你的一切都印在手里那张小票上。谁来服务你都行，换个窗口也能接着办——因为状态不在店员脑子里，而在你手上的小票里。

Swarm 选择了后者：引擎（店员）不记任何东西，全部状态都在你手上的"小票"——也就是 messages 和 context_variables 里。

二、从源码确认：引擎上没有对话状态

先看 Swarm 类的构造函数（core.py 第 26–30 行）：

swarm/core.py · Swarm.__init__ 
class Swarm:
    def __init__(self, client=None):
        if not client:
            client = OpenAI()
        self.client = client

看清楚：整个 Swarm 实例上只存了一个 self.client（OpenAI 网络客户端）。没有 self.messages、没有 self.history、没有 self.current_agent——它不保存任何一次对话的内容。

再看 run() 的签名（core.py 第 231–241 行）——所有它需要知道的东西，都是调用时通过参数传进去的：

swarm/core.py · run 的签名 
def run(
    self,
    agent: Agent,              # 这一轮用哪个 Agent —— 调用者传进来
    messages: List,            # 到目前为止的完整对话 —— 调用者传进来
    context_variables: dict = {},  # 随身档案袋 —— 调用者传进来
    model_override: str = None,
    stream: bool = False,
    debug: bool = False,
    max_turns: int = float("inf"),
    execute_tools: bool = True,
) -> Response:

agent、messages、context_variables 三样"状态"全靠参数传入。run() 用完就"忘"，下次你还得再传一遍。这就是无状态的本质：引擎不持有状态，状态在参数里进、在返回值里出。

三、状态怎么"进出"引擎

run() 结尾把结果打包成 Response 交还给你（core.py 第 288–292 行）：

swarm/core.py · run 的返回 
    return Response(
        messages=history[init_len:],   # 这一轮新产生的消息
        agent=active_agent,            # 最终"当前 Agent"（可能因交接换了）
        context_variables=context_variables,  # 更新后的档案袋
    )

于是就形成一个清晰的循环：你把状态传进去 → 引擎算一轮 → 把更新后的状态还给你 → 你保存好，下一轮再传进去。引擎全程不留底。

四、这就是为什么循环里要"手动赋回"

回到前置回顾里那段"啰嗦"的代码。现在你明白了：因为引擎不记账，所以记账的责任落在你身上。

examples/basic/simple_loop_no_helpers.py（节选） 
messages = []
agent = my_agent
while True:
    user_input = input("> ")
    messages.append({"role": "user", "content": user_input})

    response = client.run(agent=agent, messages=messages)
    messages = response.messages   # ← 把"小票"更新好，否则下轮就失忆
    agent = response.agent         # ← 记住可能已经交接过的当前 Agent
    pretty_print_messages(messages)
陷阱：忘了赋回 = Agent 集体失忆

如果你写成 client.run(agent=agent, messages=messages) 却不把返回的 response.messages 赋回 messages，那么下一轮传进去的还是旧历史——LLM 完全不知道刚才聊过什么，每轮都像第一次见面。这是新手最常见的坑，根源就在于"状态归调用者维护"。

五、无状态换来了什么，又要付出什么

无状态引擎 vs 有状态引擎
Swarm：无状态
  • 可并发：同一个 client 能同时服务成千上万个互不干扰的对话（各自的 messages 分开存）。
  • 可重放/可测试：给定同样的入参就能复现同样的行为，评测（第10章）正是靠这一点。
  • 易横向扩展：引擎实例可随意增减、放到任意机器上，因为它不持有会话。
  • 实现极简，核心才几百行。
有状态引擎（把历史存在引擎里）
  • 调用方省事：不用自己维护 messages。
  • 但并发困难：多个对话共用一个实例会串味，得为每个会话建实例或加锁。
  • 难测试/难重放：行为依赖引擎内部的隐藏状态。
  • 扩展到多机时要处理"会话粘性"、状态同步等一堆麻烦。

一句话：Swarm 把"维护状态"这点小麻烦推给了调用者，换来了并发、可测试、可扩展这些大好处。对一个定位教学、也想被认真使用的框架来说，这笔交易很划算。

延伸：这和其他框架比怎么样？

很多框架也走无状态路线，只是叫法不同。比如 OpenAI Agents SDK 用 Runner.run(agent, input) 返回结果，会话历史同样由调用方通过 result.to_input_list() 拼接后带入下一轮——思路和 Swarm 的"赋回 messages"如出一辙。LangGraph 则把状态显式建模成一个可持久化的 State 对象 + checkpointer，属于"把状态外置得更正式"的版本。

可见"引擎无状态、状态外置"几乎是现代 Agent 框架的共识。Swarm 只是把这个共识用最少的代码呈现了出来：状态就是两个普通变量 messages 和 context_variables，没有任何额外包装。

可运行小实验：证明引擎真的"不记事"

下面这段代码故意不把历史赋回，你会看到 Agent 每轮都失忆（需要 API Key 才能真跑；不跑也能从逻辑上理解）：

stateless_demo.py 
from swarm import Swarm, Agent

client = Swarm()
agent = Agent(name="Agent", instructions="You are a helpful agent.")

# 第一轮：告诉它我的名字
r1 = client.run(agent=agent, messages=[{"role": "user", "content": "我叫小明，记住哦。"}])
print("第一轮:", r1.messages[-1]["content"])

# 第二轮：故意只传一句新话，不带上第一轮的历史
r2 = client.run(agent=agent, messages=[{"role": "user", "content": "我叫什么名字？"}])
print("第二轮:", r2.messages[-1]["content"])   # 它答不上来——因为引擎没记，我们也没传
预期输出（措辞每次略有不同）
第一轮: 好的，小明，我记住了！
第二轮: 抱歉，我不知道你的名字，你还没有告诉我呢。

把第二轮改成把 r1.messages 拼在前面再传，它立刻就"想起来"了。这就直观证明了：记忆不在引擎里，在你传的 messages 里。

常见疑问

那 context_variables 算不算引擎的状态？

不算。它同样是调用者持有、通过参数传入、随 Response 传出的。引擎在一次 run 内部会用它、更新它，但 run 一结束，引擎就不再持有它——想留住得靠你把 response.context_variables 存下来。第 03 章会专门讲它的注入机制。

无状态是不是意味着 Swarm 不能做"长期记忆"？

恰恰相反，它把"长期记忆"这件事解放出来了。因为状态是普通的 messages/context_variables，你可以自由地把它们存进数据库、Redis、文件——想存多久存多久、想存哪存哪。引擎不插手，反而给了你最大的自由。第 08 章的数据库示例就是这种思路的延伸。

本章小结

  • Swarm 实例上只有一个 self.client，不保存任何对话状态——它是无状态的。
  • 状态（agent / messages / context_variables）由调用者持有，在 run() 的入参与返回值之间往返。
  • 所以交互循环里必须手动把 response.messages/agent 赋回，否则 Agent 会失忆。
  • 这换来了可并发、可重放、可测试、易扩展，代价只是调用者多维护一点状态——很划算。
