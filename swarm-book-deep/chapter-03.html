03

约定优于配置

上一章那个被小心复印的 context_variables，是怎么"魔法般"出现在你的 instructions 里、又悄悄溜进工具函数、还偏偏对 LLM 隐身的？Swarm 没用任何装饰器、没让你注册任何东西——它只靠一个参数名的约定。这就是"约定优于配置"。

本章目标

  • 看懂 context_variables 注入的三处魔法：动态 instructions、按参数名注入、对 LLM 隐藏。
  • 理解"约定优于配置"这一设计理念如何让代码近乎零配置。
  • 掌握它的边界：为什么参数名必须叫 context_variables，拼错会静默失效。
  • 能写出"函数式 instructions + 带档案袋的工具"的组合。

前置回顾

入门版里你知道 context_variables 是一个"随身档案袋"，能在轮次间携带用户名、订单号这类程序数据。你也见过工具函数偶尔带一个 context_variables 参数就能读到袋子里的东西。但当时没细究：Swarm 凭什么知道要把袋子塞给这个函数？它又怎么保证 LLM 不会去乱填这个参数？这一章我们把这三处"看不见的手"全部摊到源码里。

一、魔法一：instructions 可以是一个函数

看 get_chat_completion 里生成 system prompt 的部分（core.py 第 42–46 行）：

swarm/core.py · 动态 instructions 
        instructions = (
            agent.instructions(context_variables)
            if callable(agent.instructions)
            else agent.instructions
        )
        messages = [{"role": "system", "content": instructions}] + history

逻辑很直白：如果 agent.instructions 是可调用的（一个函数），就把 context_variables 传进去、用它的返回值当 system prompt；否则就当普通字符串用。类型定义也印证了这点（types.py 第 17 行）：instructions: Union[str, Callable[[], str]]——它既可以是字符串，也可以是函数。

这意味着你的系统提示词可以随档案袋动态变化。用户名叫小明，system prompt 就自动变成"用小明称呼用户"；换个用户，提示词跟着换——不用你手动拼字符串。

小细节：defaultdict 兜底

注意第 41 行 context_variables = defaultdict(str, context_variables)。它把档案袋包成一个"取不到的键就返回空字符串"的字典。所以你的 instructions 函数里写 context_variables['name'] 即使 name 不存在也不会 KeyError，只会得到空串——让动态提示词更省心。

二、魔法二：按参数名注入档案袋

这是最"约定"的一处。看 handle_tool_calls 决定要不要给工具函数塞档案袋（core.py 第 119–121 行）：

swarm/core.py · 靠参数名决定注入 
            func = function_map[name]
            # pass context_variables to agent functions
            if __CTX_VARS_NAME__ in func.__code__.co_varnames:
                args[__CTX_VARS_NAME__] = context_variables
            raw_result = function_map[name](**args)

而 __CTX_VARS_NAME__ 就是一个字符串常量（core.py 第 23 行）：

swarm/core.py · 约定的名字 
__CTX_VARS_NAME__ = "context_variables"

拆开看这个判断：func.__code__.co_varnames 是 Python 提供的一个内省属性，里面装着这个函数所有局部变量名（含参数名）。Swarm 就检查："这个字符串 "context_variables" 在不在你的参数名单里？"在，就把真实的档案袋塞进 args，随后 **args 展开调用时自动传给你；不在，就当你不需要，什么都不做。

没有装饰器，没有注册表，没有类型标注要求。你想要档案袋？把工具函数的参数命名成 context_variables 就行——这就是"约定"。框架和你之间达成了一个不成文的默契：叫这个名字的参数，我负责给你填上。

类比：会议室门口的"资料架"

公司有个约定：谁的工位牌上写着"context_variables"这几个字，行政就自动把当天的资料袋放到他桌上；没写的人默认不需要、不发。行政不用挨个问、不用建登记表——规则就是规则，命名即声明。省去了一大堆登记、审批的流程，代价是：万一你把牌子写成了"context_variable"（少个 s），行政按规矩就当你不需要，你的桌上永远空空，还没人会提醒你写错了。

陷阱：参数名写错 = 静默拿不到档案袋

因为注入完全靠精确的参数名匹配，所以你的工具函数想拿到 context_variables，参数就必须一字不差地叫 context_variables。写成 ctx、context_vars、context_variable（少个 s）都拿不到——而且不会报任何错：if 判断为假，直接跳过注入，你的函数照常被调用，只是那个参数拿到的是它自己的默认值（或者因缺参而报 TypeError，取决于你怎么定义）。这是"魔法"式设计的典型代价：出错时没有提示，只能靠你记住约定。

三、魔法三：对 LLM 隐藏这个参数

还有个隐患：既然工具函数有 context_variables 这个参数，那生成给 LLM 看的工具 JSON schema 时（util.py 的 function_to_json 会把每个参数都列进 properties），LLM 会不会以为这也是它该填的参数，然后一本正经地编一个值填进去？那就乱套了——档案袋是程序内部数据，绝不该让 LLM 插手。

Swarm 在 get_chat_completion 里专门把它从 schema 里剔除（core.py 第 50–56 行）：

swarm/core.py · 对 LLM 隐藏 context_variables 
        tools = [function_to_json(f) for f in agent.functions]
        # hide context_variables from model
        for tool in tools:
            params = tool["function"]["parameters"]
            params["properties"].pop(__CTX_VARS_NAME__, None)
            if __CTX_VARS_NAME__ in params["required"]:
                params["required"].remove(__CTX_VARS_NAME__)

两步"抹除"：properties.pop("context_variables", None) 把这个参数从"可见字段"里删掉；再从 required（必填列表）里移除。于是 LLM 看到的工具签名里根本没有 context_variables 这一项，它既不会、也没法去填它。等到真正调用函数时，才由魔法二（第 120–121 行）在后台把真实档案袋悄悄补上。

这三处配合得天衣无缝：对你（开发者），命名即声明；对 LLM，这个参数完全隐形；对框架，运行时按名注入真实数据。

四、这套"约定"值不值

约定优于配置 vs 显式配置
Swarm：命名约定注入
  • 零配置：不用装饰器、不用注册、不用声明依赖，函数参数叫对名字就行。
  • 代码极简：核心逻辑就一个 if ... in co_varnames，几行搞定，读起来毫无负担。
  • 工具函数保持"普通函数"的样子，不被框架 API 侵入。
显式配置（装饰器 / 声明依赖）
  • 意图清晰：@inject_context 或显式 RunContext 参数一眼可见"这里要注入"。
  • 出错更早暴露：名字写错、类型不符能在注册/校验阶段就报出来。
  • 但更啰嗦、样板代码多，且把框架概念渗进了每个工具函数。

"约定"的甜头是极致简洁，苦头是魔法隐晦、出错静默。对一个想让你"读几百行就看懂全貌"的教学框架来说，这笔交易偏向了简洁——但代价是你必须记住这条约定，否则调试时会一头雾水。

可运行片段：函数式 instructions + 带档案袋的工具

下面改编自 examples/basic/context_variables.py，同时展示三处魔法（真跑需要 API Key）：

convention_demo.py 
from swarm import Swarm, Agent

client = Swarm()

# 魔法一：instructions 是函数，随档案袋动态生成
def instructions(context_variables):
    name = context_variables.get("name", "User")
    return f"You are a helpful agent. Greet the user by name ({name})."

# 魔法二：参数叫 context_variables，框架会自动注入
# 魔法三：这个参数对 LLM 隐藏，LLM 只会决定"要不要调用"，不会去填它
def print_account_details(context_variables: dict):
    user_id = context_variables.get("user_id", None)
    name = context_variables.get("name", None)
    print(f"Account Details: {name} {user_id}")
    return "Success"

agent = Agent(
    name="Agent",
    instructions=instructions,
    functions=[print_account_details],
)

context_variables = {"name": "James", "user_id": 123}

r1 = client.run(messages=[{"role": "user", "content": "Hi!"}],
                agent=agent, context_variables=context_variables)
print(r1.messages[-1]["content"])

r2 = client.run(messages=[{"role": "user", "content": "Print my account details!"}],
                agent=agent, context_variables=context_variables)
print(r2.messages[-1]["content"])
预期输出（措辞每次略有不同）
Hi James, how can I help you today?
Account Details: James 123
Your account details have been printed successfully.

注意 Account Details: James 123 这行是工具函数自己 print 出来的——它成功从被注入的档案袋里读到了 name 和 user_id。而 LLM 全程没有、也无法为 context_variables 提供任何值，它只负责决定"该调用 print_account_details"。三处魔法各司其职。

延伸：其他框架怎么传上下文？

把"约定式注入"放到坐标系里看会更清楚。OpenAI Agents SDK 走的是"显式依赖"路线：你定义一个上下文对象，工具函数通过一个明确的 RunContextWrapper 类型参数拿到它——签名里写得清清楚楚"我需要上下文"，靠类型而非名字识别，IDE 能补全、写错会被类型检查抓住。许多依赖注入（DI）框架则更进一步，用装饰器或容器显式登记"谁需要注入什么"。

对比之下，Swarm 的约定式最省事、样板最少，但也最"隐晦"：它把安全网（早期报错、IDE 提示）换成了简洁。这没有绝对优劣——教学框架图的是让你一眼看穿机制，生产框架图的是可维护、可静态分析。理解了这条光谱，你就能判断自己的项目该站在哪一侧。

常见疑问

如果我的工具既要 LLM 传的参数、又要 context_variables，会冲突吗？

不会。比如 def query(order_id: str, context_variables: dict)：order_id 会出现在给 LLM 的 schema 里（由 LLM 决定填什么），而 context_variables 被第 50–56 行剔除、由框架在第 120–121 行注入。两者井水不犯河水——一个来自模型，一个来自程序。

instructions 用函数和用字符串，性能上有区别吗？

可忽略。函数式 instructions 只是在每次 get_chat_completion 时多调用一次你的函数来生成字符串（第 43 行），开销极小。真正的价值是动态性——system prompt 能随档案袋、随对话进展而变，这是纯字符串做不到的。

本章小结

  • 魔法一（第 42–46 行）：instructions 可为函数，接收 context_variables 动态生成 system prompt。
  • 魔法二（第 119–121 行）：靠检查 "context_variables" 是否在函数参数名（co_varnames）里，决定要不要注入——命名即声明。
  • 魔法三（第 50–56 行）：从工具 JSON schema 的 properties 和 required 里 pop 掉该参数，对 LLM 隐藏。
  • 这套"约定优于配置"换来极致简洁，代价是魔法隐晦、参数名写错会静默失效。

档案袋的流转搞清了。而在魔法二里我们瞥见了一个更有意思的东西——工具函数的返回值会被 handle_function_result 处理。如果一个工具返回的不是字符串，而是另一个 Agent，会发生什么？下一章讲 Swarm 最惊艳的极简设计：handoff。
