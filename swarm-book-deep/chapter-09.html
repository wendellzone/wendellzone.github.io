09

让 Agent 会查资料（RAG）

上一章的 Agent 学会了读写数据库——可数据库里装的是结构化的行和列（订单、价格、用户）。但如果用户问的是"GPT-4 支持多长上下文？""怎么申请退款？"这类知识型问题呢？答案不在某张表的某个字段里，而散落在成百上千篇帮助文档中。这一章我们看 support_bot：它会先去一堆文档里翻出最相关的几段，再拿着这些段落作答。这个"先查资料再回答"的套路，就是当下最重要的 Agent 增强手法——RAG（检索增强生成）。

本章目标

  • 理解 RAG（检索增强生成）到底在做什么，以及它为什么能治"LLM 编造 / 知识过时"的病。
  • 看懂 support_bot 的两阶段架构：离线用 prep_data.py 把文档灌进向量库，在线用 main.py 检索并作答。
  • 搞清 embedding（向量化）与余弦相似度——为什么"语义搜索"能捕捉到关键词匹配抓不住的东西。
  • 看清 query_docs 工具如何把检索到的原文喂回给 LLM，以及这条链路上"检索不到就会编造"的真实风险。

前置回顾

入门版里你已经知道：Swarm 的"工具"就是普通 Python 函数，Agent 的 functions 列表列出它能调用的工具；LLM 决定调哪个、传什么参数，引擎负责执行并把返回值喂回去。上一章我们让工具连上了 SQLite，工具函数里出现了真实的读写副作用。这一章的工具依然是普通函数——query_docs(query)——但它背后连的不是关系数据库，而是一个向量数据库（Qdrant）。它的返回值也不再是"退款已发起"这样的确认，而是一段从文档里检索出来的原文，这段原文会成为 LLM 组织答案的依据。换句话说：本章的关键变化是，工具的职责从"执行动作"变成了"取回知识"。

类比：开卷考试

纯 LLM 直接答题，像是闭卷考试——全凭脑子里记住的东西，记错了、过时了、根本没学过，就只能硬编一个看起来像样的答案（这就是"幻觉"）。RAG 则是开卷考试：拿到题目后，先翻书找到最相关的那几段，再照着这几段组织答案。答得准不准，取决于两件事——翻书翻得对不对（检索质量），以及照着书写得好不好（生成质量）。support_bot 的"书"，就是 OpenAI 帮助中心的一堆文档。

一、RAG 是什么，为什么要它

RAG 的全称是 Retrieval-Augmented Generation——检索增强生成。拆开就是三步：检索（Retrieval，去知识库里找相关内容）、增强（Augmented，把找到的内容拼进给 LLM 的提示里）、生成（Generation，LLM 基于这些内容作答）。核心思想只有一句话：别让模型光凭记忆答，先给它喂相关资料，让它照着资料答。

为什么需要它？因为纯 LLM 有两个天生的短板：

  • 知识会过时：模型的知识冻结在训练截止那一刻。你新出的产品文档、上周改的退款政策，它压根不知道。
  • 会一本正经地编造：问它一个它不确定的事，它往往不会说"我不知道"，而是流畅地编出一个像模像样的答案——这就是幻觉，在客服场景里是致命的。

RAG 用一个"外挂知识库"同时治这两个病：知识库随时能更新（不用重训模型），而答案有据可查（基于检索到的真实原文）。support_bot 就是一个最小可用的 RAG 客服机器人。

二、两阶段架构：离线备料 vs 在线查询

这是本章最重要的心智模型。RAG 系统天然分成两个在不同时间跑的阶段，别把它们混为一谈：

  • 离线备料（prep_data.py）：只在文档更新时跑一次。它把每篇文档变成向量，连同元数据一起灌进向量库。这一步慢、要花钱（调 embedding 接口），但跑完就存住了。
  • 在线查询（main.py）：每次用户提问时跑。它把用户的问题也变成向量，去向量库里找最相似的几篇，取回原文喂给 LLM。这一步要快，而且是只读的——它不改动向量库。

打个比方：备料像是图书馆把新书编好目录、上好架（费工夫，但只做一次）；查询像是读者进来按目录找书（每次都做，但很快，且不改动书架）。下面分别看这两阶段的源码。

2.1 离线备料：prep_data.py 逐行精读

先看它怎么把 data/ 目录里的一堆 JSON 文章加载进来（prep_data.py 第 13–30 行）：

examples/support_bot/prep_data.py · 第 13–30 行 
article_list = os.listdir("data")

articles = []

for x in article_list:
    article_path = "data/" + x

    # Opening JSON file
    f = open(article_path)

    # returns JSON object as
    # a dictionary
    data = json.load(f)

    articles.append(data)

    # Closing file
    f.close()

data/ 目录里有 70 多篇 JSON 文章，每篇长这样（来自 data/article_6402865.json）：

examples/support_bot/data/article_6402865.json 
{
  "text": "Yes! Please check out our [DALL·E API FAQ] ... for information about the API.",
  "title": "Is DALL·E available through an API?",
  "article_id": "6402865",
  "url": "https://help.openai.com/en/articles/6402865-is-dall-e-available-through-an-api"
}

关键字段是 text（正文，用来算向量）和三个元数据——title / article_id / url（用来在检索后展示、溯源）。记住这个区分：正文拿去向量化，元数据只是随行的标签。接下来是备料的核心——把每篇文章的 text 变成向量（第 32–38 行）：

examples/support_bot/prep_data.py · 第 32–38 行 
for i, x in enumerate(articles):
    try:
        embedding = client.embeddings.create(model=EMBEDDING_MODEL, input=x["text"])
        articles[i].update({"embedding": embedding.data[0].embedding})
    except Exception as e:
        print(x["title"])
        print(e)
  • 第 34 行（向量化的一行）：client.embeddings.create(model="text-embedding-3-large", input=x["text"])。这就是 embedding（向量化）：把一段文本交给 OpenAI 的 embedding 模型，换回一串浮点数（一个高维向量）。语义相近的文本，向量在空间里也彼此靠近——这是整个 RAG 能"按意思找"的基石（第三节详解）。
  • 第 35 行：把算出来的向量 embedding.data[0].embedding 塞回文章字典的 "embedding" 键里，让向量和它的元数据待在一起。
  • 第 36–38 行（错误兜底）：try/except 包住——某篇文章向量化失败（比如内容异常）时打印标题继续，不让整个备料脚本因为一篇文章崩掉。备料是批处理，容错很重要。

向量算好了，接下来连向量库、建集合、写入（第 40–80 行）：

examples/support_bot/prep_data.py · 第 40–80 行 
qdrant = qdrant_client.QdrantClient(host="localhost")
qdrant.get_collections()

collection_name = "help_center"

vector_size = len(articles[0]["embedding"])

article_df = pd.DataFrame(articles)

# Delete the collection if it exists, so we can rewrite it changes to articles were made
if qdrant.get_collection(collection_name=collection_name):
    qdrant.delete_collection(collection_name=collection_name)

# Create Vector DB collection
qdrant.create_collection(
    collection_name=collection_name,
    vectors_config={
        "article": rest.VectorParams(
            distance=rest.Distance.COSINE,
            size=vector_size,
        )
    },
)

# Populate collection with vectors
qdrant.upsert(
    collection_name=collection_name,
    points=[
        rest.PointStruct(
            id=k,
            vector={
                "article": v["embedding"],
            },
            payload=v.to_dict(),
        )
        for k, v in article_df.iterrows()
    ],
)
  • 第 40 行：QdrantClient(host="localhost") 连上本地的 Qdrant（一个向量数据库）。它由 docker-compose 起在本机（端口见第五节）。
  • 第 45 行：vector_size = len(articles[0]["embedding"])——取第一篇文章向量的长度，作为整个集合的向量维度。text-embedding-3-large 的输出维度是固定的（3072 维），集合里所有向量必须同维，否则没法比较。
  • 第 51–53 行（先删后建）：如果集合已存在就先删掉。这样每次重跑备料都是全量重建——文档改了、加了、删了，重跑一遍就同步了。简单粗暴但对这个规模够用。
  • 第 56–64 行（建集合）：create_collection 声明这个集合怎么存向量。两个关键参数：distance=rest.Distance.COSINE 指定用余弦相似度衡量向量的"接近程度"（第三节讲）；size=vector_size 固定维度。注意向量被命名为 "article"——Qdrant 允许一个点挂多个命名向量，这里只用一个。
  • 第 68–80 行（批量写入）：upsert 把所有文章一次性灌进去。每篇文章包成一个 PointStruct：id 是行号；vector={"article": ...} 是向量本体；payload=v.to_dict() 是整篇文章的元数据（title/text/url 等）。
划重点：向量与元数据"分开存、一起取"

看清 PointStruct 的结构——vector 和 payload 是两个独立字段。vector（那串浮点数）只用来做相似度计算，机器读；payload（title/text/url）是给人和 LLM 看的原文与出处。检索时，Qdrant 先用 vector 算出"哪几篇最像"，再把这几篇的 payload 原样返回。向量负责"找到"，元数据负责"取回"——两者绑在同一个点上，缺一不可。

2.2 在线查询：main.py 的检索链路

备料存好后，在线这一侧的核心是 query_qdrant（main.py 第 20–37 行）——把用户问题变成向量，去库里搜：

examples/support_bot/main.py · 第 20–37 行 
def query_qdrant(query, collection_name, vector_name="article", top_k=5):
    # Creates embedding vector from user query
    embedded_query = (
        client.embeddings.create(
            input=query,
            model=EMBEDDING_MODEL,
        )
        .data[0]
        .embedding
    )

    query_results = qdrant.search(
        collection_name=collection_name,
        query_vector=(vector_name, embedded_query),
        limit=top_k,
    )

    return query_results
  • 第 22–29 行（把问题也向量化）：用和备料时同一个模型 EMBEDDING_MODEL 把用户 query 变成 embedded_query。这一步至关重要——问题和文档必须用同一个 embedding 模型投到同一个向量空间，它们的向量才可比较。
  • 第 31–35 行（检索）：qdrant.search(...)。query_vector=(vector_name, embedded_query) 是个元组，前一项 "article" 指定拿哪个命名向量来比（对应备料时建的那个），后一项是问题向量。limit=top_k（默认 5）表示只要最相似的前 5 篇——这就是 RAG 里常说的 top-k 检索。
  • 第 37 行：返回搜索结果列表，每个元素带着 payload（那篇文章的 title/text/url）和相似度得分。

但 query_qdrant 只是底层检索，Agent 真正能调的工具是 query_docs（第 40–63 行），它把检索结果整理成 LLM 能用的形状：

examples/support_bot/main.py · 第 40–63 行 
def query_docs(query):
    """Query the knowledge base for relevant articles."""
    print(f"Searching knowledge base with query: {query}")
    query_results = query_qdrant(query, collection_name=collection_name)
    output = []

    for i, article in enumerate(query_results):
        title = article.payload["title"]
        text = article.payload["text"]
        url = article.payload["url"]

        output.append((title, text, url))

    if output:
        title, content, _ = output[0]
        response = f"Title: {title}\nContent: {content}"
        truncated_content = re.sub(
            r"\s+", " ", content[:50] + "..." if len(content) > 50 else content
        )
        print("Most relevant article title:", truncated_content)
        return {"response": response}
    else:
        print("No results found.")
        return {"response": "No results found."}
  • 第 44–51 行：调 query_qdrant 拿回 top-5，再从每篇的 payload 里掏出 title / text / url，攒成一个列表。这里用的正是备料时存进 payload 的那些元数据字段。
  • 第 53–55 行（只取最相关的一篇）：output[0] 是相似度最高的那篇。把它的标题和正文拼成一段 response 文本——这就是要喂回给 LLM 的"参考资料"。注意：虽然检索了 5 篇，这里只把最相关的 1 篇喂回去。
  • 第 60 行（返回给 LLM）：return {"response": response}。工具返回的这段原文会作为工具结果回到对话里，LLM 看到它，再据此组织给用户的回答。
  • 第 61–63 行（兜底）：一篇都没检索到时返回 "No results found."。这句话会不会真的拦住 LLM 编造，是本章一个要专门警惕的点（见"陷阱"）。

三、embedding 与余弦相似度：为什么能"按意思找"

整个 RAG 的魔法都压在 embedding 这一步上，值得单独讲清楚。

embedding（向量化）把一段文本映射成一个高维空间里的点（一串浮点数）。这个模型经过训练，使得意思相近的文本，落点也相近。于是"检索最相关的文档"就变成了一个纯几何问题：在空间里找离"问题这个点"最近的几个"文档点"。

怎么衡量"近"？这里用的是余弦相似度（COSINE）——看两个向量之间夹角的大小，而不是它们的长度。夹角越小，方向越一致，就越相似（余弦值越接近 1）。用夹角而非距离的好处是：它只关心"方向（语义倾向）"，不受文本长短带来的向量长度差异干扰。这也正是备料时 create_collection 里 distance=rest.Distance.COSINE 那行的含义。

语义搜索 vs 关键词搜索

传统关键词搜索（比如 LIKE '%退款%'）只会匹配字面出现的词。用户如果问"我付的钱能要回来吗？"——里面根本没有"退款"二字，关键词搜索就抓瞎了。而 embedding 捕捉的是语义："要回钱"和"退款"在向量空间里离得很近，照样能被检索到。这就是 RAG 用向量检索而非关键词检索的根本原因：它按意思找，不按字面找。

四、Agent 编排：转交给"会查资料"的专家

工具 query_docs 挂在哪个 Agent 上？这里的编排很简洁（main.py 第 77–95 行）：一个门面 Agent 负责接待，一个帮助中心 Agent 负责查资料，前者通过 handoff 把用户转给后者。

examples/support_bot/main.py · 第 77–95 行 
def transfer_to_help_center():
    """Transfer the user to the help center agent."""
    return help_center_agent


user_interface_agent = Agent(
    name="User Interface Agent",
    instructions="You are a user interface agent that handles all interactions with the user. Call this agent for general questions and when no other agent is correct for the user query.",
    functions=[transfer_to_help_center],
)

help_center_agent = Agent(
    name="Help Center Agent",
    instructions="You are an OpenAI help center agent who deals with questions about OpenAI products, such as GPT models, DALL-E, Whisper, etc.",
    functions=[query_docs, submit_ticket, send_email],
)

if __name__ == "__main__":
    run_demo_loop(user_interface_agent)
  • 第 77–79 行（handoff 工具）：transfer_to_help_center 是一个返回另一个 Agent 的普通函数——这正是入门版讲过的 handoff：工具返回 Agent，引擎就把后续对话交给它。
  • 第 82–86 行（门面 Agent）：user_interface_agent 只有一个工具——把用户转给帮助中心。它是入口，负责"接待并分流"。
  • 第 88–92 行（会查资料的专家）：help_center_agent 挂了三个工具——query_docs（查知识库，本章主角）、submit_ticket（开工单）、send_email（发邮件）。它的 instructions 明确了角色：OpenAI 产品的帮助中心客服。
  • 第 95 行：run_demo_loop 从门面 Agent 起步。用户一进来先碰到它，被转交后才进入会查资料的帮助中心 Agent。

注意 help_center_agent 的工具组合很有讲究：能查到就用 query_docs 答；查不到或用户有具体诉求，就用 submit_ticket 开工单、用 send_email 跟进。RAG 不是万能的，配上"兜底动作"才是一个完整的客服闭环——这也引出了下一节要警惕的坑。

五、把它跑起来

运行前提（比上一章重）

本章比上一章多两个外部依赖：① 一个运行中的 Qdrant 向量库——用 docker-compose up -d 起在本机（docker-compose.yaml 里映射的是端口 6335），所以必须先装好并启动 Docker；② OpenAI API Key（export OPENAI_API_KEY=...）——备料和查询都要调 embedding 接口。完整流程见 Makefile：make install（装依赖）→ docker-compose up -d（起 Qdrant）→ make prep（跑 prep_data.py 灌数据）→ make run（跑 main.py）。不想真跑也完全没关系——本章的重点是看懂"离线灌数据、在线检索作答"这条逻辑链路，顺着源码读就够了，无需真的起服务或消耗额度。

顺序不能乱：必须先 make prep 把向量灌进 Qdrant，make run 才有东西可查。这正是"离线备料先于在线查询"的直接体现。下面是一段推演的交互（示意，LLM 实际措辞会不同；重点看"接待 → 转交 → 检索 → 据实作答"的路径）：

预期交互（推演 · 一次成功检索）
用户: DALL·E 有 API 吗？
[User Interface Agent] → transfer_to_help_center            # 门面判断这是产品问题，转交
[Help Center Agent] → 调用 query_docs("DALL·E 有 API 吗")
Searching knowledge base with query: DALL·E 有 API 吗        # query_docs 里的 print
Most relevant article title: Yes! Please check out our [DALL·E...  # 命中 article_6402865
[Help Center Agent] 是的，DALL·E 提供 API。你可以查看官方的     # LLM 基于检索到的原文组织回答
             DALL·E API FAQ 了解更多：
             https://help.openai.com/en/articles/6705023

看清这条链路：门面 Agent 先 handoff 给帮助中心 Agent；后者调 query_docs，工具内部把问题向量化、去 Qdrant 检索、取回最相关那篇的原文（{"response": "Title: ...\nContent: ..."}）；这段原文回到对话里，LLM 照着它组织出最终回答，连带把文档里的 URL 也一并给了用户。答案不是模型凭空想的，而是有出处的。

陷阱：检索不到时，LLM 仍可能"自由发挥"

务必记住：query_docs 返回的只是检索到的原文，最终答案仍由 LLM 组织生成。这中间有个危险的缝隙——当知识库里没有相关文档时，检索会返回一堆相似度很低、其实不相关的文章（向量检索总会返回 top-k，哪怕都不太沾边），或者返回 "No results found."。此时 LLM 可能：

  • 被那些勉强沾边的文章带偏，把不相关的内容当依据答出来；
  • 或者干脆无视"没查到"，凭自己的记忆编一个流畅但错误的答案——RAG 想治的"幻觉"又回来了。

正确做法是在流程和提示词层面立规矩：明确要求 Agent"只依据检索到的资料作答；查不到就老实说不知道，并用 submit_ticket 开工单转人工"。support_bot 给 help_center_agent 配上 submit_ticket / send_email，正是为了这个兜底出口——RAG 检索是"尽力而为"，而"查不到怎么办"必须由编排显式兜住，不能指望模型自觉。

深入：本例是"最小可用版"，生产 RAG 还差什么？

support_bot 把整篇文章当作一个向量存、检索时也整篇取回——这在文章都很短时够用，但生产级 RAG 通常还要加三样东西：

  • Chunking（分块）：长文档不应整篇算一个向量（语义会被"平均"掉，也可能超过模型输入上限）。实践中会把文档切成若干段落级的小块，各自向量化，检索时命中的是"最相关的那一小块"，更精准。
  • Rerank（重排）：向量检索快但粗。常见做法是先用向量召回较多候选（比如 top-50），再用一个更精细（也更慢）的重排模型对这些候选打分，选出真正最相关的几条喂给 LLM。召回求全、重排求准。
  • 混合检索（Hybrid Search）：把向量检索（语义）和关键词检索（BM25 等，精确匹配专有名词、型号、错误码）结合起来。纯语义检索有时会漏掉"必须字面命中"的词，混合检索取两者之长。

本例刻意省掉了这些，只为让你看清 RAG 最本质的骨架：向量化 → 存 → 检索 → 喂回。骨架理解了，上面这些都是往上加的"增强件"。

六、RAG 值不值：先查资料 vs 直接开答

RAG（先检索再作答）vs 纯 LLM（直接开答）
RAG · 先查资料再答
  • 答案有据可查：基于检索到的真实原文，还能给出文档 URL 供用户核对，大幅压低幻觉。
  • 知识可即时更新：政策/文档改了，重跑一次备料即可，无需重训模型。
  • 能覆盖模型没学过的私有知识：你自己的产品文档、内部 wiki 都能接进来。
  • 代价：要维护一个向量库、跑离线备料、还要为检索质量做调优（分块、top-k、重排……）。
纯 LLM · 直接开答
  • 简单：一个提示词就能跑，没有向量库、没有备料、没有额外基础设施。
  • 快：省掉了检索这一跳。
  • 代价：会编造——遇到不确定的就自信地胡说；知识过时——训练截止后的事一律不知道；够不着私有知识。

结论：只要问答涉及会变化的、私有的、或要求准确溯源的知识（客服、企业知识库、产品答疑就是典型），RAG 几乎是必选项——它用"维护一个向量库"的成本，换来"答案有据、知识可更新"的可靠性。反之，纯闲聊、创意写作这类不依赖外部事实的场景，直接让 LLM 开答反而更轻快。

常见疑问

为什么用户的问题也要用同一个 embedding 模型向量化？

因为向量之间能比较相似度的前提是它们在同一个向量空间里。不同的 embedding 模型会把文本投到不同的、不可通约的空间——就像一个用"经纬度"标位置、另一个用"街道门牌"，两套坐标没法直接算距离。所以备料时文档用 text-embedding-3-large，在线查询时问题必须也用它，两边的向量才可比。一旦换了 embedding 模型，整个向量库都得用新模型重新备料一遍。

为什么用余弦相似度，而不是普通的直线距离？

余弦相似度看的是两个向量的夹角（方向是否一致），不看它们的长度。在文本 embedding 里，向量的"方向"编码了语义倾向，而"长度"往往受文本长短等无关因素影响。用夹角衡量，就能只关心"意思像不像"，不被长短干扰。这也是为什么备料时 create_collection 明确指定了 distance=COSINE——建库时选定的度量方式，检索时会一直沿用。

为什么向量和元数据要分开存在 vector 和 payload 两个字段里？

因为它们的用途完全不同。vector（那串浮点数）只服务于相似度计算——机器拿它算"哪篇最像"，人根本读不懂。payload（title/text/url）才是要展示、要喂给 LLM、要给用户溯源的内容。检索时是"先用 vector 找到点，再取这个点的 payload 用"。分开存让职责清晰：vector 负责"定位"，payload 负责"内容"，两者绑在同一个 PointStruct 上一起取回。

在线查询会不会改动向量库？每次问都要重新备料吗？

不会，也不用。query_qdrant 里只有 qdrant.search(...)，这是纯只读操作——它只是去已经建好的库里找相似向量，不写、不改、不删。所以在线查询没有副作用，天然可并发、结果也可缓存（同一个问题的检索结果是稳定的）。只有当文档本身发生变化（新增、修改、删除文章）时，才需要重跑一次 prep_data.py 把向量库更新到最新——这正是"离线备料 vs 在线只读检索"这条分界线的意义。

本章小结

  • RAG = 检索增强生成：先去知识库检索相关资料，再让 LLM 照着资料作答。它治的是纯 LLM 的两大病——会编造和知识过时。类比"开卷考试：先翻书找相关段落，再作答"。
  • 两阶段架构是核心心智模型：离线备料（prep_data.py，文档更新时跑一次，把文档向量化后灌进 Qdrant）与在线查询（main.py，每次提问时把问题向量化、只读检索、取回原文喂回 LLM）。
  • embedding + 余弦相似度让检索能"按意思找"：语义相近的文本向量也相近，余弦相似度看夹角、只关心语义方向——这是关键词匹配做不到的。问题与文档必须用同一个 embedding 模型。
  • 向量与元数据分开存：PointStruct 里 vector 负责相似度计算、payload（title/text/url）负责取回展示与溯源，一起绑在同一个点上。
  • 检索到 ≠ 答对：最终答案仍由 LLM 组织，检索不到时它可能被弱相关结果带偏、甚至无视"没查到"继续编造。必须在编排上兜底——没查到就说不知道、开工单转人工（这正是 help_center_agent 配 submit_ticket / send_email 的用意）。
  • 本例是最小可用版；生产级 RAG 还要加 chunking（分块）、rerank（重排）、混合检索——但它们都是往这个"向量化→存→检索→喂回"骨架上加的增强件。

到这里，你的 Agent 已经会用工具、会读写数据库、会查资料了。可一个绕不开的问题浮现出来：你怎么知道它答得到底好不好？是真的据实作答，还是在编？检索准不准？下一章我们换个视角，聊聊怎么给 Agent 做评测——把"感觉它还行"变成"有指标、可衡量"。
