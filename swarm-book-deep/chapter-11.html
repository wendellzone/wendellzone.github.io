改造 Swarm 与 mini-Swarm

读懂一份代码最硬的证据，是能把它改了、甚至能自己重写一遍。这一章我们不再只是阅读 Swarm，而是动手：给工具加中间件、换一个模型、最后从零手写一个约四十行的 mini-Swarm。写完你会发现——Agent 框架的内核，其实就这么点东西。

本章目标

  • 用装饰器给工具函数加日志、重试、计时等"中间件"，体会"工具即普通函数"带来的可组合性。
  • 理解 Swarm(client=...) 的鸭子类型约定，学会指向本地 Ollama / 兼容网关，换掉底层模型。
  • 不 import swarm，从零写出一个能跑的 mini-Swarm，把 core.py 的 run 循环亲手复现一遍。
  • 看清自己写循环时最容易踩的坑，以及"从原型到生产还差什么"。

前置回顾

前面十章里，你已经把 Swarm 的内核拆得很细了：无状态引擎（第 01 章）、deepcopy 划出的副作用边界（第 02 章）、"工具就是带 docstring 的普通函数"（第 03 章）、"handoff 就是让工具返回一个 Agent"（第 04 章）、以及 run() 那个"问 LLM → 有没有工具调用 → 执行 → 追加结果 → 再问"的主循环（第 05 章）。这一章把这些认知反过来用：既然我懂了每一块，那我就能改它、能替换它、能重写它。

一、给工具加"中间件"：因为工具只是普通函数

回忆第 03 章的核心结论：Swarm 里的工具没有任何特殊基类、没有注册表、没有装饰器要求——它就是一个普通 Python 函数，靠 function_to_json（util.py 第 31–87 行）读它的签名和 docstring 生成给 LLM 的 schema。

这句"就是普通函数"有个立竿见影的好处：任何能作用在普通函数上的手段，都能作用在工具上。其中最顺手的就是装饰器。我们可以在不改动工具本身逻辑的前提下，给它包一层日志、重试、计时——也就是所谓的"中间件"。

1.1 一个 @with_logging 装饰器

先写一个最简单的：每次工具被调用时打印入参，返回时打印结果。

middleware.py · 日志装饰器 
import functools


def with_logging(func):
    """给工具函数加调用日志：打印入参与返回值。"""

    @functools.wraps(func)                 # ← 关键：保留原函数的 __name__ 和 __doc__
    def wrapper(*args, **kwargs):
        print(f"[调用] {func.__name__}  参数={kwargs or args}")
        result = func(*args, **kwargs)
        print(f"[返回] {func.__name__} -> {result!r}")
        return result

    return wrapper
为什么 functools.wraps 这里不是可选项？

Swarm 靠 func.__name__ 建立"函数名 → 函数"的映射（core.py 第 96 行 function_map = {f.__name__: f for f in functions}），又靠 func.__doc__ 生成工具描述（util.py 第 80 行）。如果你不加 @functools.wraps，包装后的函数名会变成 "wrapper"、docstring 会丢失——LLM 看到的工具全叫 wrapper，还没有说明，直接乱套。给 Swarm 工具写装饰器，functools.wraps 是必需的。

1.2 一个 @with_retry 装饰器

再写一个带参数的：工具抛异常时自动重试若干次（真实世界里，工具常常要调外部 API，偶发失败很正常）。

middleware.py · 重试装饰器 
import time


def with_retry(times=3, delay=0.5):
    """失败自动重试。times 次都失败才把异常抛出去。"""

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_err = None
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:      # 生产里应收窄成具体异常类型
                    last_err = e
                    print(f"[重试] {func.__name__} 第 {attempt} 次失败：{e}")
                    time.sleep(delay)
            raise last_err                  # 重试用尽，把最后一次异常抛出

        return wrapper

    return decorator

1.3 把中间件叠在工具上

装饰器可以像洋葱一样一层层叠。下面给一个"查天气"工具同时加上重试和日志，然后把它挂到 Agent 上——Swarm 那边完全不需要任何改动，它拿到的仍然是一个"名字对、docstring 对"的普通函数。

use_middleware.py 
from swarm import Swarm, Agent
from middleware import with_logging, with_retry


@with_logging                 # 外层：记录每次调用
@with_retry(times=3)          # 内层：失败先重试
def get_weather(city: str):
    """查询某个城市的天气。"""
    # 假装这里在调一个偶尔抽风的外部 API
    return f"{city} 今天晴，26℃"


agent = Agent(
    name="天气助手",
    instructions="你是一个天气助手，需要时调用 get_weather。",
    functions=[get_weather],  # ← 挂的是被装饰后的函数，Swarm 无感知
)

client = Swarm()
resp = client.run(agent=agent,
                  messages=[{"role": "user", "content": "北京天气怎么样？"}])
print(resp.messages[-1]["content"])
预期输出（需要 API Key 才能真跑；措辞略有不同）
[调用] get_weather  参数={'city': '北京'}
[返回] get_weather -> '北京 今天晴，26℃'
北京今天天气晴朗，气温 26℃，适合出门～
这就是"可组合性"的红利

因为 Swarm 没有给工具规定任何形态，工具就退化成了"最普通的函数"；而最普通的函数，正好能享受 Python 生态里所有现成的函数级工具——装饰器、functools、contextlib……不给约束，反而换来了最大的自由。这正是第 03 章"约定优于配置"哲学在改造场景下的回报。

二、换一个模型：Swarm(client=...) 的鸭子类型约定

很多人以为 Swarm 被"锁死"在 OpenAI 上。其实不然。再看一眼构造函数（core.py 第 27–30 行）：

swarm/core.py · __init__ 
class Swarm:
    def __init__(self, client=None):
        if not client:
            client = OpenAI()
        self.client = client       # ← 只是存下来，没有任何类型检查

再看它唯一真正用到 self.client 的地方（core.py 第 69 行）：

swarm/core.py · get_chat_completion 的最后一行 
        return self.client.chat.completions.create(**create_params)

看清楚了：Swarm 对 client 的全部要求，就是它得有一条 .chat.completions.create(...) 的调用路径，并返回一个"长得像 OpenAI Chat Completions"的响应对象（能取 .choices[0].message）。它从不检查 client 到底是不是 OpenAI 类的实例——这就是 Python 的鸭子类型：只要走起来像鸭子、叫起来像鸭子，它就当你是鸭子。

2.1 指向本地 Ollama / 兼容网关

许多本地推理服务（如 Ollama）和第三方网关，都刻意提供了"兼容 OpenAI"的 HTTP 接口。于是你只要构造一个改了 base_url 的 OpenAI 客户端，塞给 Swarm 就行：

use_local_model.py 
from openai import OpenAI
from swarm import Swarm, Agent

# 指向本地 Ollama 的 OpenAI 兼容端点
local_client = OpenAI(
    base_url="http://localhost:11434/v1",   # Ollama 的兼容接口
    api_key="ollama",                        # 本地服务通常不校验，填个占位即可
)

client = Swarm(client=local_client)          # ← 把自定义 client 交给 Swarm

agent = Agent(
    name="本地助手",
    model="llama3.1",                        # ← 用本地拉下来的模型名
    instructions="你是一个跑在本地的小助手。",
)

resp = client.run(agent=agent,
                  messages=[{"role": "user", "content": "用一句话介绍你自己。"}])
print(resp.messages[-1]["content"])
预期输出（需本地已运行 Ollama 并拉取对应模型；措辞随模型而异）
我是一个运行在你本地机器上的小助手，不联网也能陪你聊天～

注意 agent.model（types.py 第 16 行，默认 "gpt-4o"）这时要改成本地实际拥有的模型名——它会原样传进 create_params["model"]（core.py 第 59 行）。换模型这件事，在 Swarm 里几乎是零成本的：换 client、改 model，别的一行都不用动。

2.2 灵活的另一面：隐式约定的脆弱

鸭子类型让"换模型"变得极其轻巧，但这份轻巧是有代价的。

"隐式接口约定"的灵活 vs 脆弱
灵活：无需正式抽象层
  • 不必实现任何 LLMProvider 基类或适配器接口——凑齐一条方法路径就能用。
  • 任何"兼容 OpenAI"的服务（本地、私有、代理网关）都能即插即用。
  • Swarm 核心因此不用背任何"多后端适配"的复杂度，保持了极简。
脆弱：没有契约，出错在运行时
  • 兼容性没有任何静态保证——某个字段（如 tool_calls、parallel_tool_calls）不被支持，要到真跑起来才报错。
  • 本地模型对 function calling 的支持参差不齐，工具调用可能时灵时不灵。
  • 响应结构只要有一点点不像 OpenAI，message.tool_calls（core.py 第 275 行）这类访问就会崩。

一句话：Swarm 用"约定"代替了"抽象层"。对一个教学与轻量使用为主的框架，这笔交易很值；但当你要接的模型离 OpenAI 越远，这份"隐式契约"就越可能在运行时给你惊吓。生产系统里，通常要在 Swarm 外面再包一层自己的"客户端适配 + 冒烟测试"来兜底。

三、亲手写一个 mini-Swarm（本章高潮）

现在来做最能证明"你真的懂了"的事：不 import swarm，只依赖 openai SDK，从零写一个能跑的极简版。目标是让你亲眼看到——core.py 里那个 run 循环，剥掉流式、deepcopy、debug 之后，骨架其实只有几十行。

3.1 极简 Agent 与 function_to_schema

先用 dataclass 定义一个只有三样东西的 Agent，再写一个简化版的"函数转 schema"（对照 util.py 的 function_to_json，我们只保留最常用的类型映射）。

mini_swarm.py · 第 1 段：Agent 与 schema 
import json
import inspect
from dataclasses import dataclass, field
from openai import OpenAI


@dataclass
class Agent:
    """极简 Agent：只有名字、系统提示、和一组工具函数。"""
    name: str = "Agent"
    instructions: str = "You are a helpful agent."
    functions: list = field(default_factory=list)


def function_to_schema(func) -> dict:
    """把普通函数转成 OpenAI tools 需要的 JSON（对照 util.py 的简化版）。"""
    type_map = {str: "string", int: "integer", float: "number", bool: "boolean"}
    sig = inspect.signature(func)
    properties, required = {}, []
    for name, param in sig.parameters.items():
        properties[name] = {"type": type_map.get(param.annotation, "string")}
        if param.default is inspect.Parameter.empty:
            required.append(name)
    return {
        "type": "function",
        "function": {
            "name": func.__name__,
            "description": func.__doc__ or "",     # docstring 当描述
            "parameters": {"type": "object",
                           "properties": properties,
                           "required": required},
        },
    }

3.2 核心：约四十行的 run 循环

下面是全书的"手术台"——把 core.py 第 252–292 行的 run、第 89–137 行的 handle_tool_calls、第 71–87 行的 handle_function_result，压缩进一个函数里。逐行都有中文注释，请对照图 11-1 阅读。

mini_swarm.py · 第 2 段：核心 run 循环 
client = OpenAI()   # 想换本地模型？改成 OpenAI(base_url=..., api_key=...)


def run(agent: Agent, messages: list, max_turns: int = 10):
    active_agent = agent                        # 当前是谁在干活（可能中途被换）
    messages = messages.copy()                  # 不改调用者的原始列表（对应 deepcopy）

    for _ in range(max_turns):                  # 主循环护栏：最多转这么多圈
        tools = [function_to_schema(f) for f in active_agent.functions]
        func_map = {f.__name__: f for f in active_agent.functions}

        # ① 问 LLM：带上系统提示 + 全部历史 + 可用工具
        completion = client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role": "system", "content": active_agent.instructions}]
                     + messages,
            tools=tools or None,
        )
        message = completion.choices[0].message
        messages.append(message.model_dump())   # 把 LLM 这条回复追加进历史

        # ② 没有工具调用 → 这就是最终答复，收工
        if not message.tool_calls:
            break

        # ④ 有工具调用 → 逐个执行
        for tool_call in message.tool_calls:
            name = tool_call.function.name
            args = json.loads(tool_call.function.arguments)   # 参数是 JSON 字符串！
            result = func_map[name](**args)                   # 真正调用那个普通函数

            # 工具返回的若是一个 Agent，就切换 active_agent（这就是 handoff！）
            if isinstance(result, Agent):
                active_agent = result
                content = json.dumps({"assistant": result.name})
            else:
                content = str(result)

            # ⑤ 把工具结果以 role=tool + 对应的 tool_call_id 追加回历史
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,     # 必须回填，让 LLM 知道对应哪次调用
                "content": content,
            })
        # ⑥ 循环回到开头，带着新结果再问一次 LLM

    return messages, active_agent               # 把新历史和最终 Agent 交还给调用者
对照真身：几乎一一对应

这四十行几乎能和 core.py 逐段对上：active_agent = agent 对应第 252 行；while/for 循环护栏对应第 257 行的 len(history) - init_len < max_turns；"问 LLM"对应第 260–268 行的 get_chat_completion；"无 tool_calls 就 break"对应第 275–277 行；"逐个执行 + 追加 role=tool"对应 handle_tool_calls 第 100–132 行；"返回值是 Agent 就切换"对应第 76–80 行 + 第 285–286 行。真身多出来的，主要是流式、deepcopy、debug、以及把 context_variables 注入工具的那几行——都是"锦上添花"，不是骨架。

陷阱：自己写循环时最常漏的两件事

① 忘了用 role=tool + 正确的 tool_call_id 把工具结果追加回 messages。OpenAI 的协议要求：只要上一条 assistant 消息里出现了 tool_calls，下一步就必须为每一个 tool_call 补上一条对应的 role=tool 消息（tool_call_id 要一一对上）。漏了、或 id 对不上，下一次 create 会直接报 400 错误；就算不报错，LLM 也收不到工具的结果，等于白调。
② 忘了 arguments 是 JSON 字符串。tool_call.function.arguments 是一个字符串（例如 '{"city": "北京"}'），不是 dict。必须先 json.loads 再 **args 展开，否则会把整个字符串当成一个位置参数传进去，直接 TypeError。Swarm 在 core.py 第 114 行替你做了这步。

可运行片段：用 mini-Swarm 跑一个 get_weather

把上面两段拼起来（mini_swarm.py），加一个工具和入口，就能跑了。需要 pip install openai 并设置 OPENAI_API_KEY。

mini_swarm.py · 第 3 段：跑起来 
def get_weather(city: str):
    """查询某个城市的天气。"""
    return f"{city} 晴，26℃"


if __name__ == "__main__":
    agent = Agent(
        name="天气助手",
        instructions="你是天气助手，需要时调用 get_weather，并用中文自然作答。",
        functions=[get_weather],
    )
    history, final_agent = run(
        agent,
        [{"role": "user", "content": "上海今天天气怎么样？"}],
    )
    print("最终 Agent：", final_agent.name)
    print("最终答复：", history[-1]["content"])
预期输出（需要 API Key；措辞每次略有不同）
最终 Agent： 天气助手
最终答复： 上海今天天气晴朗，气温 26℃，很适合出门～

整个过程里发生了什么，可以顺着历史 messages 复盘：user 提问 → assistant 决定调用 get_weather(city="上海")（这条带 tool_calls）→ 我们执行工具、追加一条 role=tool 的结果 → 再问 LLM → 这次它不需要工具了，直接用中文作答（无 tool_calls，break）。你刚刚亲手复现了 Swarm 的一次完整 run。

延伸：mini-Swarm 想上生产，还差哪些东西？

我们的四十行只是"骨架跑通"，离能扛真实流量还很远。至少还缺：

  • 流式输出：真身用 run_and_stream（core.py 第 139–229 行）逐块 yield，我们完全省了。
  • 并发工具调用：LLM 可能一次返回多个 tool_calls，生产里往往要并发执行而非串行。
  • 超时与取消：工具卡住、模型不返回时的兜底。
  • tracing / 可观测性：每一步的耗时、token、决策链路要能被追踪。
  • 结构化错误：工具不存在、参数非法、模型返回畸形——真身在 core.py 第 103–113 行、util.py 里都有兜底，我们统统省了。
  • 护栏（guardrails）：输入/输出的安全校验、越权工具的拦截。

这份清单正好通向本书最后一章——第 12 章会把"从学习原型走向生产要补的能力"系统地铺开。

常见疑问

装饰器叠的顺序有讲究吗？@with_logging 在上还是 @with_retry 在上？

有。装饰器从下往上包裹：最靠近函数的那个是最内层。本章示例里 @with_retry 在下（内层）、@with_logging 在上（外层），意味着"每次真正的调用尝试都在重试逻辑里，而日志只在最外层记一次入参/最终结果"。如果你想让每一次重试都打日志，就把 @with_logging 放到内层。顺序不同，语义不同——但因为都用了 functools.wraps，最外层暴露给 Swarm 的 __name__/__doc__ 始终是原函数的，不受影响。

换成本地模型后，工具调用不稳定，是我写错了吗？

大概率不是你的锅。这正是本章第二节"隐式约定脆弱"那一面：function calling 的支持质量高度依赖具体模型。有些本地小模型对 tools 的遵循度很差，会该调工具时不调、或把参数拼错。排查顺序：先确认该模型官方声明支持 function calling；再用 debug=True（Swarm 真身支持）看它到底返回了什么；必要时把工具数量减到一个、把 instructions 写得更直白。这是模型能力问题，不是 Swarm 的问题。

mini-Swarm 没处理 context_variables，会缺什么？

会缺"把随身档案袋注入工具"的能力。真身在 core.py 第 120–121 行会检查工具函数签名里有没有名为 context_variables 的参数，有就自动把当前档案袋塞进去（第 03 章讲过这个约定）。我们的 mini 版为了聚焦主循环，把它省了——如果你想补上，只需在执行工具前判断 "context_variables" in inspect.signature(func).parameters，是就把它加进 args。这也是个很好的练习：亲手把这条约定加回去，你对第 03 章会理解得更深。

本章小结

  • 工具就是普通函数，所以能用装饰器加日志/重试/计时等中间件——记得 functools.wraps，否则 __name__/__doc__ 会丢，Swarm 就认不出工具了。
  • Swarm(client=...) 只认鸭子类型：凑齐 .chat.completions.create 就能用，改 base_url 即可接本地 Ollama / 兼容网关，换模型近乎零成本；代价是没有正式抽象层，兼容性靠约定、出错在运行时。
  • 约四十行就能写出能跑的 mini-Swarm，与 core.py 的 run 几乎逐段对应——Agent 框架的内核确实就这么点东西。
  • 自己写循环最容易漏：用 role=tool+正确 tool_call_id 追加结果、以及 arguments 要 json.loads。
