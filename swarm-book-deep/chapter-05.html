主循环的边界与健壮性

前四章我们看了状态、边界、注入、交接。现在把镜头拉回 run() 的那个 while 循环本身——它凭什么不会永远转下去？工具名写错会不会让整个程序崩掉？"并行工具调用"到底并不并行？这一章专讲主循环里那些不起眼、却决定健壮性的护栏细节。

本章目标

  • 看懂 while 条件里的两道护栏：max_turns 防死循环、active_agent 为 None 时停。
  • 理解工具缺失时的容错：不崩溃，而是追加错误消息继续。
  • 澄清一个高频误解：parallel_tool_calls 不等于框架并行执行工具。
  • 明白 model_dump_json 洗数据、以及 execute_tools=False "只取意图不执行"的用意。

前置回顾

入门版把 run() 主循环讲成"调模型 → 有工具就执行 → 再调模型 …… 直到没有工具调用为止"。这个骨架没错，但它回避了所有"万一"：万一 LLM 陷入"调工具→调工具→……"停不下来？万一它点了一个根本不存在的工具？万一你只想看看它打算调什么、却不真的执行？这一章就是把这些"万一"对应的防御代码，从主循环里一条条挖出来。

一、护栏一：while 条件里的两把锁

看 run() 主循环的入口条件（core.py 第 257 行）：

swarm/core.py · while 条件 
        while len(history) - init_len < max_turns and active_agent:

一行里藏了两道护栏：

  • len(history) - init_len < max_turns：还记得第 02 章的 init_len（起跑线）吗？len(history) - init_len 就是"本轮已经新增了多少条消息"，也就是循环已经跑了多少步。一旦达到 max_turns，循环停止。这是防死循环的护栏——万一 LLM 陷入"调工具→再调工具→……"永不收尾，max_turns 能强行喊停。
  • and active_agent：如果 active_agent 变成了 None，循环也停。这给了一种"主动退场"的可能——工具可以通过返回一个把 agent 置空的 Result 来终止编排（回忆第 04 章：partial_response.agent 决定了下一轮的 active_agent）。
陷阱：max_turns 默认是无穷大

run() 的签名里 max_turns: int = float("inf")（第 239 行）——默认没有上限。这意味着如果你不显式传 max_turns，一旦模型和工具配合出了"你调我、我调你"的死循环，理论上它会一直转下去、烧掉大量 token 和费用。生产里强烈建议显式设一个合理的 max_turns（比如 10、20），把这道护栏真正用起来，而不是依赖默认的"无穷"。

二、护栏二：工具名不存在也不崩

LLM 有时会"幻觉"出一个并不存在的工具名。看 handle_tool_calls 怎么兜底（core.py 第 100–113 行）：

swarm/core.py · 工具缺失的容错 
        for tool_call in tool_calls:                 # 第100行：串行遍历每个工具调用
            name = tool_call.function.name
            # handle missing tool case, skip to next tool
            if name not in function_map:             # 第103行：这个工具存在吗？
                debug_print(debug, f"Tool {name} not found in function map.")
                partial_response.messages.append(
                    {
                        "role": "tool",
                        "tool_call_id": tool_call.id,
                        "tool_name": name,
                        "content": f"Error: Tool {name} not found.",   # 第110行：写一条错误消息
                    }
                )
                continue                             # 第113行：跳过，继续下一个

关键在不抛异常、不中断：工具名不在 function_map 里时，Swarm 追加一条 role=tool 的错误消息（content 是 "Error: Tool X not found."），然后 continue 跳到下一个工具调用。这条错误消息会随历史回到 LLM 眼前——模型看到"刚才那个工具不存在"，往往能在下一轮自我纠正，换个正确的工具或直接回答。整个程序不会因为一次幻觉就崩掉。

三、澄清：parallel_tool_calls 不等于并行执行

这是全书最容易被误解的一处。先看两个事实。事实一，工具是在一个普通的 for 循环里一个接一个执行的（core.py 第 100 行那个 for tool_call in tool_calls）——纯串行，没有任何线程/协程并发。事实二，Agent 有个字段 parallel_tool_calls 默认为 True（types.py 第 20 行），它被传给 OpenAI（core.py 第 66–67 行）：

swarm/core.py · parallel_tool_calls 传给 OpenAI 
        if tools:
            create_params["parallel_tool_calls"] = agent.parallel_tool_calls

把两个事实拼起来，真相就清楚了：parallel_tool_calls 只是允许 LLM 在一次回复里一口气点多个工具（一次"下多张单"），它决定的是"模型能不能一轮返回多个 tool_calls"，而不是"框架并行执行这些工具"。拿到这些 tool_calls 后，Swarm 依旧是老老实实地用 for 循环串行跑完的。

类比：一次点多道菜 vs 后厨同时开火

parallel_tool_calls=True 好比允许你在餐厅一次性点三道菜（而不是吃完一道再点下一道）。但后厨（Swarm 的 for 循环）是一个厨师按顺序一道一道做的——点单可以并行，出菜依然串行。想让后厨真正"同时开三个灶"，得自己改造框架（用 asyncio/线程池并发执行工具），那是第 11 章"动手改造"的话题。

四、护栏四：把 OpenAI 类型"洗"成普通 dict

模型返回的 message 是 OpenAI SDK 的 pydantic 对象。Swarm 没有直接把它塞进 history，而是先"洗"一遍（core.py 第 271–273 行）：

swarm/core.py · 洗成普通 dict 
            history.append(
                json.loads(message.model_dump_json())
            )  # to avoid OpenAI types (?)

model_dump_json() 把 pydantic 对象序列化成 JSON 字符串，json.loads 再把它解析回一个纯粹的 Python dict。为什么要多这一道？因为这样 history 里存的全是普通 dict，而不是 OpenAI 的特定类型——避免 OpenAI 的类型渗进你的历史：历史因此可以被 json.dumps 直接序列化（存数据库、写文件、跨进程传都方便），也不会因为 SDK 升级换了对象结构而影响你已存的历史。源码注释末尾那个 (?) 很可爱——它坦承这是个务实的权宜之举，但效果确实是让 history 保持"干净的普通数据"。

五、护栏五：execute_tools=False，只看意图不执行

看主循环里决定"是否收尾"的那行（core.py 第 275 行）：

swarm/core.py · execute_tools 开关 
            if not message.tool_calls or not execute_tools:
                debug_print(debug, "Ending turn.")
                break

两种情况会 break 收尾：没有工具调用（模型给出了最终答复），或者 execute_tools 为 False。后者是个很妙的开关：当 execute_tools=False 时，即便模型点了工具，Swarm 也不真去执行，而是直接把"模型打算调用哪些工具"作为结果返回给你。

这有什么用？你能拿到模型的"意图"而不产生任何真实副作用——不查数据库、不发请求、不转账。这正是评测（第 10 章）要用的能力：给定一个输入，我只想验证"模型是否决定调用正确的工具"，而不希望真的执行它。execute_tools=False 就是为这类"只测决策、不测执行"的场景埋下的伏笔。

可运行/可读小实验

实验一：用 max_turns 和 debug 观察循环轮数。把 max_turns 设成 1，循环最多跑一圈就停；开 debug=True 能看到每一步的日志（真跑需要 API Key）：

loop_guard_demo.py 
from swarm import Swarm, Agent

client = Swarm()

def get_weather(city: str):
    """查询天气"""
    return f"{city} 今天晴，26 度。"

agent = Agent(name="Agent", instructions="你是天气助手，需要时调用工具。",
              functions=[get_weather])

# max_turns=1：最多跑一圈。debug=True：打印每一步内部日志
response = client.run(
    agent=agent,
    messages=[{"role": "user", "content": "北京天气怎么样？"}],
    max_turns=1,      # ← 把防死循环护栏收紧到 1 轮
    debug=True,       # ← 观察循环实际跑了几轮
)
print("本轮新增消息数：", len(response.messages))
预期现象
[时间戳] Getting chat completion for...: [...]
[时间戳] Received completion: [...]      ← 只出现一轮（因为 max_turns=1）
本轮新增消息数： 1

把 max_turns 去掉（用默认无穷），同样的问题模型通常会跑两轮：第一轮点 get_weather，第二轮拿到天气再组织成自然语言答复。对比两次的 debug 日志，就能直观看到护栏①在起作用。

实验二（说明）：故意调用不存在的工具看容错。如果模型幻觉出一个 function_map 里没有的工具名，你不会看到程序崩溃，而会在返回的历史里发现一条 content 为 "Error: Tool xxx not found." 的 role=tool 消息（来自第 110 行）。模型下一轮读到这条错误，通常会改调正确的工具或直接作答——这就是护栏②"容错跳过"的实际效果。

六、两组取舍

max_turns 有限 vs 无限 · 容错跳过 vs 直接抛错
Swarm：有护栏 + 容错跳过
  • max_turns 一旦设定，就有确定的上界，绝不会烧钱到失控。
  • 工具缺失时写错误消息继续，把纠错机会交回给模型，鲁棒性好。
  • 单次 run 是可终结的——要么达成、要么触顶、要么 agent 置空。
无限轮 / 直接抛错
  • 无限轮"更自由"，但默认 inf 埋着失控烧钱的隐患，必须自己收紧。
  • 工具缺失就抛异常，能更早暴露问题，但一次幻觉就让整个对话崩掉，对用户不友好。
  • 严格性换来了脆弱性——是否合适取决于你更怕"悄悄跑偏"还是"直接挂掉"。

常见疑问

max_turns 到底是"对话轮数"还是"消息条数"？

看第 257 行，比较的是 len(history) - init_len，也就是本轮新增的消息条数，而不是"来回对话的轮数"。一次模型回复算一条、一次工具调用结果也算一条，所以一个"调工具再答复"的完整交互会消耗好几条。设 max_turns 时按"消息条数上界"来理解，别按"人类感知的对话回合"来估。

parallel_tool_calls 设成 False 有什么用？

它会告诉 OpenAI"每次回复最多只点一个工具"。当你希望模型一步一步来、便于观察和调试，或某些工具有先后依赖不宜一次全点时，设 False 更可控。但要记住：无论 True 还是 False，Swarm 这边永远是串行执行的——这个开关只影响模型"一次点几个"，不影响框架"怎么跑"。

本章小结

  • while 双条件（第 257 行）：max_turns 防死循环、active_agent 为 None 时停；但 max_turns 默认无穷，生产要显式设值。
  • 工具名不存在时不崩溃：追加 "Error: Tool X not found." 并 continue（第 103–113 行），把纠错交回模型。
  • 工具是 for 循环串行执行（第 100 行）；parallel_tool_calls（默认 True）只让模型一次多点几个，不代表框架并行。
  • model_dump_json（第 271–273 行）把消息洗成普通 dict，避免 OpenAI 类型污染历史；execute_tools=False（第 275 行）只取意图不执行，为第 10 章评测埋下伏笔。
